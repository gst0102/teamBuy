# 全项目用户体验与性能：第一性原理与对抗式审查报告

日期：2026-09-03

## 1. 审查结论

本轮没有直接修改业务代码，完成了全项目小程序、前端服务层、后端列表接口、缓存/媒体链路、登录/分享/积分相关代码的体验与性能审计。

当前最重要的结论不是“所有页面都慢”，而是有四条机制会在特定条件下直接损害用户信任或首屏体验：

1. 公开资料详情的首屏数据可能等待图片下载和本地缓存完成。
2. 互帮互助大厅在展示任务前先做本地迁移和最多 20 页服务端同步。
3. 群资源库把加载中、请求失败和真实空列表都呈现为空态，且刷新时会先清掉已有列表。
4. 旧商机页面在接口为空或失败时展示逼真的内置示例商机，页面没有明确标识示例数据，部分示例操作还会反馈成功。

以上问题中，第 4 项是信任和数据真实性风险；第 1、2、3 项是首屏和恢复能力风险。它们需要优先处理，不能被“接口测试通过”掩盖。

当前没有通过静态代码审查确认的新增 P0 结算、积分、联系方式越权或原生分享回调错误；但这不等于已经完成微信开发者工具人工验收，真实首屏耗时、系统字体和分享面板仍未知。

## 2. 第一性原理判定标准

用户打开任意高频页面，真正需要完成的是一条最短闭环：

```text
打开 → 立即看懂当前状态 → 选一个动作 → 得到可验证反馈 → 失败时能重试或恢复
```

因此本轮不以“有没有接口”和“有没有页面”为完成标准，而以以下五项损失最小化为标准：

- 等待损失：首屏是否被非关键媒体、统计或同步任务阻塞。
- 认知损失：用户能否区分加载中、成功为空、请求失败和示例数据。
- 操作损失：主要动作是否可见、可点击、不会因为字号或固定宽度变形。
- 恢复损失：失败后是否保留可用旧数据、提供重试和明确原因。
- 信任损失：展示内容、积分、审核、完成状态、联系方式和分享结果是否真实可追溯。

## 3. 已确认问题

### P1：公开资料详情首屏被图片缓存链路阻塞

证据：

- `miniprogram/services/api.js:675-684` 的 `fetchPublicNote()` 在返回前等待 `normalizeAndCacheNote()`。
- `miniprogram/utils/media-cache.js:201-224` 的 `withCachedMedia()` 会等待封面和最多 3 张图片下载、保存后才返回 `displayUrl`。
- `miniprogram/pages/note-preview/index.js:1050-1095` 在拿到上述结果后才设置主要视图；随后还要加载客户操作配置。

影响：

在冷缓存、弱网、图片较大或某张图片下载失败重试时，用户看到资料正文的时间会被媒体任务拉长。资料正文是首屏主价值，图片应是附属资源；当前链路的等待顺序与产品目标相反。

建议：

- 详情接口先返回可渲染的文本、字段和媒体 URL；本地媒体缓存改为后台预热。
- 首屏只使用已经存在的本地缓存，未命中时先用远端 URL 或明确图片占位，不等待 `saveFile`。
- 将客户动作配置、地图解析、分享图准备与正文首屏解耦，并显示局部加载状态。

验收：冷启动打开含 3 张大图的公开资料，先出现标题/正文/主操作，再逐张补齐图片；任意图片失败不能让正文消失。

### P1：互帮互助大厅在首屏前执行完整同步

证据：

- `miniprogram/subpackages/my-tools-mutual-help/index/index.js:52-75` 的 `refresh()` 先 `await shared.syncServerTasks()`，之后才从本地任务生成页面数据。
- `miniprogram/subpackages/my-tools-mutual-help/shared.js:621-650` 会先逐条迁移旧本地任务，再分别拉取公开任务和本人任务，每类最多循环 20 页、每页 50 条。

影响：

用户打开“互帮互助”时，已有本地快照也不能立即展示；任务数或历史迁移增大后，首屏等待会随数据量增长。网络慢时用户容易误认为白屏、无任务或功能不可用。

建议：

- 先读取用户隔离的本地任务快照并渲染，再后台同步服务端。
- 旧本地任务迁移改为后台队列或单独状态，不阻塞任务大厅。
- 服务端同步只拉取当前页面所需的首屏游标，后续分页按需加载；增加请求合并和刷新竞态保护。

验收：已有快照在断网时仍可见；联网时页面先可操作，后台同步完成后再增量更新；同步失败有重试提示而不是长时间 loading。

### P1：群资源库无法区分加载、失败和空数据

证据：

- `miniprogram/pages/group-resource-library/index.js:297-340` 将三个请求的异常全部转为 `null`，随后把无响应结果转换为空数组并设置 `loading:false`。
- `miniprogram/pages/group-resource-library/index.wxml:69-95` 只根据 `displayGroups.length` 进入列表或空态，没有使用 `loading` 或浏览请求错误状态。
- `miniprogram/pages/group-resource-library/index.js:351-377` 刷新筛选时先把 `groups` 和 `displayGroups` 清空，再发起新请求。

影响：首次加载、服务端 500、超时、断网和“确实没有匹配群”都会显示为同一个空态。用户没有重试入口，也无法判断是自己筛选错了还是功能坏了；刷新期间旧数据也会瞬间消失。

建议：

- 为浏览、我的发布、积分状态分别保留 `loading/success/empty/error` 状态。
- 请求失败时保留上一次可用列表，展示“加载失败，重试”；筛选刷新时在新结果成功前不要清空旧结果。
- 为群资源首屏增加短 TTL 元数据缓存，并继续保留现有游标分页和请求序号保护。

验收：分别模拟空数组、500、超时和有旧缓存四种情况，页面文案、列表保留和重试动作必须不同。

### P1：旧商机页面把示例数据当真实数据展示

证据：

- `miniprogram/pages/opportunity-market/index.js:5-32,94-160` 在初始状态、接口空数组和接口异常时使用 `mockCards`；`index.wxml:45-80` 没有展示 `usingMock` 标识。
- `miniprogram/pages/opportunity-radar/index.js:139-170` 在空结果和异常时使用逼真的推荐商机；对应页面没有明确的示例数据视觉标识。
- `miniprogram/pages/opportunity-saved/index.js:85-135` 在保存列表为空或请求失败时使用 `mockSavedCards`；示例卡仍会进入正常列表渲染。
- `miniprogram/pages/opportunity-detail/index.js:65-87` 默认使用 `mockLead`，没有参数时甚至默认进入 `opp_demo_1`；详情页展示的是类似真实商机的内容。
- 这些旧页面仍登记在 `miniprogram/app.json`，当前正式商机入口虽已改为新页面，但不能把“可能是旧入口”当成安全边界。

影响：接口故障或真实数据为空时，用户会把演示内容误认为真实商机；对示例卡的保存、分享或生成回应包还可能产生“操作成功”的错误反馈。这是产品信任问题，也会污染后续人工验收。

建议：

- 生产构建移除旧页面的 mock fallback；若开发环境必须保留，页面顶部必须显示不可忽略的“示例数据，仅用于演示”，并禁止保存、分享、解锁和生成业务结果。
- 空数据统一展示真实空态；请求失败展示错误态和重试，不用示例数据掩盖故障。
- 重新检查旧页面是否仍被任何入口、分享路径或历史数据打开；若保留兼容路由，至少执行同样的真实数据边界。

验收：让接口返回空数组、500、超时和正常数据，四种情况下都不能出现未标识的真实感示例商机；示例 ID 的写操作必须被硬阻断。

### P1（规模增长风险）：多个核心列表没有服务端分页或仍全量扫描

证据：

- `backend/app/api/routes_notes.py:35-60` 的资料列表没有 `limit/offset/cursor`。
- `backend/app/api/routes_opportunities.py:28-75` 的旧商机和保存列表没有分页；`319-338` 的供需公开列表也没有分页。
- `backend/app/api/routes_orders.py:19-26` 的订单列表没有分页；`backend/app/services/app_service.py:16402-16425` 会构造匹配用户的全部订单后再计算汇总。
- `backend/app/services/app_service.py:648-704` 会先加载并筛选全部商机，再截取用户结果最多 12 条；`1048-1061` 会返回全部匹配供需卡。

影响：当前数据量小的时候不一定能复现，但用户、商机、订单或供需卡增长后，响应体、JSON 解析、内存和首屏渲染成本线性上升；服务端还会重复扫描和计算，容易把“偶发慢”误判成网络问题。

建议：

- 先为仍在正式导航链路中的列表补齐服务端分页，并让数据库查询在分页前完成筛选、排序和字段投影。
- 订单汇总改为服务端聚合或轻量摘要接口，列表按游标加载。
- 旧页面若不再使用，应移除入口或明确标记为兼容页面，避免继续维护两套全量列表协议。

验收：用 1,000/10,000 条种子数据测量响应字节数、服务端耗时、客户端解析耗时和首屏可见时间；目标页面首屏不应随总数据量线性等待。

## 4. P2 体验和维护风险

### P2：部分页面首屏把“暂无内容”当作默认渲染

`miniprogram/pages/notes/index.wxml:328-331` 没有使用页面已有的 `loading` 状态，冷启动请求尚未完成时就可能显示“暂无笔记”。旧商机市场、雷达、收藏、详情和回应包页面也存在初始 mock/空对象直接渲染、错误态不完整的问题。

这类问题单独看不一定阻断功能，但会让用户在网络波动时做出错误判断。建议统一抽取页面状态模型，不再让 WXML 通过“数组是否为空”猜测请求状态。

### P2：首页全量刷新仍等待待认领导入的媒体归一化

`miniprogram/pages/home/index.js` 虽然会优先绘制缓存卡片，但完整刷新把 `fetchPendingImports()` 放在主 `Promise.all` 中；`miniprogram/services/api.js:353-365` 对每个待认领项等待卡片和笔记媒体归一化。待认领导入属于次要提醒，不应拖住首页其余刷新链路。

建议把待认领数量/轻量元数据和媒体准备拆开，导入详情在用户点击后再补齐媒体。

### P2：共享组件仍可能保留偏小的辅助文字

页面级字号升级不能穿透自定义组件的样式隔离。当前组件中仍有 20–22rpx 的消息、沟通、选择卡、接龙列表等辅助文字。它们不一定都应放大，但在真实系统字体下可能继续造成“整体偏小”的感受。

建议按组件语义单独验收，不做全局机械替换；优先检查核心操作上下文中的说明文字和状态标签。

### P2：环境默认值和开发文档存在漂移

本地 `backend/.env` 是开发/模拟配置，`backend/app/core/config.py` 也保留开发环境、mock 存储和 mock 登录默认值；`backend/README.md` 与 `miniprogram/README.md` 仍有旧 MVP/mock 叙述。生产服务器实际配置本轮未读取、未修改、未部署，因此不能断言线上错误，但这属于部署前风险：环境变量缺失时可能意外启用不应进入生产的能力。

建议把生产启动检查做成部署前门禁：明确 `APP_ENV`、存储、登录、企微和数据库配置，并在 CI/发布脚本中拒绝 mock 登录、mock 存储和开发数据模式。

## 5. 对抗式场景检查

| 场景 | 预期不变量 | 本轮结论 |
| --- | --- | --- |
| 冷启动打开含多张大图的公开资料 | 标题、正文和主操作先可见；图片失败不吞掉正文 | 代码路径不满足，首屏被媒体缓存等待 |
| 互助大厅存在旧本地任务或 20 页服务端任务 | 先展示快照，后台同步；同步不能决定首屏是否出现 | 代码路径不满足，先同步后渲染 |
| 群资源接口 500/超时 | 明确失败并可重试，不能伪装成空列表 | 代码路径不满足，失败被转为空态 |
| 商机接口返回空数组/500 | 真实空态或错误态；不能无标识展示样例 | 旧商机页面不满足；正式新入口需人工确认 |
| 用户快速切换筛选或触底加载 | 新请求结果不能被旧响应覆盖 | 群资源、正式商机等已有请求序号/游标保护；旧页面仍需人工回归 |
| 大量订单、资料、商机、供需卡 | 首屏和响应体不随总数据量线性膨胀 | 多个旧/兼容接口仍全量返回或全量扫描 |
| 分享图缺失、过期、生成失败 | 不发送错误旧图，不回退到错误页面 | 现有分享插件静态门禁已通过；微信开发者工具仍需验证最终回调 |
| 联系方式、积分、完成状态 | 服务端事实优先，不被本地演示数据替代 | 既有相关回归通过；本轮未发现新增越权证据 |

## 7. 建议执行顺序

1. 先处理旧商机页面的 mock fallback 和失败/空态边界，消除“假数据像真数据”的信任风险。
2. 再拆分公开资料详情媒体缓存、互助大厅服务端同步和首页待认领导入的首屏阻塞链路。
3. 统一群资源、资料和旧业务页面的加载/成功空态/失败/重试状态模型。
4. 为正式导航中的订单、资料、供需和旧商机兼容接口补分页与服务端摘要，再用大数据量压测。
5. 最后在微信开发者工具清缓存，按冷启动、返回缓存、弱网失败、不同设备和原生分享回调做人工验收。
