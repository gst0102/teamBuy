# 商机合作对抗式审查报告

## 审查结论

代码层面未发现阻断发布的已确认 P0 缺陷；已修复一处会导致联系方式越权暴露的 P0 风险。小程序真机视觉、生产会话和真实积分流水仍需人工验收，不能仅凭静态检查视为最终上线通过。

## 审查对象与攻击问题

### 1. 身份伪造与联系方式越权 —— 已修复，P0

原实现允许详情接口直接信任查询参数 `viewerUserId`。攻击者可以把名片所有者 ID 放入参数，接口就可能返回完整联系方式。

修复后，生产环境的列表和详情接口可以匿名访问，但可选查看者身份只取自后端已验证的 Authorization 会话；前端传入的 `viewerUserId` 在生产环境不再决定所有权。解锁 POST 同样使用验证后的会话身份，并拒绝请求体冒充其他用户。

### 2. 列表和详情泄露敏感信息 —— 已覆盖

列表和未解锁详情只返回展示身份、行业、能力标签、合作意向和联系方式数量，不返回手机号、微信号、邮箱或二维码地址。联系方式只在服务端完成扣分/幂等判断后返回。

### 3. 积分绕过与重复扣分 —— 已覆盖

扣分由服务端资源钱包完成，前端积分只用于展示。消费记录使用动作、目标类型和目标 ID作为幂等边界，并保留 24 小时有效期；余额不足返回 402，不创建联系方式解锁结果；名片所有者查看自己的名片不扣分。

### 4. 动态合作过期 —— 已修复，P1

过期或非法有效期的合作意向不再进入“找合作”列表，详情页也不显示“正在发生”。编辑页保存时根据长期、7 天、30 天有效生成过期时间。

### 5. 发布数据质量 —— 已覆盖

商机合作开启时，服务端发布校验行业和至少一项“我能提供”；服务能力最多 6 项，行业标签最多 8 项。关闭商机合作时不强制补行业，避免关闭功能后仍被表单卡住。

## 残余风险与最小后续动作

- 当前列表服务会扫描用户资料后在内存中筛选，适合当前 MVP；数据量增长后应增加按卡片类型、发布状态、行业和更新时间的服务端索引/分页查询。
- 目前没有微信开发者工具编译产物和真机截图，必须人工确认高保真布局、懒加载表现和授权失败反馈。
- 直接分享的客户页仍属于原有公开分享链路；商机合作的 1 积分门槛只作用于商机市场详情页联系方式解锁。这是有意的产品边界，但上线前应由负责人确认两种入口的预期一致。
- 完整测试集的 Postgres 健康检查仍受本地 JSON 测试环境影响；不应通过修改业务代码掩盖该环境差异。
