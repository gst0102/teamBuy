# 资料发客户：对抗式审查与修复报告

日期：2026-08-14

## 结论

本轮确认一个 P0 根因并修复：导入资料保存后仍是 `status=draft`，发布接口只接受 `active`，因此点击发布稳定报错。修复后后端回归通过，前端五类入口完成静态链路审查。未部署、未上传体验版，最终真机验收仍由用户完成。

## 第一性原理

- 事实：保存内容、允许客户读取、触发微信原生分享是三个不同动作。
- 约束：客户只能打开 `shareState=published` 的资料；微信 `open-type=share` 不能等待一次异步发布请求。
- 推导：不能把 `private` 误判为“完善”，也不能在分享回调里偷偷竞态发布；保存必须先完成生命周期推进，发布必须通过公开安全门禁。

## 已修复

1. `update_user_note` 和统一内容编辑门禁：拥有者实际编辑遗留 draft 后推进到 `active`，仍保持 private。
2. `publish_user_note`：已有完整内容的遗留 draft 不再因陈旧 status 被直接拒绝，仍执行公开安全检查。
3. 资料列表：投影 `sourceNoteStatus` 供诊断，完成度只要求真实标题且至少有正文或封面；不再用 `status=draft` 或 `cardState=draft` 误伤已保存的文章/链接。
4. UI：五类编辑器与资料卡统一使用“发客户”；内部“发布”不再作为用户可见文案。
5. 分享：待分享 canvas 必须与当前卡片 ID 匹配，快速切卡不会串封面；生成图、原封面、默认图继续三级兜底。

## 五类入口攻击矩阵

| 类型 | 保存 | 公开门禁 | 分享入口 | 主要失败保护 |
| --- | --- | --- | --- | --- |
| 普通资料 | `note-edit` | title + body/cover + safe check | 资料卡“发客户” | 空白/系统占位仍为“完善” |
| 微信文章/链接 | `link-editor` | HTTPS + safe check | 资料卡“发客户” | 解析失败仍保留原 URL，不空图 |
| 房源 | `property-editor` | 结构化公开字段 + safe check | 资料卡“发客户” | 私密电话/上游信息不进公开投影 |
| 商品 | `product-editor` | 商品公开字段 + safe check | 资料卡“发客户” | 价格/规格缺失时不允许完成度通过 |
| 服务/名片 | 独立 studio | 各自公开投影 + safe check | 资料卡“发客户” | 旧模板字段不作为新入口依赖 |
