# 销售型 SCRM 五阶段对抗式审查与修复报告

日期：2026-08-12

## 结论

自动化范围通过；没有剩余已确认 P0 代码缺陷。真实微信支付、真机视觉与交互、法务和提现运营流程仍需上线前人工验收，本轮未部署。

## 攻击面与已修复问题

1. **旧接口绕过付费墙（P0）**：旧业务看板、线索列表/详情、客户动作明细、合集访客分析会暴露客户信息。已在后端统一校验会员；免费合集列表只返回汇总，不返回访客和事件明细。
2. **生成同款复制私密正文（P0）**：旧复制逻辑直接使用原始 note 正文。已改为从公开净化快照复制，补测手机号、内部备注、客户统计和上游信息不进入新资料。
3. **长链循环邀请（P0）**：原规则只拦截 A↔B 两节点循环。已改为沿完整邀请祖先链检测，并补 A→B→C→A 测试。
4. **退款撞上提现申请（P0）**：已申请提现的奖励原来复用 `pending` 状态，退款可能留下金额不平的申请。新增 `reserved` 状态；退款会拒绝相关提现申请、撤销目标奖励并释放同申请中的其他奖励。
5. **生成同款归因丢失（P1）**：复制保存后重新加载状态会漏保存新关系。已明确合并关系，并让付款时重新读取关系写回订单归因。
6. **免费用户通过次级页面进入（P1）**：客户、线索、线索详情、资料客户动作、合集分析页补会员预检并跳会员页。
7. **静态 PostgreSQL schema 缺表（P1）**：动态仓储可建表，但 `schema.sql` 不完整。已补六张业务表及关键唯一索引。

## 未关闭风险

- 当前后端历史架构以请求参数中的用户 ID 表达登录身份，未建立统一 session/token。新付费链沿用了现有边界；生产商业化前应单列认证改造，不能把参数相等视为强认证。
- 微信真实支付、支付回调验签、自动续费、企业付款和提现审核不在本轮实现；测试确认接口仅允许非 production。
- 真机页面布局、按钮居中、分享卡观感、三步生成体验仍需开发者工具和真机人工验收。
- 50% 直推奖励涉及平台规则、税务与营销合规，上线前需法务确认。
