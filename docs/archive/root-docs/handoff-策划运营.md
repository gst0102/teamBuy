# 资料整理助手：阶段性交接归档

更新时间：2026-06-23 19:50
适用对象：新的 Codex 会话、开发 Codex、验收官、运营策划会话

## 1. 项目背景与目标

当前正式产品定位是 **资料整理助手**。

产品主链路是：

1. 用户主要依托企业微信客服 / 会话归档发起资料导入。
2. 后端通过企业微信 API、微信客服回调、会话内容存档等方式接收文字、微信笔记、链接、图片、视频、位置等素材。
3. 后端将素材归入当前用户资料库，形成可编辑的 `UserNote` / typed card。
4. 用户进入小程序进行二次编辑、审核、结构化和发布。
5. 用户把资料卡、电子名片、服务方案、房源页、团购页或资料包发给客户 / 群。
6. 客户打开、浏览、点击、留资、预约、接龙、留言等行为回流到客户看板。
7. 发布者第一时间看到“谁来了、看了什么、要不要跟进”，形成运营闭环。

当前最重要的商业判断：

- 产品不是单纯的笔记工具，也不是完整 CRM。
- 核心价值是“资料整理 + 展示分享 + 客户痕迹回流 + 跟进处理”。
- 用户已经明确：客户痕迹、待跟进、访客、谁看了什么，是后续付费的核心，不能只做成弱统计或藏在详情页。
- 第一个重点冷启动场景是房产中介：用户以中介身份发房源卡片，其他中介或客户看到后被吸引，再通过企业微信发资料体验自动生成。

长期架构以 `docs/stage2-docs/08-plugin-architecture.md` 为准：

- 稳定基座：企业微信通信、会话内容存档、用户身份、会话管理、合规、支付、笔记库和展示页基础能力。
- 可插拔 Skill：具体内容处理能力。
- 企业微信入口采用混合驱动：快捷指令 / 菜单点按优先，规则匹配其次，AI 意图识别兜底。
- AI 不直接写库、扣费、发通知或执行业务动作。

## 2. 当前阶段目标

当前阶段不是继续横向加功能，而是把第一阶段的信息架构和客户回流闭环做清楚。

阶段目标：

- 重构首页 / tabbar / 工作台模式，让用户进来知道自己当前是在“日常资料台、房源工作台、团购工作台、服务工作台”中的哪一个。
- 保留普通模式作为默认资料整理模式，避免普通用户一进来看到房产、团购、客户等业务入口而困惑。
- 房产 / 团购 / 服务等行业模式只展示当前模式最常用入口。
- 建立专题/合集中心的产品心智：不是文件夹，而是可分享、可复用、可转化的资料包。
- 重点收口房源首页四指标和客户看板：`房源 / 打开 / 访客 / 待跟进`。
- 首页先告诉用户“来客户了”，客户看板再展示具体人、来源、动作、联系方式和下一步处理。
- 小程序前端体验版上传仍由用户在微信开发者工具手动完成；Codex 默认负责代码、检查、后端部署和交接。

- 匿名或缺请求者身份返回 401。

## 7. 用户已经确认过的产品 / 技术决策

### 7.1 产品方向

- 产品名与核心定位：资料整理助手。
- 主入口依托企业微信进行资料导入和会话归档。
- 小程序负责二次编辑、审核、整理、展示和客户回流。
- 用户角色相对固定：房产中介、团长、服务行业或普通资料用户。
- 普通用户不应该默认看到客户、SCRM、看房、接龙等业务入口。
- 默认工作台是日常资料台，后续可切换房源、团购、服务。

### 7.2 功能边界

- 当前已有核心功能区：普通笔记、电子名片、团购、房产、服务方案。
- 不继续横向扩太多大功能。
- 第一阶段优先补支撑能力：专题 / 合集、客户线索 / 互动记录、分享数据看板、模板中心、会员权益、邀请奖励。
- 其中当前最关键是专题 / 合集和客户痕迹回流。

### 7.3 专题 / 合集

用户认可专题 / 合集中心。

已确认产品定义：

- 标签负责找资料。
- 专题负责组织事情。
- 合集负责对外分享。
- 专题合集不是传统文件夹，而是围绕目标把多条资料组合成可查看、可分享、可转化的资料包。

第一版重点：

- 普通资料合集。
- 房源推荐合集。
- 服务案例合集。
- 可分享资料包页面。
- 从资料卡一键加入专题。
- 专题内一键生成分享页。

### 7.4 首页 / 工作台

用户认可首页根据工作台模式展示不同内容。

已确认：

- 日常资料台：写笔记、保存图片、整理链接、建资料包。
- 房源工作台：新建房源、记需求、房源合集、我的名片。
- 团购工作台：新建商品、团购合集、查看接龙、发群文案。
- 服务工作台：做电子名片、做服务方案、案例合集、发给客户。
- 其他三个工作台也应保留写笔记 / 资料入库能力，不要只有业务功能。

### 7.5 工作台视觉

用户不满意顶部右侧只放一个大字“资 / 房 / 团 / 服”。

已确认视觉方向：

- 使用能表达场景的图形组合，而不是单字占位。
- 服务工作台示例：名片 + 服务方案纸 + 咨询气泡，主色青绿色。
- 房源、团购、资料台也应使用同一套视觉语言。
- 团购图片应偏水果类，更符合团购直觉。
- 小程序前端静态图片先用 240x240 WebP / PNG 级别资源，控制代码包大小。

### 7.6 客户看板 / SCRM 命名

用户认可：

- 首页不要叫 SCRM。
- 首页只告诉“来客户了”。
- 页面可以叫客户看板、待跟进、客户动态、咨询看板、接龙看板等。
- SCRM 是底层能力，不是前台第一语言。

### 7.7 房源首页四指标

已确认：

- 房源工作台首页四指标为 `房源 / 打开 / 访客 / 待跟进`。
- 第四项不要叫客户，改为待跟进。
- 四项都可点击并进入对应页面。
- 点击待跟进必须能看到具体记录，不允许“数字有，列表空”。

### 7.8 今日 / 累计口径

用户指出首页写“今日概览”时不能显示历史累计。

已确认：

- 首页可以同时支持今日和累计切换。
- 今日入口下钻后必须真的只展示今天的访客 / 动作。
- 用户点击今日访客，应能看到今天是谁来了、看了哪些、如何联系。

### 7.9 冷启动推广

用户有不少中介群资源。

用户认可的第一阶段推广切入口：

- 用户以中介身份先在群里发自己的房源卡片。
- 卡片里埋钩子，让其他中介好奇点开。
- 对方加企业微信后，发视频 / 发资料给企业微信。
- 系统帮对方生成房源推荐包或房源卡片。
- 第二阶段引入收费与利益分成，让推广者有收益，推广产品比单纯成交一单租房更有长期价值。

相关发散文档：

- `docs/stage2-docs/发散想法.md`

### 7.10 开发 / 验收协作

用户认可：

- 可以由 Codex 推进开发和验收，但最终上线仍由用户人工确认。
- 验收官可使用 `ai-qa-acceptance Skill`，也可以继续优化验收 Skill。
- 验收不能只跑一轮，应该开发、验收、修复、复测循环，直到验收官通过且 Codex 自测体验无明显问题。
- UI 美观度也必须验收，不能只看接口和功能。

## 8. 下一步建议执行顺序

建议不要再开新功能，按以下顺序做“核心体验打磨和验收”。

### 第一步：用户上传最新小程序体验版

后端已经部署，但前端最新代码需要用户用微信开发者工具上传体验版。

上传后重点真机看：

- 首页工作台是否是最新版本。
- 房源工作台是否有今日 / 累计。
- 点击待跟进是否进入客户看板且看到“高先生 / 预约看房 / 新世界广场B-938”。
- 资料库默认列表是否不再半屏。

### 第二步：房源客户看板真机复验

用真实房源链路复验：

1. 从企业微信发一条房源资料。
2. 小程序资料库确认生成房源。
3. 分享或打开房源客户页。
4. 产生浏览、预约、留资或咨询。
5. 回到首页看今日数字。
6. 点击今日待跟进 / 今日访客。
7. 确认能看到具体客户、房源、动作、联系方式或缺联系方式原因。

验收标准：

- 数字和列表一致。
- 今日和累计不会混。
- 客户动作不混入普通资料或服务资料。
- 用户能一眼知道下一步该联系谁。

### 第三步：客户看板 UI 精修

继续死抠客户看板，而不是加 CRM。

建议优先优化：

- 待跟进列表首屏。
- 每条客户记录显示：客户名、动作、来源房源、时间、电话 / 微信、下一步按钮。
- 无联系方式时显示原因，例如“已预约，未留电话”。
- 最近访客和待跟进要区分：访客是浏览事实，待跟进是要处理的人。
- 房源效果优先使用后端 `propertyBreakdown`。

### 第四步：权限回归

补 owner、非 owner、匿名三类身份验证：

- owner 能看自己的客户看板。
- 非 owner 不能看别人的客户看板。
- 匿名访客不能访问后台统计。
- 展示页公开访问不受后台看板权限影响。

### 第五步：专题 / 合集中心一期文档与实现

当前首页 / 客户回流收口后，再做专题 / 合集中心。

建议先做：

- 普通资料合集。
- 房源推荐合集。
- 服务案例合集。
- 资料卡加入合集。
- 合集可分享页面。

不要一开始做复杂专题模板市场。

### 第六步：冷启动运营实验

用房源卡片做第一轮冷启动。

建议实验：

- 用户自己作为中介发房源卡片到中介群。
- 观察点击、咨询、加企微、发资料转化。
- 给 3-5 个中介朋友手工生成示范房源推荐包。
- 整理最有效的一句话钩子和演示视频。
- 暂不急着规模化收费，先确认“别人看到后愿意发资料给企业微信让系统生成”。
