## 1. 项目背景与目标

`teamBuy / 资料整理助手` 当前已经从单纯资料整理工具，演进为更接近私域经营和成交辅助的小程序 + 后端系统。

当前最核心的业务闭环是：

1. 用户把房源、资料、图片、链接、名片等内容发给企业微信资料助手。
2. 后端通过企业微信会话内容存档或相关接入链路接收消息。
3. 系统把内容整理成资料、房源、合集或待识别内容。
4. 用户回到小程序里查看、编辑、分享、做合集、看反馈和后续跟进。

这一期聚焦的是把这个闭环里最容易卡住用户的部分补平：

- 首次添加企业微信资料助手怎么做。
- 首次绑定为什么不能串号。
- 同一个用户重复点击为什么不该总换绑定码。
- 批量房源文本为什么不能只入库一条。
- 小程序首页如何把绑定流程说清楚，不让用户迷路。

长期架构仍遵循：

- `AGENTS.md`
- `docs/stage2-docs/08-plugin-architecture.md`

核心原则仍然不变：

- 小程序 `openid` 是最终用户身份锚点。
- 企业微信 `external_userid` 只是来源映射。
- 企业微信客服、企业微信成员好友、会话内容存档、群机器人是不同链路，不能混着理解。
- 当前阶段优先把真实主链路跑顺，不追求一次把所有自动回复、群发、客服卡片都做满。

## 2. 当前阶段目标

第七期的阶段目标可以概括为三件事：

1. 把“添加资料助手”的首次绑定流程做顺。
2. 把企业微信导入里的高价值样本处理对，尤其是批量房源。
3. 给后续上线和新会话接手留下一份不会丢上下文的归档。

更具体地说，当前阶段已经明确的目标是：

- 首页点击“添加房源助手 / 加企业微信助手”后，用户能看懂下一步该做什么。
- 绑定流程采用“二维码 + 自动复制绑定话术 + 手动发送”。
- 同一用户在未绑定前重复点击时，绑定码要稳定，不要每次变化。
- 用户一旦已经绑定，就不再重复提示绑定。
- 批量挂牌房源文本需要自动拆成多条 `property_listing`，而不是只进一条普通资料。
- 后端生产环境要跟上这次绑定码复用逻辑。
- 小程序前端体验版仍需要用户手动上传，Codex 不代替微信开发者工具上传。

## 3. 已完成的功能

### 3.1 企业微信资料助手绑定码方案已落地

已完成：

- 后端新增并启用了 `POST /api/auth/wecom-bind-intent`。
- 小程序首页企业微信助手入口会创建绑定意图。
- 标准绑定话术格式为：`绑定资料助手 TB-XXXXXX`。
- 企业微信客服同步消息和会话归档消息都能识别绑定码。
- 绑定码消息只用于身份绑定，不生成资料卡片。
- 绑定成功后，后续同一 `external_userid` 发来的内容会自动归属到对应小程序用户。

### 3.2 绑定码复用与已绑定提示已完成

已完成：

- 同一小程序用户在未绑定状态下，如果绑定码仍在有效期内，重复点击会复用同一个绑定码。
- 不再出现“每点一次就换一个 TB-XXXXXX”的体验。
- 如果用户已经建立 `external_userid -> ownerUserId/openid` 绑定：
  - 后端返回 `status=bound`
  - 前端不再展示二维码与绑定话术
  - 前端只提示“资料助手已绑定，可以直接转发资料”

### 3.3 添加资料助手引导层已完成

## 6. 已知问题和风险

### 6.1 小程序前端还未完成本轮体验版上传验证

当前代码已就绪，但还没有得到“上传新版体验版后，真机完整走一遍绑定流程”的最终人工确认。

要重点验证：

- 点击“添加房源助手 / 加企业微信助手”是否看到真实二维码
- 绑定话术是否确实已复制
- 胶囊按钮是否在真机上不挤压、不变形
- 已绑定用户是否真的只提示“可直接转发资料”

### 6.2 测试环境 `mock-login` 被关闭

服务器测试环境目前对 `POST /api/auth/mock-login` 返回：

- `403 Forbidden`
- `{"detail":"测试登录已关闭"}`

这不是本轮代码 bug，但会影响用测试环境直接跑某些无 UI 的接口回归脚本。

### 6.3 企业微信链路仍然有边界，不能混用

当前仍需明确区分：

- 企业微信成员好友
- 微信客服会话
- 会话内容存档
- 群机器人
- 客户群发

本轮已经明确：

- 当前“添加资料助手”主路径是企业微信成员好友 / 会话归档
- 不是 `wx.openCustomerServiceChat`
- 不是自动代用户发消息

如果后续新会话不了解这个边界，很容易又把首页入口改回微信客服链路。

### 6.4 批量房源规则还会继续生长

虽然当前真实样本已经能拆出 7 条，但这类文本规则仍然会持续迭代。

后续仍可能遇到：

- 更口语化的房源写法
- 多个电话号码
- 更复杂的门牌号
- 房源与普通资料混写

所以未来必须继续走：

- 真实失败样本
- 补测试
- 补规则
- 回归导入链路

### 6.5 还有一些能力是“已设计/已研究”，不是“已完成”

不要把以下能力误判为已经完全上线：

- 群机器人运营卡片生成器
- 企业微信官方群自动加群配置闭环
- 小程序官方加入群聊 `config_id/plugid` 主链路
- 自动化日报/运营群内容生产闭环
- 支付、分销、推广能力

这些都还在后续阶段，不应编造成“已完成”。

## 7. 用户已经确认过的产品/技术决策

以下决策已经被用户明确确认，后续新会话默认应遵循：

- 产品正式名称是“资料整理助手”。
- 当前主链路是“企业微信成员好友 + 会话内容存档收消息”，不是微信客服主入口。
- 小程序不能代用户自动发送绑定码消息。
- 添加资料助手首版采用：
  - 真实二维码
  - 自动复制绑定话术
  - 用户手动在企业微信聊天框粘贴发送
- 绑定码不应该每次点击都变化。
- 已绑定用户不应该再提示绑定。
- 同一个用户重复点击时，未绑定状态下应复用同一个有效绑定码。
- 会话归档导入遇到批量挂牌文本时，不能只生成一条普通资料，应该拆成多条房源。
- 电话、微信、中介费等上游信息默认进入私密数据，不公开给客户卡片。
- 小程序上传体验版和提交审核，默认由用户在微信开发者工具手动完成。
- 当前接近上线，优先把真实链路跑顺，不做无边界扩散式重构。

## 8. 下一步建议执行顺序

建议新会话按下面顺序继续，不要跳着做。

1. 先让用户上传最新小程序体验版，真机验证“添加资料助手”流程。
2. 真机验证两个场景：
   - 未绑定用户：是否看到二维码、复制绑定话术、发送后绑定成功
   - 已绑定用户：是否只提示“已绑定，可直接转发资料”
3. 再验证真实企业微信资料导入：
   - 绑定成功后发一条普通资料
   - 绑定成功后发一条批量房源清单
   - 检查资料是否正确归属到当前小程序账号
4. 如果真机流程通过，再进入运营内容和群机器人卡片生成器的下一阶段设计与开发。
5. 如果真机流程不通过，优先修主链路，不要同时开新功能线。
