# “我的工具 · 互帮互助”架构与页面方案 V1

**状态：架构基线；前端本地演示已开始按此实现，后端与真机验收仍未完成。**
**产品：资料整理助手**
**更新时间：2026-08-31**

## 1. 这次收敛后的核心结论

互帮互助只使用一种积分：`mutualPoints`（互助积分）。不新增信誉分、热度分、等级分或其他排序分。

同一积分在四个地方使用：

1. 用户账户余额：首次进入互帮互助时赠送 100 分。
2. 任务结算的消耗：发布者在每笔有效完成结算时消耗积分。
3. 完成任务的获得：执行者通过有效完成任务获得积分。
4. 首页排序：默认按发布者当前互助积分从高到低；用户可以切换为执行者可获得的赏金积分从高到低。

这里的“发布者积分”就是发布者当前可用的 `mutualPoints` 余额，不另造一套“信誉分”。它是首页业务排序依据，不代表平台对任务质量的保证；任务拒绝、冻结和处罚由任务状态规则负责。

## 2. MVP 页面结构

入口放在小程序“我的”页，名称为“我的工具”，进入后第一项为“互帮互助”。互帮互助是“我的工具”下的一个子模块，不占用小程序全局底部 TabBar；第一期只保留四个页面内顶部 Tab：

| 页面 | 主要职责 | MVP 必须有的内容 |
| --- | --- | --- |
| 互帮互助首页 | 浏览和领取/查看任务 | 小程序任务 / 羊毛 / 普通任务、积分排序、赏金排序、任务卡片 |
| 任务详情与提交 | 查看规则、跳转、查看或提交 | 按类型显示任务说明、验收/查看规则、入口、完成或打赏动作 |
| 发布任务 | 发布三种任务 | 小程序任务、羊毛福利、普通任务，以及各自的入口和积分规则 |
| 我的工具 | 查看积分和个人任务 | 当前积分、收入/支出、我发布的、我领取的、充值、提现 |

顶部 Tab 固定为：`首页` / `发布` / `任务` / `我的`。任务详情和提交页仍归属“任务” Tab；发布页内部采用类型切换：`小程序任务` / `羊毛` / `普通任务`。不把三套发布流程拆成三个入口，避免第一期功能显得复杂。

## 3. 三种任务规则

### 3.1 小程序任务

发布者填写：

- 任务标题
- 小程序 `shortLink`
- 可选封面图
- 每次有效完成消耗积分：默认 5 分，第一期固定为 5 分
- 任务数量
- 可选说明

用户点击任务后，由小程序主动调用 `wx.navigateToMiniProgram` 打开目标小程序。你提供的 `shortLink` 形式作为本项目的输入契约保留；创建任务时保存原值并做基本格式校验，点击时直接传给跳转 API。目标小程序权限、微信版本和真机行为仍需要实际验收。[微信小程序跳转说明](https://intl.cloud.tencent.com/zh/document/product/1219/68015)

页面不把目标小程序嵌入当前页面，而是将该任务渲染成卡片式入口：目标名称/任务标题、进入说明和箭头组成可点击卡片，点击卡片后调用 `wx.navigateToMiniProgram({ shortLink })`，返回资料整理助手后再完成任务。这里的卡片是本小程序自己的 UI，不等于微信系统生成的目标小程序分享卡片；如果要把任务转发给好友，分享的是本项目的任务详情页，不能由本项目伪造另一个小程序的原生分享卡片。跳转能力必须在真实微信设备上验收，模拟器不能替代真机结果。

发布完成后的推荐分享链路为：发布成功 → 进入刚创建的任务详情 → 点击“分享给好友” → 好友打开资料整理助手任务详情 → 阅读任务说明和验收标准 → 点击目标小程序卡片 → 返回后提交完成。任务大厅已有的任务卡只承担发现和进入详情，不重复承担目标小程序跳转。第一期本地演示可以先返回任务详情路径；正式跨用户版本必须由服务端按 `taskId` 或可撤销分享 token 返回公开任务数据，不能依赖发布者本地缓存，也不能在未知 ID 时回退到其他任务。

返回资料整理助手后进入一个简单的完成页：

- 默认显示“已返回，可以提交完成”。
- 反馈文字可填可不填。
- 反馈图片可传可不传。
- 满足有效停留条件后，用户点击“完成任务”。

积分结算：

- 发布者每次有效完成结算时消耗 5 分，不在发布时预冻结。
- 执行者每次获得 4 分，即发布者消耗积分的 0.8 倍。
- 剩余 1 分作为平台运营余额，不展示为另一种用户积分。
- 同一用户、同一任务、同一批次只能结算一次。
- 发布者积分不足以支付下一笔时，任务自动变为“已暂停/已下架”，不能继续点击或完成；积分余额不能扣成负数。对于 5 分任务，余额小于 5 分时就停止下一笔，而不是等到产生负数。

“超过 3 秒”只作为第一期的有效完成条件之一，不能只相信前端传来的一个秒数。服务端需要校验任务会话 nonce、进入时间、返回时间、领取关系和幂等键；这属于后续开发验收重点。

### 3.2 普通任务

普通任务用于问卷反馈、图片标注、文本校对、页面测试、资料整理、商品信息核对等人工任务。第一期不做复杂问卷编排，只保留一张清晰的任务说明表单。

### 3.3 羊毛任务

羊毛是福利/信息入口，不是需要交付材料的任务。发布者填写标题、羊毛分类、羊毛说明和可选入口；说明内容可以用文字、图片或图文混排表达，重点写清福利内容、领取/使用步骤、有效期和注意事项。

- 查看方式可以是免费查看，或一次性支付指定互助积分后查看完整内容；同一用户、同一任务只收费一次。
- 羊毛不填写验收标准，不生成提交材料，不进入发布者验收，也不适用 5 天自动通过。
- 羊毛没有固定完成奖励；若发布者开启打赏，查看者使用后可以自愿打赏发布者。
- 羊毛的可选次数表示可领取/解锁名额，正式版必须在服务端按成功查看动作原子扣减，不能借用普通任务的提交次数语义。
- 羊毛允许评论和举报；付费解锁后若入口或内容明显失效，可以申请退还解锁费，由 PC 端审核。

### 3.3 任务详情按角色拆分

任务详情不再让发布者和执行者共用同一套操作区。角色页面的完整设计见：

`docs/stage2-docs/45-mutual-help-task-role-pages-v2.md`

- 执行者任务详情：任务标题、奖励或查看费用、剩余次数、任务说明；普通任务显示验收标准和提交材料，小程序任务显示目标入口和完成动作，羊毛显示福利入口和可选打赏；分享链接默认进入此页。
- 发布者任务管理：任务状态、完成/查看进度、普通任务待验收提交、通过结算、补交/拒绝、分享和暂停发布；发布者从“我的”进入此页。
- 两个页面共享 `MutualTask`，但服务端必须依据当前登录用户返回 `viewerRole` 并校验权限，不能只由前端判断 `ownerUserId`。
- 好友分享卡不使用详情页默认长截图；正式上线前生成独立的固定比例任务分享图，`path` 指向执行者详情页，目标小程序的原生卡片仍不能由本项目伪造。

任务类型不依赖标题判断：顶部的 `小程序任务 / 羊毛 / 普通任务` 切换就是必填的 `taskKind` 字段；羊毛和普通任务分别使用对应的轻量分类选择。

任务内容支持文字、图片或图文混合，不要求发布者只能打字。普通任务的验收标准也支持文字、图片或图文混合；羊毛没有验收标准，图片用于展示福利截图、领取步骤和注意事项。文字与图片按发布顺序保存和展示。

发布者填写：

- 任务标题（必填）
- 任务分类（必填）：普通任务使用页面功能体验 / 问卷反馈 / 图片视频标注 / 文本校对 / 资料整理 / 商品信息核对 / 人工调研 / 其他；羊毛使用优惠券折扣 / 活动抽奖 / 返利免单 / 免费资源 / 工具网站 / 试用体验 / 其他
- 任务内容/羊毛说明（必填，支持文字 / 图片 / 图文混合）
- 操作步骤（可选；羊毛建议直接写进说明内容）
- 验收标准（仅普通任务必填，支持文字 / 图片 / 图文混合）：完成后按什么条件判定通过
- 示例结果图片或流程图（可选；普通任务可放入验收标准，羊毛可放入说明）
- 提交材料类型（仅普通任务）：文字 / 图片 / 两者均可
- 任务次数（可选）：普通任务表示成功完成上限；羊毛表示可领取/解锁名额
- 截止时间（可选）
- 发布者奖励积分，最低 5 分
- 违规说明（可选）

普通任务执行者按照验收标准提交文字、图片或其他约定材料；小程序任务返回后点击完成并可选提交反馈；羊毛查看说明后直接使用福利，不提交材料。反馈文字不默认强制填写；只有发布者明确将“文字反馈”设为交付材料时，才变为必填。

发布内容的数据结构采用有序内容块，而不是把图片压成 Base64 塞进文本字段：

```text
taskContentBlocks: [{ type: "text", text }, { type: "image", mediaAssetId }]
acceptanceCriteriaBlocks: [{ type: "text", text }, { type: "image", mediaAssetId }]
```

两个字段都至少要有一个有效内容块；因此“只发一张任务说明图”或“只发一张验收流程图”也是合法的。图片上传必须走现有媒体资产登记、哈希去重、访问控制和失败兜底链路。第一期不做富文本编辑器，先提供有序内容段编辑：可依次添加文字段或图片段、编辑文字段、删除内容段，并在发布后按原顺序展示。需要流程感时由发布者在文字段内写“步骤1、步骤2”，不强制把每个任务拆成固定步骤。

内容图片展示必须保持原始宽高比，不使用会裁切主体的 `aspectFill`。详情页点击图片进入微信原生预览，支持放大、左右滑动查看同一任务的全部内容图片；图片下提供“保存到相册”，远程图片先下载到本地再保存，并在未授权时引导用户打开相册权限。

普通任务的积分规则：

- 发布者填写的奖励积分是消耗基数，最低 5 分。
- 执行者验收通过后获得 `floor(rewardPoints × 0.8)` 分。
- 默认奖励 5 分时，执行者获得 4 分。
- 发布任务时不冻结积分；每次验收结算时检查发布者当前余额。
- 发布者余额不足以支付下一笔时，任务自动暂停/下架，不能继续点击“完成”；余额不允许变成负数。

任务次数规则：

- 任务次数为空时，表示不设置数量上限，直到发布者主动暂停、任务过期或积分不足。
- 任务次数填写 3、5 等数字时，表示最多成功验收 3、5 份，不是领取次数，也不是提交次数。
- 服务端以成功验收结算的数量为准，并用原子条件更新防止并发超额。
- 达到任务次数后，任务状态变为“已完成/已下架”；首页不再显示“去完成”，详情页的完成按钮置灰，服务端同时拒绝后续完成请求。
- 首页卡片显示“剩余 3 份”等剩余次数；未设置次数时显示“次数不限”。

## 4. 首页排序与卡片展示

首页默认排序严格使用：

```text
publisherMutualPoints DESC
```

用户可以切换：

```text
rewardPoints DESC
```

其中 `rewardPoints` 指执行者最终可获得的单份积分，不是发布者的总预算。默认排序的同分规则为：

1. 发布时间倒序；
2. 任务剩余数量倒序；
3. 任务 ID 倒序，保证分页稳定。

排序必须在服务端完成，前端只传 `sort=publisher_points_desc` 或 `sort=reward_points_desc`，避免分页后排序错误。

首页视觉上保留参考图的卡片流，但改为更清楚的任务信息：

- 顶部第一层：`首页` / `发布` / `任务` / `我的` 四个 Tab，当前 Tab 使用橙色文字和短下划线表示。
- 首页内容层：`小程序任务 / 羊毛 / 普通任务` 类型切换。
- 首页内容层右侧：`积分优先`、`赏金最高` 排序切换。
- 卡片左上：任务类型标签。
- 卡片中部：标题、简要说明、发布者积分。
- 卡片右上：`+4 分` 等执行者可获得的奖励，确保用户扫卡片时第一眼能看到收益。
- 卡片底部：剩余数量、`去完成`。
- 羊毛卡片右上显示“免费查看”或“查看 N 分”，不显示固定完成奖励。
- 不使用“评鉴 100%”等容易让人误解为平台质量保证的文案。

## 5. 领取、提交、验收

### 小程序任务

```text
浏览任务 → 点击去体验 → navigateToMiniProgram
       → 返回资料整理助手 → 可选填写反馈 → 点击完成
       → 服务端校验 → 发布者扣 5 分，执行者得 4 分
```

### 普通任务

```text
浏览任务 → 领取 → 按验收标准完成
       → 上传文字/图片材料 → 发布者验收
       → 通过：执行者得 0.8 倍积分
       → 退回：填写理由，可补交或申诉
```

### 羊毛任务

```text
浏览任务 → 查看摘要和评论
       → 免费查看，或确认支付一次解锁费
       → 查看福利说明和使用入口 → 可选打赏/评论
```

羊毛不产生提交记录，不进入发布者验收，也不适用 5 天自动通过。

普通任务详情页必须显示“验收标准”，不能只显示一个标题和一个大按钮；羊毛详情页显示“查看/使用规则”，不伪造验收标准。提交页只出现本任务要求的材料类型，避免把所有复杂字段一次性展示给执行者。

## 6. 连续拒绝与积分返还

同意设置“连续拒绝三个不同执行者后降级发布者并返还执行者积分”，但触发条件需要定义清楚：

- 必须是三个不同执行者；
- 三次提交均已完成领取流程，且不是主动取消或明显缺少必填材料；
- 每次拒绝都必须填写理由；
- 第三次拒绝后，任务立即暂停接单，发布者进入降级/复核状态。

积分处理顺序：

1. 不在发布时预冻结积分；每次验收/拒绝都记录对应提交和积分流水。
2. 触发连续三次拒绝时，先从发布者当前可用积分中返还被拒执行者应得积分；发布者余额不足时不能扣成负数，立即暂停其任务和提现，进入待补处理。
3. 发布者扣除对应惩罚积分；补足积分后才能恢复相关结算和发布能力。
4. 如果发布者申诉并证明拒绝符合验收标准，可以恢复任务；如果确认恶意拒绝，保留降级结果并继续限制发布。

这不是新增信誉分，而是任务状态、积分流水和发布资格状态的组合规则。首页排序仍只读取 `mutualPoints`。

## 7. 我的工具与 PC 配置

小程序“我的工具”首屏展示：

- 当前互助积分
- 可提现积分
- 待验收积分
- 我发布的任务
- 我领取的任务
- 积分明细

积分明细统一记录每一笔来源和去向：初始赠送、完成小程序任务、普通任务验收、结算、返还、处罚、充值、提现。

提现规则第一期按可配置参数实现：

- 最低提现余额：100 分；
- 余额 300 分时，最多可提现 200 分；
- 手续费率：前期 PC 默认配置为 0%；
- 真实提现审核、手续费和到账方式由 PC 运营端配置；
- 审核中的充值/提现入口可以不在小程序审核首屏展示，但服务端不能依赖“隐藏入口”代替权限和状态控制。

PC 配置项：

```text
initial_mutual_points = 100
miniapp_publisher_cost = 5
miniapp_executor_ratio = 0.8
ordinary_task_min_reward = 5
withdraw_min_balance = 100
withdraw_max_reserve_points = 100
withdraw_fee_rate = 0
```

## 8. 最小数据对象

第一期建议使用独立互帮互助业务对象，不修改现有资料卡结构：

- `MutualAccount`：用户当前可用积分余额；
- `MutualPointLedger`：不可变积分流水；
- `MutualTask`：任务类型、标题、分类、图文任务内容、图文验收标准、链接、奖励和数量；
- `MutualClaim`：执行者领取关系、任务会话和状态；
- `MutualSubmission`：提交材料、反馈、验收结果和拒绝理由；
- `MutualDispute`：补交、申诉、连续拒绝复核记录；
- `MutualWithdrawal`：提现申请、手续费、审核和到账状态。

所有积分变化必须通过积分流水完成，不能由小程序直接修改余额。余额是流水的可校验投影；扣分、返还和发放都需要幂等键。

## 9. 风险边界

- 不能把未知状态直接结算成成功；跳转返回、任务提交和发布者验收都要有明确状态。
- 不能让积分余额被扣成负数；余额不足时暂停/下架需要继续消耗积分的任务和操作。
- 小程序任务必须把“卡片点击 → 目标小程序 → 返回 → 完成任务”作为一个可追踪流程；不能把页面上展示了卡片误认为目标小程序已经打开。
- 发布者不能无理由连续拒绝；拒绝理由、补交和申诉必须可追溯。
- 普通任务不收集短信验证码、支付密码或与任务无关的账号凭证。
- 上传图片必须复用现有媒体资产登记与去重链路，不在业务表中保存 Base64；内容图片和验收图片都要保留块顺序以及发布者可见权限。
- 参考图只作为页面结构和视觉方向，不直接复制“砍价、刷量、诱导分享”等业务文案。
- 小程序前端仍按现有项目规则使用 `rpx`、安全区和统一按钮居中基线；首页列表不等待非首屏媒体下载。

## 11. 第一性原理补充与优化

### 11.1 先定义必须成立的闭环

这个功能成立的最小条件不是“页面多”，而是下面五件事同时成立；其中普通任务需要交付闭环，羊毛需要查看/使用闭环：

```text
用户能找到任务 → 用户知道要做什么或要查看什么 → 用户完成提交或查看使用
→ 普通任务能按规则验收 → 双方积分都能准确结算
```

因此第一期的每个页面都只服务这条链路：

- 首页解决“找任务”和“比较积分”；
- 详情页解决“看懂规则”和“开始任务”；
- 提交页解决“按标准交付”；
- 发布页解决“把任务说清楚并配置奖励”；
- 我的页解决“确认积分和任务状态”。

### 11.2 必须补充的最小规则

- 任务发布不冻结积分；每次完成结算时检查余额，余额不足就暂停/下架任务，不能扣成负数。
- 每个领取记录要有唯一任务会话和幂等键，防止重复完成、重复发分。
- 发布者在规定时间内不处理提交时，任务需要自动验收或进入平台待处理队列，不能让执行者无限期等待。
- 拒绝必须带理由；执行者至少有一次补交或申诉入口，但不把正常任务流程做成复杂仲裁。
- 任务过期、取消、暂停、已满额都要有明确状态和用户可见文案。
- 余额、任务暂停、提交待验收是同一积分体系下的业务状态，不是三套积分；第一期不预冻结发布者积分。

### 11.3 排序规则的边界

按发布者当前互助积分排序是既定产品规则；但它只能回答“这个发布者当前有多少可用积分”，不能回答“这个任务一定可靠”。因此页面不需要新增信誉分；普通任务详情必须完整展示验收标准，羊毛详情必须完整展示查看/使用规则，让用户自己判断是否参与。

### 11.4 视觉和交互优化

- “+4 分”放在任务卡片右上角，和类型标签形成对角信息层级；标题区域保持干净。
- 四个功能 Tab 放在互帮互助页面顶部，避免与小程序全局底部 TabBar 产生层级冲突。
- 首页只保留一个主动作“去完成”；排序和类型切换使用次级控件。
- 普通任务提交页只渲染本任务需要的材料类型；反馈文字和图片默认可选，不让用户面对空洞的大表单。
- 充值、提现和手续费配置属于“我的工具”的次级区域，首屏先展示余额和任务状态。

## 12. 任务类型与验收标准字段结论

### 12.1 结论

需要任务类型，但不需要再增加一个和顶部切换重复的输入框：

- `taskKind` 是必填结构字段，由发布页顶部的 `小程序任务 / 羊毛 / 普通任务` 切换直接写入；它决定任务走小程序即时完成、羊毛查看/使用还是普通任务提交流程。
- `taskCategory` 用于羊毛和普通任务的轻量分类选择，二者使用不同的分类集合。
- 任务标题是自由文本，只负责让用户快速知道任务主题，不能承担流程路由、筛选和验收逻辑。

### 12.2 验收标准必须独立成字段

普通任务发布时必须填写“验收标准”，不能只写在任务标题或任务内容里。它至少要回答：

1. 执行者要提交什么；
2. 发布者检查哪些条件；
3. 满足什么条件才算通过；
4. 不通过时允许如何补交。

第一期不做复杂的规则编辑器，使用有序文字/图片内容块即可；示例图片/流程图和提交材料类型作为普通任务的可选辅助字段。普通任务详情页和提交页必须原样展示验收标准，羊毛详情页展示说明内容，不显示验收字段。

### 12.3 三种任务的完成口径

| 任务类型 | 最小完成/结算口径 |
| --- | --- |
| 小程序任务 | 用户通过任务会话打开目标小程序、满足有效停留条件、返回后点击完成；反馈文字和图片可选 |
| 普通任务 | 用户按验收标准提交指定材料，发布者在规定时间内通过或退回并填写理由 |
| 羊毛 | 用户查看说明并使用福利；免费查看或解锁费在查看动作完成时记一次，不产生提交或验收 |

这套字段关系是最小且稳定的：标题负责理解，类型负责路由，内容负责说明，普通任务的验收标准负责结算依据，羊毛的查看规则负责使用和解锁依据。不能把这些信息合并为一个标题字段。

## 13. 小程序分包策略

### 13.1 结论

建议现在就按分包边界设计，但第一期使用普通分包，不使用独立分包。

当前项目的 `miniprogram/app.json` 已经存在 `subpackages.workbench`，其中放置了资料编辑、工作台和运营分析等低频页面；这说明分包不是从零引入的新机制。后续“我的工具”继续沿用按业务域分包即可。

分包的本质是让低频业务按需下载，不是把四个顶部 Tab 分别拆成四个包。全局底部 TabBar 页面、默认启动页面、公开分享/详情的核心入口和跨业务必须使用的轻量公共能力仍留在主包。官方分包规则也要求 TabBar 页面放在主包，普通分包页面在进入时再加载，并且分包不能直接依赖其他分包。[腾讯云小程序分包加载文档](https://intl.cloud.tencent.com/zh/document/product/1219/61748)

### 13.2 建议的业务边界

开发“我的工具”时建议预留以下边界，名称是规划示例，不要求本轮立即改 `app.json`：

```text
主包
├── 全局底部 TabBar：首页 / 资料 / 雷达 / 我的
├── 登录、公开详情、分享落地等基础入口
└── 跨业务公共 API、认证、轻量组件和样式

已有普通分包
└── subpackages/workbench

我的工具普通分包
├── subpackages/my-tools：我的工具入口和工具列表
├── subpackages/my-tools-mutual-help：互帮互助首页 / 发布 / 任务 / 我的
└── subpackages/my-tools-wechat-groups：未来微信群工具
```

如果互帮互助第一期页面和资源很少，也可以先把“我的工具入口”和互帮互助放在同一个 `my-tools` 分包；但微信群功能不要默认继续堆进同一个包。每个业务域独立成普通分包，后续才能按需加载、单独回归和控制包体积。

### 13.3 为什么不使用独立分包

互帮互助和微信群都是从“我的 → 我的工具”进入的正常业务流，需要复用当前用户、登录态、全局样式、API 服务和业务上下文。独立分包不能直接依赖主包和其他分包，反而会增加认证、公共组件和状态同步的复杂度；它更适合扫码直达、活动页等真正可以脱离主包启动的入口。

因此第一期只使用普通分包，并且不在小程序启动时预下载“我的工具”。用户点进“我的工具”后，再根据真实包体积和首屏耗时决定是否预下载互帮互助分包。最终包体积必须以微信开发者工具的代码依赖分析和重新编译结果为准，不能用磁盘文件大小替代。

## 14. 多任务入口实现跟进（2026-08-31）

任务类型和任务入口是两个不同维度：`taskKind` 决定完成与结算流程，`taskLinks` 记录执行者需要打开的一个或多个入口。普通任务也可以挂小程序短链接、网页链接，不能因为入口是小程序就自动改成小程序任务的即时结算规则。

当前本地前端演示的入口策略：

- `#小程序://...` 识别为小程序入口，详情页调用 `wx.navigateToMiniProgram`；发布者和执行者都可以打开，打开权限不能和提交权限混用。
- `https://...` 识别为网页入口。只有已配置并通过微信业务域名校验的域名才进入小程序 `web-view`；当前代码只配置资料整理助手自己的 `teambuy.lifelove.top`。
- 其他 HTTPS 外链不直接塞进 `web-view`，详情页复制链接并提示“请打开手机浏览器”，避免白屏、域名未配置和第三方页面兼容问题。
- `http://...`、非 HTTPS 以及无法识别的文本不允许发布为任务入口。

业务域名不能通过维护一份“全网主流域名清单”自动获得资格；外部站点是否可进 `web-view`取决于小程序后台配置、域名所有权和 HTTPS 校验。后续若要支持小红书、淘宝等站点，应逐个确认业务场景、配置和真机兼容性，未确认前统一使用手机浏览器兜底。

发布页、执行者详情页和发布者管理详情页现在都使用统一的“任务入口”卡片；任务大厅和任务管理卡片只展示入口摘要，分享图仍然是资料整理助手自己的任务卡，不伪造目标小程序或第三方网站的原生卡片。正式跨设备版本仍必须把 `taskLinks`、任务详情、媒体和分享快照迁移到后端。

## 15. 任务大厅展示范围与默认布局跟进（2026-08-31）

- 任务大厅展示所有当前可完成的已发布任务，包括当前用户自己发布的任务；用户可以像其他任务一样点击并自行完成，不能在前端用发布者身份把自己的任务隐藏掉。
- 顶部“任务”Tab仍负责查看和管理自己发布的任务，两者是不同入口，不代表自己的任务必须从大厅消失。
- 任务大厅默认使用 `2x` 双列，用户仍可以主动切换为 `1x` 单列；布局选择只影响卡片排列，不改变排序、次数或积分规则。

## 16. 羊毛任务与公共任务引擎跟进（2026-08-31，修订）

- 羊毛任务使用公共任务实体，通过 `taskKind=wool` 区分流程，通过 `woolPolicy` 保存 `unlockFeePoints` 和 `allowTip`；不再保存或读取固定完成奖励。
- 羊毛是福利/信息入口，不是交付任务：内容使用有序文字/图片块，但不要求验收标准、不要求提交材料、不进入发布者验收或 5 天自动通过流程。
- 执行者可以先看评论和任务摘要；付费羊毛任务在详情页确认一次性解锁后，才开放完整说明和使用入口；免费羊毛任务直接开放。
- 羊毛的积分动作只有查看解锁费和可选自愿打赏；普通任务仍保留内容、验收标准、提交材料、发布者验收和 5 天自动通过。普通任务包含小程序入口时仍按普通任务验收。
- 普通任务和羊毛任务共用评论模型，支持推荐标签、文字、举报和后台处理状态。羊毛还支持解锁费用退款申请，退款只针对已支付的解锁费用。
- 第一阶段页面实现使用本地 `wool.js` 演示适配器；正式服务端必须将解锁、打赏、退款和普通任务结算收敛到统一积分流水及原子事务，PC 端承担举报/退款审核。
