# 用户内容安全与违禁词配置方案 v1

> 状态：方案设计，尚未实现
>
> 目标：让“资料整理助手”对用户提交、编辑、发布、公开展示的文字内容具备统一、可配置、可追溯的内容安全能力。

## 1. 结论

违禁词不是某几个输入框的校验，而是一条内容发布安全链路：

```text
用户输入/导入
    ↓
统一规范化（只用于检测，不静默改写原文）
    ↓
统一扫描（规则版本化）
    ↓
决定：拦截 / 待审核 / 警告放行
    ↓
保存草稿或进入发布审核
    ↓
公开展示前再次检查
    ↓
规则变更后异步复检历史内容
```

真正需要保护的是“内容对外可见”这一结果，而不是单次保存请求。因此只在小程序端拦截，或只在某个页面加关键词判断，都不能作为完整方案。

## 2. 当前事实、约束与未知项

### 已确认事实

- 当前 `backend/app/services/text_safety.py` 主要用于清理非法 Unicode surrogate，尚未形成违禁词规则引擎。
- 用户内容分布在多条链路：资料/卡片、合集、名片与个人资料、商机合作、微信群资源与活码、互助任务、任务提交、评论等。
- 群资源已有审核、投诉、自动暂停和积分退款相关流程；供需卡已有审核状态；互助评论已有举报流程。
- 生产数据基于现有 repository 的业务实体和 JSON payload 结构，不能通过替换全量数据模型来实现。
- 小程序必须兼顾正常用户输入体验，不能因为一次误命中导致内容被静默改写或丢失。

### 设计约束

- 不能把完整用户原文、手机号、微信号等敏感字段复制到安全日志。
- 规则不能暴露给普通用户，错误提示只说明“暂不能发布的内容类别”或“需要审核”。
- 规则更新、审核操作和人工放行必须可追溯、可回滚。
- 内容版本、分享快照版本和安全判定版本必须保持一致，旧判定不能放行新内容。
- 不能依赖逐条查询规则或逐卡实时扫描来构造首页、列表首屏。

### 仍需业务确认的事项

- 首批规则来源：平台人工维护，还是接入第三方内容安全服务。
- 是否把手机号、微信号、二维码、外链风险作为独立的“联系方式/外链安全”策略，而不是混在违禁词库中。
- 高风险命中是否允许人工放行。建议高风险默认不允许普通审核员放行，特殊放行需要更高权限和理由。
- 平台的内容留存和审核记录保留期限。

## 3. 规则模型

规则库不直接修改业务内容，规则只产生判定。

| 字段 | 说明 |
| --- | --- |
| `id` | 规则 ID，永久保留，不物理删除 |
| `term` | 规则词或短语；仅管理员可见 |
| `normalizedTerm` / `termHash` | 检测用规范化词和哈希 |
| `matchType` | 第一版支持 `contains`、`exact`；正则作为后续隔离能力 |
| `category` | 规则类别，可配置，不把业务类别写死在前端 |
| `severity` | `high`、`medium`、`low` |
| `action` | `block`、`review`、`warn` |
| `scopes` | 适用内容类型或字段范围；空值表示全局 |
| `enabled` | 是否启用 |
| `version` | 规则变更版本 |
| `source` | `manual`、`import`、`provider` |
| `expiresAt` | 临时规则的失效时间，可为空 |
| `operator`、`reason` | 操作者和变更理由 |
| `createdAt`、`updatedAt` | 审计时间 |

建议首批类别包括：

- 违法违规或明显诈骗；
- 赌博、毒品、色情、暴力等高风险内容；
- 虚假承诺、金融/医疗高风险宣传；
- 垃圾营销、诱导刷量、恶意引流；
- 平台自定义黑名单；
- 联系方式、外链、二维码风险（建议作为独立策略，可共享审核队列）。

“包含某个词”不等于“内容一定违规”。例如同一个词在正常行业语境和赌博语境中含义不同，所以不能把所有命中都设为直接拦截。

## 4. 规范化与匹配原则

扫描前生成检测副本，但原始业务文本保持用户输入，不做静默替换。

第一版规范化范围：

- Unicode NFKC；
- 去除零宽字符和非法 surrogate；
- 全角/半角统一；
- 连续空格、换行和常见分隔符归一化；
- 英文大小写折叠；
- 保留原文到规范化文本的字段级映射，便于管理员定位。

第一版不自动把繁体转换成简体，也不把所有谐音、拆字、图片文字猜测当作确定命中；这些策略需要独立评估误杀率。正则表达式也不作为首版默认能力，避免规则错误造成 ReDoS 或大范围误命中。

命中优先级固定为：

```text
block > review > warn > allow
```

同一内容命中多条规则时，只对外返回最高决策，不返回具体违禁词；后台保留规则 ID、类别、字段名和命中次数。

## 5. 内容覆盖矩阵

所有入口都调用同一个 `ContentSafetyService`，业务服务只负责声明内容类型和字段，不自行实现关键词判断。

| 内容类型 | 需要扫描的用户字段 | 保存/发布策略 |
| --- | --- | --- |
| 资料/旧卡片 | 标题、摘要、正文、正文块、标签、位置、分享标题 | 草稿可保留编辑；发布时必须通过 |
| 合集/展示页 | 名称、描述、分享标题、分区标题、展示字段配置中的文案 | 发布前必须通过，命中后不可公开 |
| 名片/个人资料 | 昵称、展示名、职位、公司、简介、行业标签、合作意向 | 高风险立即阻止保存；模糊命中进入审核 |
| 商机合作 | 商机标题、摘要、正文、行业、标签、当前需求/能力 | 发布或进入公开目录前审核 |
| 供需卡 | 标题、摘要、行业、标签、需求内容、申请留言 | 继续使用现有审核状态，并叠加安全判定 |
| 微信群资源 | 群名称、行业、用途、备注、城市文字 | 进入群资源审核；二维码图片和目标链接另做图片/链接安全 |
| 活码 | 名称、描述、目标链接的可读元数据 | 文字走规则；二维码本身不由文字规则替代识别 |
| 互助任务 | 标题、描述、任务内容、完成标准、链接说明、福利说明 | 发布前审核；高风险不能发布 |
| 任务提交 | 提交说明、完成证明文字 | 高风险不入验收链路；图片另做媒体审核 |
| 互助评论 | 评论正文 | 高风险不展示；模糊命中进入审核；保留举报机制 |
| 反馈/投诉/私有沟通 | 用户描述、补充说明 | 默认不进入公共目录；仍记录安全判定，避免后台被恶意内容污染 |
| 企业微信导入原文 | 原始消息和生成卡片的公开投影 | 原始归档可保留为未认领/内部数据；任何公开投影必须复检 |

以下内容不应被简单当作违禁词处理：系统生成的固定文案、规则类别名称、内部 ID、联系方式加密值。系统生成文案可标记为 `system_trusted`，但只允许固定模板通过，不允许用户文本借此绕过检查。

## 6. 状态与生命周期

### 保存草稿

- `block`：返回字段级错误，不写入持久化正文；前端保留当前输入，用户可修改后重试。
- `review`：允许保存为私有草稿，状态标为 `reviewing`，不可进入任何公开列表或分享快照。
- `warn`：允许保存并向用户显示风险提示；是否允许公开由内容类型策略决定。

### 发布与更新

- 发布接口必须重新扫描完整公开投影，不能信任前端上次扫描结果。
- `block`：返回“包含暂不能发布的内容”，不公开、不生成可用分享快照。
- `review`：转为待审核，用户看到“已提交审核，审核通过后公开”。
- 通过：写入当前内容版本和安全规则版本，才允许公开。
- 已发布内容更新后，旧公开版本不应继续代表新内容；新版本必须重新判定，必要时暂时降为待审核，并使对应分享快照失效。

### 公开读取

公开接口只返回“已发布且安全判定仍有效”的内容。发现内容版本或规则版本过期时：

- 高风险旧判定：先停止公开；
- 低风险或未判定：进入异步复检，不让列表接口同步等待全量扫描；
- 复检完成前不生成或继续使用新分享图。

### 规则更新

启用、修改或批量导入规则时生成新 `ruleVersion`，后台投递历史内容复检任务。任务以 `targetType + targetId + contentRevision + ruleVersion` 去重，旧任务不能覆盖新版本判定。

## 7. 数据结构建议

现有业务实体继续保留原字段；新增安全数据，不把大量命中详情塞进每个业务 payload。

### `content_safety_rules`

存放可配置规则，使用明确索引支持按启用状态、作用域和规范化词查询。规则禁用而不是删除。

### `content_moderation_assessments`

建议字段：

```text
id
targetType
targetId
ownerUserId
contentRevision
contentFingerprint
ruleVersion
status: allowed | reviewing | blocked | overridden | stale
decision: allow | warn | review | block
matchedRuleIds
matchSummary: [{fieldPath, category, severity, count}]
reviewedBy
reviewedAt
reviewNote
createdAt
updatedAt
```

只保存字段名、类别、规则 ID、次数和必要的脱敏片段哈希，不把完整原文复制到命中记录。`contentFingerprint` 用于判断判定是否仍对应当前内容版本。

### `content_moderation_audit_logs`

追加记录规则变更、自动判定、人工审核、人工放行、重新扫描和状态回滚。审核记录不能通过更新一行数据抹掉历史。

在当前 repository 架构下，首版可沿用现有 payload 持久化方式新增上述三类存储与对应索引；当审核队列规模和统计查询明显增长，再迁移为专用关系表，不改变服务接口。

## 8. 后台配置与审核入口

入口建议放在 PC “运营工作台 → 内容安全”，不要放到“数据分析”。这是风险控制和运营动作，不是统计报表。

首版页面分为四块：

1. **规则库**：搜索、分类、严重级别、动作、作用域、启停、有效期；新增/编辑前显示规范化结果和冲突提示。
2. **审核队列**：内容类型、标题摘要、用户、命中类别、命中字段、当前状态；提供通过、拒绝、重新扫描，敏感词本身默认脱敏显示。
3. **规则测试**：粘贴测试文本，显示命中类别、最终决策和作用域，不写入任何业务数据。
4. **版本与统计**：当前规则版本、待复检数量、命中趋势、误杀/申诉数量、最近操作。

规则操作要求：

- 不提供物理删除，只能停用或退役；
- 批量导入先预览、去重、冲突检查，再正式启用；
- 高风险规则启用前显示历史内容影响数量；
- 人工放行必须记录操作者、理由和有效范围，不能通过全局白名单绕过所有内容；
- 白名单只支持精确短语 + 内容类型 + 有效期，默认不支持“某用户永久免检”。

## 9. 接口草案

### 内部服务接口

```text
scan_content(content_type, fields, content_revision, rule_version=None)
assert_can_publish(content_type, fields, content_revision)
enqueue_rescan(target_type, target_id, content_revision, rule_version)
```

### PC 管理接口

```text
GET   /api/ops-admin/content-safety/rules
POST  /api/ops-admin/content-safety/rules
PATCH /api/ops-admin/content-safety/rules/{rule_id}
POST  /api/ops-admin/content-safety/rules/import/preview
POST  /api/ops-admin/content-safety/rules/import
POST  /api/ops-admin/content-safety/test
GET   /api/ops-admin/content-safety/queue
POST  /api/ops-admin/content-safety/queue/{assessment_id}/approve
POST  /api/ops-admin/content-safety/queue/{assessment_id}/reject
POST  /api/ops-admin/content-safety/queue/{assessment_id}/rescan
GET   /api/ops-admin/content-safety/stats
```

普通用户不直接调用规则接口。小程序只接收结构化结果，例如：

- `CONTENT_BLOCKED`：暂不能保存/发布，请修改相关内容；
- `CONTENT_REVIEWING`：已提交审核，审核通过后公开；
- `CONTENT_WARNING`：内容可能影响公开展示，请确认后继续。

不把命中的具体词直接返回给小程序，避免帮助绕过规则。

## 10. 性能、并发与安全要求

- 服务启动或规则更新时，将启用规则编译为 Trie/Aho-Corasick 等内存匹配器，原子替换当前版本；请求不逐条查数据库。
- 列表接口只依据内容状态和安全判定过滤，不为每一条记录同步下载媒体或重新完整扫描。
- 扫描结果绑定内容指纹和 revision；旧请求、旧 worker、旧审核结果不能覆盖新内容。
- 所有管理接口必须使用后台管理员权限，不能由小程序传入一个 userId 自行冒充管理员。
- 日志不得打印完整用户正文、手机号、微信号或二维码内容；异常只记录目标 ID、字段路径和安全事件 ID。
- 正则规则若未来开放，必须限制表达式长度、执行时间和语法，不允许直接运行任意管理员输入。
- 图片、二维码、外链、OCR 内容是独立风险面；违禁词引擎不能伪装成图片审核或链接安全审核。

## 11. 分阶段落地

### 阶段 0：盘点与报告模式

- 建立统一字段提取器和规则库；
- 对现有公开内容离线扫描，只记录命中，不改变线上展示；
- 输出命中量、误杀样本、需要人工确认的行业词。

### 阶段 1：规则配置与测试

- 完成 PC 规则库、规则测试、版本和审计；
- 新内容继续以报告模式运行，观察命中率；
- 建立首批人工维护规则，不接入复杂模型。

### 阶段 2：保护新发布内容

- 先覆盖名片、商机、群资源、互助任务、评论和资料发布；
- `block` 直接拦截，`review` 进入审核队列，`warn` 依内容类型处理；
- 发布、更新、分享快照全部使用同一最终判定。

### 阶段 3：历史内容复检

- 按批次复检旧内容；
- 高风险内容自动停止公开，低风险内容进入人工队列；
- 提供误杀恢复和重新扫描，不直接修改用户原文。

### 阶段 4：独立扩展

- 图片/OCR/二维码安全；
- 外链域名和跳转安全；
- 第三方内容安全服务或模型作为“建议”，不能替代确定性的发布门禁；
- 申诉、处罚和用户信用联动。

## 12. 验收与对抗式测试清单

首版实现前必须先补测试，至少覆盖：

- 普通命中、大小写/全角/零宽字符/分隔符绕过；
- `block > review > warn` 的决策优先级；
- 规则作用域不会误伤其他内容类型；
- 规则停用后不再命中，规则版本变更会触发复检；
- 保存草稿、发布、更新已发布内容、公开读取和生成分享快照都走最终门禁；
- 任务评论、任务提交、群资源投诉后的内容仍不能绕过安全状态；
- 旧 revision 的异步结果不能覆盖新 revision；重复审核和重复复检幂等；
- 普通用户看不到具体规则词、审核者身份和内部命中详情；
- 手机号、微信号、二维码、原始企业微信内容不进入安全日志；
- 误杀行业词可进入精确、限范围、限时白名单；
- 规则导入不会造成重复、全局误启用或长时间锁住请求线程；
- 首屏列表不会因规则扫描或历史复检同步阻塞。

验收报告必须分开写明：规则单测、后端接口测试、全链路发布门禁、后台人工审核、微信开发者工具真机体验。仅通过 Python 编译或接口 200 不能证明内容安全链路完成。

## 13. 推荐的下一步开发顺序

1. 确认首批规则类别、动作阈值和人工放行权限；
2. 实现规则与审核记录的数据结构及 repository；
3. 实现 `ContentSafetyService` 和统一字段提取器；
4. 先接入资料、名片、商机、群资源、互助任务/评论这六组高暴露入口；
5. 增加 PC 规则库、规则测试和审核队列；
6. 报告模式跑现有数据，清理误杀样本；
7. 开启新发布门禁，最后再做历史内容复检。

本方案最初作为设计基线编写；截至 2026-09-04，阶段 1 的规则、判定、审计、PC 配置和高暴露入口接入已在本地实现。仍未包含生产部署、小程序上传，以及图片/OCR/二维码/外链和历史异步复检等后续阶段能力。
