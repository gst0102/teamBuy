# teamBuy 当前有效决策

## 当前补充：互助任务沟通与执行者报表 V1

- 任务沟通是一位发布者与一位执行者的私聊；同任务不同执行者之间必须隔离，V1 不建任务群。气泡左右位置以当前查看者 ID 与消息 `senderUserId` 是否相等判定，不能用消息类型或角色名称判左右；所以同一条消息在发送者一侧靠右、接收者一侧靠左。
- 聊天支持文字、本人上传的图片和任务已配置的小程序入口卡片；卡片只允许引用该任务入口，避免任意外链伪造。微信原生卡片转发不是自定义聊天消息的实现方式；当前 V1 卡片在本小程序内展示并通过已有 `shortLink` 打开。
- 后端保存会话、消息和未读计数；前端 4.5 秒轮询作为第一版传输方案，暂不承诺推送通知或即时到达提示。参与校验来源为入口打开/复制、羊毛任务解锁或完成提交。
- 执行者报表以服务端提交和参与事件为准；汇总完成、待验收、退回、已到账积分及任务明细。任务详情优先展示任务入口/完成操作，再呈现评论等后续信息。
- 微信开发者工具编译、体验版上传与真机 UI 验收由用户手动完成；本地 pytest 通过不等于已部署或用户验收通过。

## 当前补充：2026-09-14 同名微信群按数量成组

- 同一微信账号、相同群编号与规范化群名的多个微信群按一个低颗粒度路由包管理，不要求逐个维护物理群身份。扫描器统计同一实时控件树快照中的不同结果行矩形数量，以 `occurrenceCount` 同步到 PC 并保存为 `groupOccurrenceCount`；跨重叠滚动页/搜索前缀只取最大共现数，不重复累计。
- 手机按该数量逐次搜索真实群名、读取新的控件树结果矩形并点击；每次都必须看到原生“完成(n)”递增后才继续。包内任一旧候选被禁用/移出时整包跳过；明确未找到时整包更新移出状态。PC 仍保留旧候选 ID/历史作为别名，不再把它们当成独立发送目标。
- 无法在同一可见快照中同时观察到的同名群没有可可靠推导的身份或数量；不使用位置/顺序制造持久身份。扫描只能报告可观测的最大共现数量，真机发送仍须按 UI 计数验证。

## D1. 文档权威边界

- 全项目通用规则以根目录 `AGENTS.md` 为准。
- AScript 子目录使用 `automation/ascript/AGENTS.override.md` 的专项规则。
- 当前状态以 `docs/CURRENT.md` 为准；已确认的长期决策以本文件为准。
- 归档文档只用于查证历史，不得覆盖当前文件。

## D2. 产品与架构

- 产品正式名称为“资料整理助手”。
- 系统分为稳定基座和可插拔 Skill。基座承载企业微信、会话归档、身份、权限、媒体、资料库、展示页和支付权益；Skill 承载具体内容处理和场景能力。
- 所有文字输入统一走 `ContentObject -> content-to-note -> UserNote`；不为微信笔记、聊天、链接和手动文字重复建设整理系统。
- 资料卡采用 typed card：链接/文章、文本、房源、团购商品、图片/OCR 按 `cardType` 区分，统一收藏、编辑、整理、生成流程。
- AI 只能返回经过校验的结构化建议或固定意图，不能直接写库、扣费、发通知或执行关键业务动作。

## D3. 身份与会话归档

- 小程序微信 `openid` 是用户唯一身份锚点；`userId` 只是内部主键。
- 企业微信 `external_userid` 只能作为来源映射，不能凭昵称、手机号或文本相似度自动认领。
- 会话归档使用共享核心的单一回调、单一 Finance SDK Worker、单一企业级游标和统一解密层。
- teamBuy 作为项目消费者使用独立 token、业务幂等状态和显式群路由；不推进共享核心游标，不跨项目暴露原始媒体标识。

## D4. 媒体与分享

- 图片按 `mediaType + originalSha256/storageSha256` 去重；业务入口统一使用媒体资产服务。
- 分享快照统一走 `miniprogram/plugins/share-snapshot/index.js` 和后端快照接口。
- 分享快照必须绑定当前资料/合集/名片版本；没有有效快照时，不返回资料库、首页或其他错误页面作为分享目标。

## D5. 小程序体验

- 首屏允许匿名浏览，需要归属的动作才按需触发登录。
- 列表先展示元数据，媒体和非关键计算懒加载或后台补齐；缓存必须隔离环境、接口和用户身份。
- 客户身份、手机号、微信号和雷达详情只保存在短时进程内，不写持久化缓存。
- 页面核心布局使用 `rpx`；按钮、标签和操作区使用 flex 居中；用户提供的参考图属于验收标准。

## D6. AScript + ESP32

- AScript 规则只在 `automation/ascript/AGENTS.override.md` 维护。
- HID 自动化只允许使用官方已安装能力和微信正常 UI；禁止微信注入、私有协议、XML 构造、token/session/key 提取和安全规避。
- 页面自动化采用“控件树感知 + ESP32 HID 执行 + 状态复核”：HID 模式用 `mode=6` 读取控件树，控件树只提供唯一目标的 `rect`/中心点，实际点击、长按、滑动、输入和返回均由官方 `BleDevice` 完成；OCR 只用于辅助确认，找不到唯一树节点就停止。
- 双开入口的两个“微信”标签共用 GridView 时，必须从实时树中各自单项容器矩形计算槽位点击位置。进入微信后通过“我”页微信号复核任务账号；昵称（当前为“高同学”和“leo”）只作展示，不作为唯一键。
- `BleDevice.click()` 返回 `None` 属于正常无返回值接口，实际成功必须用界面锚点、日志或截图验证。
- AScript 手机入口统一称为“微信助手”：当前只保留“群发微信”入口，运行时先做定向 `g10` 群台账扫描，再执行群发批次；旧的全量/每日增量、设备状态和任务日志入口已移除。群、文字和卡片内容由 PC 端配置。
- 群台账同步的主路径采用定向搜索：进入具体微信后先在“我”页读取唯一微信号，回到首页搜索 PC 配置的业务编号前缀（当前为 `g10`），进入“群聊 → 更多群聊”，用 mode=6 树读取群编号和群名并做 partial reconcile；不把通讯录“群聊”页或完整会话列表扫描作为群发前置步骤。

## D7. 测试与生产分离

- `TEST_SINGLE` / `TEST_ONLY` 只针对本人设备、本人账号和一个明确配置的 c 开头群编号/批次；PC 对该编号返回并通过资格校验的全部目标组成测试范围，不再由 AScript 群名或候选 ID 静态名单二次筛选。每次仅一条文字和一张现成卡片，不跨编号、不循环重跑，按微信原生上限分块。
- 在明确的 `TEST_SINGLE` / `TEST_ONLY` 任务中，允许自动化完成一次完整 UI 流程并验证结果，不设置默认的发送前停留点。
- `PRODUCTION` 不继承 `TEST_SINGLE` 的发送权限；生产执行必须另行设计官方能力、白名单、审计、限额和回滚。
- 生产链路默认只做准备、预览或 dry-run，不能因测试链路已通过就推断生产可用。

## D8. 群路由

- 群编码必须能映射到具体微信账号下的唯一聊天对象；进入聊天后还要复核顶部标题或等价界面锚点。
- 一个群可以绑定多个人工群编号，一个群编号也可以绑定多个群；`g1001`、`g1002` 仍是 PC 台账中的精确路由标签，同时可由其共同前缀（当前 `g10`）用于微信检索；检索前缀不是最终群身份，最终身份仍是具体微信账号下的群名记录。
- 发送内容不再复制到每个群记录中，改为“群编号 -> 发送内容方案 -> 第 N 批”；同一群编号下的群共享文字和小程序卡片配置。群列表点击群编号即可进入对应方案，批量替换也按方案执行。
- 执行时由 AScript 用户选择批次，PC 后端按“微信账号 + 群编号”生成分组任务，任务内携带该编号下的真实群名单；手机端按微信原生最多 9 个收件群分组发送。群编号和批次均为运行时配置，不能硬编码测试编号。任务生成与手机端实际发送分离，后者必须继续通过官方 ESP32 HID 和微信正常 UI 验证。
- 群编号批次入队不再因 `membershipStatus=unknown` 预先阻塞；手机执行器负责用微信界面确认目标群。只有执行器明确回传“群不在/找不到群”时，PC 才将该群标记为 `removed` 并在台账记录原因，后续批次自动跳过该群。
- 对同账号、同群编号、同群名的候选采用整体许可/移出状态：任何一个旧候选被明确禁用或移出时，整个重名路由包都会跳过；执行器确认整个群名搜索无结果时，PC 对包内保存的候选别名统一记录移出状态。该策略不提供同名物理群逐个追踪。

## D10. AScript 测试证据必须按运行实例归档

- 历史真实发送成功是独立的有效证据；后续同类测试失败只能新增一条“当前运行失败”记录，不能回写成历史测试失败。
- 每次诊断和验收必须绑定实际工程名/路径、设备、微信账号、时间、运行编号、运行时/插件状态、关键日志和截图。必须明确区分历史成功、当前异常、页面未验证和用户验收通过。
- `eval_python` 的导入异常只说明该次调用异常。除非完成同一工程、同一运行时、同一插件来源/缓存和同一设备状态的对比，不得下结论说是版本不匹配，也不得据此否定前一轮成功。
- ESP32 导入或持久连接的验收必须用 AScript 正式工程 `run_project` 和实时日志；优先复用已检查内容的连接测试入口。2026-09-10 已实测 `eval_python` 报 `H8tX` 而现有 `hid_e2e_20260908` 工程导入和连接成功，因此不能把前者作为发送工程的硬性失败门禁，也不能仅凭 `.pyc` 文件头要求重装、升级或清缓存。排查缓存先记录实际 `spec.origin`/`spec.cached`，不得按示例包名或当前工作目录批量删除。
- 正式 ESP32 HID 测试禁止使用 `eval_python` 执行导入、点击或发送；完整链路只能在实际 AScript 工程中通过 `run_project` 完成。`eval_python` 仅可用于不改变设备状态的必要诊断，不能作为正式测试入口。
- 未观察到异常时不得声称存在异常；只有 UI 页面证据和发送结果证据同时具备时，才可报告“发送成功”。

## D11. 新旧 AScript 工程隔离

- 正式入口改为独立的“微信助手”工程，负责九宫格和后续功能；“资料整理助手”作为可回退备份保留。
- 新工程完成文件核对、部署、真实测试并由用户验收之前，不删除或覆盖备份工程。
- 手机存在多个同名或历史副本时，先确认实际启动工程的路径/文件清单，再同步代码；不能仅凭同名查询结果判断手机正在运行哪一份工程。

## D12. 双开微信账号身份

- 双开实例的账号边界必须使用微信“我”页的唯一微信号或同等稳定唯一标识；昵称只能作为展示信息，不能生成账号 ID 或合并任务。
- 群候选、设备账号槽位、心跳元数据和发送任务必须使用同一稳定账号 ID；无法读到唯一标识时停止，不得猜测槽位或回退为昵称身份。

## D13. 群发前置扫描与任务准备

- 群发入口先执行定向群台账扫描：每个微信账号进入首页搜索 `g10`，只处理“群聊”区块；通过实时 mode=6 控件树点击“更多群聊”，再依据实时列表矩形由官方 ESP32 HID 下滑到到底并重读控件树。
- 扫描回传具体微信号下的 `groupCode + groupName + occurrenceCount` 映射，后端按账号隔离更新逻辑路由候选并保存重名收件数量；定向扫描只做 partial upsert，不因缺少“更多群聊”或被踢群的历史残留执行全量删除。实时控件树唯一找到“更多群聊”时点击并继续扫描；等待后没有该入口时，微信当前可见结果视为该前缀的完整结果，正常结束，不因此阻塞发送；多个入口则因歧义停止，不能盲点。人工配置的 `canSend` 等营销字段不被扫描覆盖。
- 扫描与 reconcile 完成后，PC 才按“微信账号 + 群编号 + 批次”创建发送任务；测试准备模式只允许创建指定编号（当前为 `c1001`）的任务，不领取任务、不打开转发页、不发送文字或卡片。

## D15. 自动化完成邮件持久化与异步投递

- `/api/automation/runs/complete` 先把报告作为 `automation-completion-email` 写入 PostgreSQL 共用的持久 `sync_tasks` 队列，再立即返回排队状态；独立后台 worker 负责 SMTP 投递和有界重试，SMTP 延迟或暂时失败不能阻塞设备完成回调。
- `deviceId + runId` 是完成报告的幂等键；同一设备重复提交同一运行编号只保留一封邮件任务。查看 `/api/wecom/sync-tasks` 与对应 task logs 可确认 `queued/running/retrying/success/failed` 状态。
- `success/degraded/failed/unverified` 都是合法运行报告终态；`unverified` 表示设备无法确认最终页面/送达状态，不应因请求校验被丢弃，也不得伪报为成功。
- SMTP 投递是至少一次语义：若邮件服务器已接受邮件而 worker 在持久化成功状态前崩溃，重试可能发送重复邮件；不声称 SMTP 提供端到端恰好一次保证。
