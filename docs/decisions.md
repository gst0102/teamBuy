# Decisions

## 2026-06-10

### 决策：资料库正式持久化以 PostgreSQL 仓储为准，JSON 仅作为开发兜底

选择：

- 资源卡片、分类标签、浏览记录、接龙名单、导入批次等正式数据继续走后端仓储接口。
- 生产/准生产环境使用 `DATABASE_BACKEND=postgres` 和 `DATABASE_URL`。
- `backend/mock/runtime-state.json` 只作为本地开发兜底和 mock 演示数据，不作为正式资料库数据底座。

原因：

- 用户资料库需要跨设备、长期保存，不能依赖本地运行态 JSON。
- 当前后端已有 `PostgresRepository` 和索引结构，先收口使用方式，比重新设计存储层更稳。

### 决策：上传到后端的图片和视频必须先压缩再入库

选择：

- 手动上传和企业微信媒体转存都会先进入同一套媒体处理服务。
- 图片限制最大边长并转为 WebP 压缩版。
- 视频通过 ffmpeg 转为 H.264/AAC MP4，限制宽度和码率质量。
- v0.1 默认不保留原始大文件，资料库只保存可展示的压缩文件 URL。
- 上传接口返回 `originalSize`、`storedSize` 和 `compressed`，便于验收压缩是否生效。

原因：

- 小程序资料库会高频上传图片和视频，原文件直接入库会快速占满服务器磁盘，也会拖慢页面加载。
- 展示型资源页优先需要稳定、够清晰、加载快的文件，而不是原图/原视频归档。

### 决策：原生小程序不引入 Pinia，采用资源 store 模式集中管理

选择：

- 当前项目是原生微信小程序，不具备 Vue/Pinia 运行时。
- 新增原生小程序 `stores/resource-store.js`，集中管理资源列表、分类、单卡片缓存和失效刷新。
- 资源媒体保留原始远程 URL，同时额外维护 `coverDisplayUrl` / `media[].displayUrl` 作为本机缓存展示路径。

原因：

- 用户希望用 Pinia 思路管理资源状态；在原生小程序里应保留这个架构意图，但不能强行引入不匹配的 Vue 生态包。
- 原始 URL 和本地缓存展示路径分离，可以避免保存资源时把手机本地路径写回后端。

### 决策：小程序不再提供“发给客服”操作入口

选择：

- 企业微信客服导入发生在小程序外部的企业微信客服会话中。
- 小程序内只负责待认领、编辑、资源库管理、发布分享和线索跟进。
- 中间加号 tab 改为“添加”，进入手动快速入库页。
- `pages/imports/index` 保留为“待认领导入”页，不作为发送入口，也不暴露 mock 导入按钮。

原因：

- 正确主链路是用户先在企业微信客服会话发送微信笔记、链接等内容，系统自动生成资料草稿，用户再进入小程序编辑管理。
- 已经进入小程序后再引导用户“发给客服”会让路径绕远，并误导用户理解企业微信导入的边界。

### 决策：待联系提醒先支持本地状态闭环

状态：已被 2026-06-10 “高意向访客待联系状态升为后端持久化”取代。

选择：

- 高意向访客加入待联系后，可在管理页标记为“已联系”。
- 未联系前可“取消待联系”，已联系后可“清除记录”。
- 本地 storage 从用户 ID 数组升级为 `{ userId: "pending" | "contacted" }` 状态表。
- 旧数组格式按 `pending` 自动迁移。

原因：

- 用户已经确认“加入待联系”有价值，但如果不能取消或标记完成，提醒会越积越多。
- 当前仍只是个人轻量提醒，不引入后端待办模型，先把发布者个人处理节奏闭环。

### 决策：高意向访客先转为本地待联系提醒

状态：已被 2026-06-10 “高意向访客待联系状态升为后端持久化”取代。

选择：

- 高意向访客卡片提供“复制昵称”和“加入待联系”。
- 待联系状态先保存在小程序本地 storage，按资源区分。
- 暂不新增后端待办、备注或协作模型。

原因：

- 当前目标是让发布者个人能更快处理未接龙但反复访问的访客。
- 本地提醒可以快速验证操作价值；后续如需要多人协作，再升级为后端持久化线索备注。

### 决策：管理页登录访客按重复访问识别高意向

选择：

- stats 对同一登录用户的多次访问聚合为一条访客记录，并提供 `viewCount`。
- 管理页以“重复访问且尚未接龙”作为当前高意向访客判断。
- 访客区支持“高意向 / 最近 / 全部”三段筛选。

原因：

- 未接龙但重复查看资源的用户，通常比单次访问更值得发布者主动关注。
- 访客线索不能只是一串浏览记录，需要直接帮助发布者判断优先级。

### 决策：发布者管理页线索列表按跟进状态分组

选择：

- 接龙名单使用“待跟进 / 已跟进 / 全部”三段筛选。
- 默认展示待跟进线索。
- 保留待跟进线索高亮和快捷动作。

原因：

- 发布者日常处理线索时，最重要的是先清空待跟进列表。
- 分组后已处理线索不会干扰当前工作，但仍可通过“已跟进 / 全部”回看。

### 决策：发布者管理页线索卡片直接提供跟进快捷动作

选择：

- 在线索列表里直接提供电话直拨、复制电话、复制地址。
- 这些动作只在发布者视角显示。

原因：

- 接龙线索进入管理页后，发布者下一步通常就是打电话、复制电话或复制地址。
- 把动作放在列表卡片内，可以减少进入详情或手动选中文本的操作成本。

### 决策：客户侧接龙状态要跟随发布者跟进状态变化

选择：

- 客户打开资源页时，根据 `currentUserRelay.followUpStatus` 显示“已提交”或“已跟进”。
- `pending` 显示“已提交接龙，发布者会尽快联系你”。
- `followed` 显示“发布者已跟进”，让客户知道线索已被处理。

原因：

- 接龙不是单向表单，客户需要知道自己的留资是否已被发布者处理。
- 这个状态闭环能减少客户重复提交和反复询问，也让发布者的跟进动作产生可见反馈。

### 决策：同一用户对同一资源只允许一条有效接龙

选择：

- 客户提交接龙成功后，资源详情页切换为已提交状态。
- 后端拒绝同一 `userId` 对同一 `cardId` 重复创建 active 接龙。
- 发布者管理页将未跟进接龙单独高亮为“待跟进新线索”。

原因：

- 接龙本质是留资线索，不是可无限重复提交的评论。
- 重复提交会污染发布者待跟进列表，也会让客户不知道自己是否已经提交成功。

### 决策：客户视角资源页不展示统计和接龙名单

选择：

- 普通客户打开资源页时，不展示 PV/UV/接龙数统计卡片。
- 普通客户打开资源页时，不展示已接龙名单。
- 发布者打开资源页时，继续展示统计卡片、访问详情入口和完整接龙名单。

原因：

- 分享出去的资源页首先是客户浏览和提交接龙的正式页面，不应混入团长管理数据。
- 浏览统计、接龙名单、电话和地址属于发布者跟进线索，不属于普通查看用户的信息范围。

### 决策：资源编辑页必须支持发布后继续补素材

选择：

- 在资源编辑页直接提供“添加图片/视频”入口。
- 新增素材继续写入卡片结构化 `media`，再通过“保存修改”持久化。
- 首张图片可自动成为封面，其他图片/视频默认进入详情展示区。

原因：

- 资源是长期维护对象，发布后补图、补视频是高频动作。
- 如果要求用户回到创建流程，会割裂资源维护体验，也容易让用户误解为需要重新创建资源。

### 决策：分享资源使用小程序原生分享，访问详情只属于发布者

选择：

- “分享资源”按钮使用 `open-type="share"` 直接调起微信分享面板。
- “访问详情”入口只在当前登录用户是资源发布者时展示。

原因：

- 小程序内无法绕过微信能力边界自行跳到独立微信分享页，原生分享面板是正确入口。
- 访问详情包含浏览、接龙和跟进管理信息，属于团长/发布者管理能力，不应暴露给普通查看用户。

## 2026-06-09

### 决策：自定义导航标题不再通过 WXML 属性实体串传递

选择：

- 标题文案由 `custom-nav` 组件按当前页面路由自动映射。

原因：

- WXML 属性中的 `&#x...` 实体串会在页面上被直接显示，不能稳定作为标题来源。
- 自定义导航是全局模式，标题映射收口到组件里更稳，也更方便后续统一调整。

### 决策：手动添加资源页移除“来源设置”，优先把上传与发布链路做完整

选择：

- 本轮不展示“来源设置”交互。
- 优先清晰表达“封面图 / 详情素材”规则，并打通保存与预览发布。

原因：

- 当前最核心的可测试链路是手动添加资源，不是来源归档分类。
- 参考图中更强调上传、封面、标签、发布动作，来源设置不是当前阻塞点。

### 决策：资源库两层筛选含义要固定

选择：

- 第一排固定为“分类筛选”。
- 第二排固定为“标签筛选”。
- “客服接收 / 手动添加 / 可接龙 / 带链接”不再作为标签筛选项。

原因：

- 用户会天然把两排都理解成同一种“标签”，当前混用会造成认知混乱。
- 来源和能力应作为资源属性展示，不应混进标签体系。

### 决策：手动上传的详情图片/视频进入卡片 `media`，不再塞进详情文本

选择：

- 图片和视频作为卡片结构化 `media` 数据保存。
- 仅附件类文件链接继续写入 `detailText`。

原因：

- 详情素材属于正式展示内容，应该可预览、可排序、可复用。
- 把图片/视频拼进纯文本会让详情页无法做成真正的产品化展示。

### 决策：编辑页不再使用“保存草稿”文案

选择：

- 进入编辑页后，资源已经存在于资料库中。
- 普通保存动作用“保存修改”。
- 发布动作用“发布并查看”，发布前自动保存当前修改。

原因：

- “保存草稿”会让用户误以为资源还没入库，和“保存到资源库”后的流程冲突。
- 用户更关心当前修改是否保存，以及资源是否已经发布可分享。

### 决策：编辑页素材管理先支持删除、设封面和排序

选择：

- 本轮不新增二次上传入口，先管理已有素材。
- 支持删除详情素材、图片设为封面、上移/下移排序。

原因：

- 当前最直接的问题是已上传素材无法维护。
- 二次上传会增加文件上传、封面默认选择和失败回滚等更多交互，适合下一轮单独补。

### 决策：资源编辑页采用“发布页式编辑”

选择：

- 资源编辑页尽量接近用户最终看到的资源详情页。
- 标题、项目名、位置在封面预览区直接编辑。
- 图片点击即可设为封面，不再展示“封面图片链接”字段。

原因：

- 用户编辑时最关心最终展示效果，发布页式编辑能减少学习成本。
- 技术字段会干扰业务用户判断，尤其是封面 URL 这类内部实现细节。

本文件只记录已经明确确认的产品或技术决策，不记录临时想法。

选择：

是否可调整：

后续可扩展商业化，但 v0.1 不做交易闭环。

- 完整标签重命名、排序、批量打标、客户标签等属于后续增强，不进入本轮。

# 2026-06-10

### 决策：上传图片统一转 WebP，视频继续转 H.264/AAC MP4

- 后端上传图片通过 ffmpeg 转为 WebP，并按最长边限制压缩。
- 后端上传视频继续通过 ffmpeg 转为 H.264/AAC MP4。
- 资料库只保存压缩后的展示 URL，不保存本机缓存路径和原始大文件。

原因：

- 用户明确希望图片使用 WebP 减少体积。
- 小程序端缓存图片/视频是展示优化，不能替代后端正式资源地址。
- 后端存储压力优先在上传入口解决，后续如需原文件归档再单独设计对象存储策略。

### 决策：高意向访客待联系状态升为后端持久化

- 新增后端 `lead_reminders` 模型和 API，保存待联系 / 已联系 / 备注。
- 管理页高意向访客不再使用小程序本地 storage 保存跟进状态。
- 新增小程序统一“待联系”列表，用于跨资源集中处理线索。

原因：

- 用户换手机或清理缓存后仍需要继续处理线索。
- 待联系线索属于发布者个人业务数据，应和资料库、接龙、访问统计一样持久化。
- 当前只做个人待办，不扩展团队协作、分配、提醒通知和完整 CRM。

### 决策：待联系列表同时提供资源详情和线索管理入口

- 线索卡片必须明确展示来源资料名称。
- “查看详情 / 资源详情”进入客户可见的资源详情页。
- “线索管理”进入发布者管理页。

原因：

- 待联系线索来自某个具体资料，发布者需要先知道线索上下文。
- 详情页用于核对对外展示内容，管理页用于处理访问、接龙和跟进，两者不能混成一个入口。

### 决策：线索第三阶段先做个人跟进记录和下次跟进时间

- `LeadReminder` 增加 `followUpLogs` 和 `nextFollowUpAt`。
- 待联系页支持新增跟进记录、选择下次跟进日期。
- 当前仍是发布者个人线索工作台，不做团队分配、提醒推送和完整客户档案。

原因：

- 单一备注框不适合记录多次沟通过程。
- 下次跟进日期可以帮助发布者处理跨资源线索，但不需要马上接入通知系统。

### 决策：线索第四阶段按跟进时间组织待办

- 待联系页新增“全部时间 / 今日 / 逾期 / 未来 / 未设置”时间筛选。
- 待联系线索按逾期、今日、未来、未设置、已完成排序。
- 线索卡片展示跟进状态标签，并显示最近 3 条跟进记录。

原因：

- 线索一多后，单纯按更新时间展示不利于当天处理。
- 当前先做前端筛选和排序，不引入服务端分页、提醒通知和日历同步。

### 决策：线索第五阶段先做页内提醒，不接微信通知

- 待联系页顶部新增“今日待跟进 / 已逾期”醒目提醒看板。
- 提醒卡片点击后直接筛选对应线索。
- 新增“一键只看未处理线索”，展示所有 `pending` 线索并沿用跟进优先级排序。
- 本阶段不接微信订阅消息、不做定时推送。

原因：

- 当前仍以小程序内工作台可用性为优先。
- 微信通知涉及订阅授权、模板配置和平台审核，适合等本地工作台稳定后再做。

### 决策：线索第六阶段增加结论归档状态

- `LeadReminder.status` 扩展为 `pending / contacted / invalid / paused / completed`。
- 归档状态保存 `conclusionReason` 和 `closedAt`。
- 待联系页新增“已归档”筛选，并支持无效、暂不跟进、已完成三个结论动作。
- 恢复待联系时清空归档时间和归档原因。

原因：

- 线索不能只在待联系和已联系之间循环，否则工作台会越来越脏。
- 无效、暂缓、已完成是处理结论，不应覆盖备注和跟进记录。

### 决策：线索第七阶段拆出线索详情页

- 待联系列表页只保留线索摘要、状态、来源资料和关键动作。
- 新增 `pages/lead-detail/index`，承载备注、跟进记录、下次跟进、归档原因和结论状态操作。
- 后端新增单条线索详情接口 `GET /api/lead-reminders/{id}`，按发布者校验权限并补充来源资料标题。

原因：

- 列表页承载过多输入框和动作后，扫线索效率下降。
- 详情页更适合处理单条线索的长备注、跟进流水和归档结论。

### 决策：线索第八阶段先沉淀发布者私有客户资料

- `LeadReminder` 增加客户手机号、微信号、预算、意向等级。
- 这些字段只在发布者自己的线索详情页维护。
- 当前不做团队客户池、客户分配、客户去重和 CRM 权限模型。

原因：

- 线索处理后需要沉淀成可复用客户资料，而不是只停留在待办状态。
- 私有字段可以先验证用户价值，避免过早引入团队 CRM 复杂度。

### 决策：线索第九阶段新增客户资料汇总页

- 新增 `pages/customers/index` 客户资料库。
- 客户资料库从发布者自己的线索中筛选已填写手机号、微信号、预算或意向等级的记录。
- 支持按意向等级筛选：全部、高意向、中意向、低意向、待判断。
- 入口放在“我的”和“待联系”页。

原因：

- 单条线索已经能沉淀客户资料，需要一个集中查看入口。
- 当前仍保持发布者私有客户资料，不做团队 CRM 和跨发布者客户合并。

### 决策：客户资料库第二阶段补搜索和快捷复制

- 客户资料库支持按昵称、手机号、微信号、预算、来源资料搜索。
- 手机号和微信号提供一键复制。
- 仍只在发布者私有客户资料范围内检索，不做全局客户搜索。

原因：

- 客户资料库进入日常使用后，检索和复制联系方式是最高频动作。
- 先做本地前端筛选，等客户量变大后再升级为后端搜索。

### 决策：客户资料库第三阶段补排序和资料完整度快捷筛选

- 客户资料库支持排序：高意向优先、最近更新。
- 客户资料库支持快捷筛选：有电话、有微信、有预算。
- 排序、意向筛选、资料完整度筛选和搜索可以叠加。

原因：

- 日常客户管理既需要找高意向客户，也需要快速定位联系方式完整的客户。
- 当前客户量不大，继续使用前端排序筛选；数据量扩大后再下沉到后端。

### 决策：客户资料库第四阶段先做复制摘要，不做文件导出

- 客户资料库支持把当前筛选结果复制为表格文本。
- 摘要字段为：姓名、手机号、微信号、预算、意向等级、来源资料。
- 当前不生成 CSV / Excel 文件，不接系统文件保存能力。

原因：

- 当前最实用的是把筛选后的客户列表快速发给自己或粘贴进表格。
- 文件导出涉及文件权限、格式和平台行为，等复制摘要稳定后再做。
