# Decisions

## 2026-06-29

### 决策：群发消息第一版走企业微信群机器人 webhook 白名单，不做外部群自动群发

选择：

- 第一版新增后端群发 API，只面向我们自己的企业群机器人 webhook。
- webhook 通过 `WECOM_GROUP_BOT_WEBHOOKS` 配置为 `groupId -> webhook` 白名单，只允许后端读取，前端和 Git 不保存真实地址。
- 群发接口统一要求 `WECOM_ADMIN_TOKEN`，默认 `dryRun=true` 只预览消息；必须显式传 `dryRun=false` 才真实发送。
- 第一版只发送文本消息，内置中午更新、下午入口、晚间总结三类企业群运营模板，支持自定义文本。
- 一次请求可以传多个 `groupId`，后端逐个发送并返回每个群的状态。
- 当前不做外部客户群自动群发，不把机器人拉入外部群作为主链路。

原因：

- 企业微信群机器人 webhook 是最适合先试效果的低耦合通道，不需要复用微信客服或客户联系单聊接口。
- 外部客户群 Bot 能力已确认不稳定，继续坚持“外部群人工转化，企业群机器人稳定播报，小程序承接”的分工。
- `dryRun` 默认开启可以避免误发；白名单能避免请求方随意传 webhook 造成越权触达。

### 决策：小程序点击入群的 config_id 由 PC 运营后台通过企业微信 API 生成

选择：

- 手动创建外部客户群和二维码仍然允许，用于扫码测试、朋友圈、人工转发。
- 小程序内“点击加入群聊”需要的 `config_id/plugid`，第一版由 PC 运营后台调用企业微信 `externalcontact/groupchat/add_join_way` 创建。
- PC 后台生成时需要填写客户群 `chat_id`、群名规则、群序号、是否群满自动建群、渠道 `state`。
- 生成成功后保存 `configId/chatIdList/roomBaseName/operatorName`，方便后续复制给小程序插件入口。
- PC 后台提供企业微信客户群列表查询，运营直接选择客户群填入 `chat_id`，不再要求从后台页面手动找 ID。

原因：

- 企业微信后台手动创建的加群二维码不一定展示小程序插件需要的 `config_id`。
- API 创建能稳定拿到 `config_id`，更适合接入小程序按钮式入群。
- 将生成动作和客户群选择放在 PC 运营后台，可以避免开发者手动调接口，也方便留存历史配置和追踪渠道。

### 决策：外部群日报运营第一版用 PC 后台群标识映射 webhook

选择：

- 第一版外部群日报运营不依赖企业微信真实客户群 `chat_id`，也不依赖小程序入群 `config_id`。
- PC 后台维护自定义 `groupId -> webhook` 映射，例如 `resource_test -> 资料助手资源测试群 webhook`。
- 群发 API 继续使用 `groupId/groupIds` 作为目标群标识；目标 webhook 可来自环境变量白名单，也可来自 PC 后台保存的群发渠道映射。
- PC 后台只脱敏展示 webhook，真实 webhook 仅保存在后端本地状态文件或生产环境配置中，不进入前端代码或 Git。

原因：

- 当前用户更需要尽快测试日报运营和上线主链路，暂时不应被小程序 `config_id` 入群能力阻塞。
- 企业群机器人 webhook 已经在测试外部群打通，足以支撑第一版“不同群发不同运营数据”。
- 自定义群标识比企业微信真实 `chat_id` 更适合运营和 AI 协作理解，例如 `housing_changsha`、`resource_test`、`daily_ops`。

### 决策：企业群机器人保留文本日报，并增加小程序卡片入口

选择：

- `POST /api/wecom/group-bot/broadcast` 默认仍发送文本，保持现有日报链路稳定。
- 如需发送小程序入口卡片，传 `messageType=miniapp_card`，并提供 `miniappAppId` 和 `miniappPath`。
- 小程序卡片使用企业微信群机器人 `template_card/text_notice` 格式，卡片点击动作跳转到小程序。

原因：

- 测试群实测 `template_card` 返回 `errcode=0`，可作为比纯文本更清晰的小程序入口。
- 文本日报更适合承载详细内容；卡片更适合做入口提醒，两者需要并存。

## 2026-06-28

### 决策：企业资源搜索第一版只开放高频查询，不直接暴露天眼查全量工具

选择：

- 在资源库中新增 `企业资源搜索`，作为群资源库之外的第二类资源能力。
- 资源页入口采用九宫格组织，不做纵向长列表，方便后续继续扩黄页、商机线索等资源类能力。
- 第一版不把天眼查 162 个工具直接暴露给前台，而是收敛成：企业搜索 + 企业卡 + 6 个高频查询功能。
- 第一版开放的查询功能为：基本信息、股东结构、司法风险、经营情况、历史变更、知识产权。
- 搜索候选免费；基本信息低门槛；深度查询按功能扣积分。
- 查询结果可以保存为企业资源卡；“导出企业摘要卡”作为后续能力。
- Tianyancha API Key 只放后端，前端只调用自家后端接口。
- 同企业同功能 24 小时优先走缓存，避免重复扣分和浪费额度。

原因：

- 前台直接暴露 162 个工具会显得像工具箱，不像产品能力。
- 用户真正需要的是“找企业 -> 看值不值得联系 -> 存成资源”，而不是自己挑低层接口。
- 搜索免费能降低使用门槛，深度功能扣分更符合资源服务的价值感。
- 企业资源卡比一次性查询更能沉淀长期线索资产。

### 决策：服务名片和服务方案归到资料页，合集页只负责打包

选择：

- 名片、服务方案、商机合作页属于单个资料资产，默认在资料页创建和管理。
- 合集页服务场景只负责把名片、方案、案例组合成案例合集。
- 服务场景合集空态不再直接展示“先做名片 / 先做方案”，改为引导去资料页创建。

原因：

- 用户心智更清晰：资料是单个资产，合集是多个资产的打包页。
- 合集页如果直接生产名片/方案，会让用户误以为名片和方案也是合集的一种。

### 决策：首页所有场景都要露出企业微信导入入口

选择：

- 房源场景保留主按钮 `添加房源助手`。
- 日常资料、团购、服务/商机场景在助手区补充轻量 `加企业微信助手` 入口。
- 首页助手区副标题必须使用场景化文案，不再硬写房源说明。

原因：

- 企业微信转发是资料进入系统的重要入口，不能只有房源场景能感知。
- 非房源场景仍需要保留自己的主动作，例如写笔记、新建商品、做服务页，所以企微入口用轻量行承接，不抢主按钮。

### 决策：我的页顶部身份卡只保留一个轻量修改入口

选择：

- 顶部身份卡移除头像角标式“改”提示，只保留右上角单一修改入口。
- 修改入口优先用轻图标，不再用长文字按钮或重复的“改”字标记。

原因：

- 头像角标和右上角入口同时存在时，真机上会显得像重复提醒，顶部不够干净。
- 用户更需要知道“这里可以改”，而不是看到两个编辑提示抢视觉。

### 决策：我的页和资料页顶部说明继续从“品牌句子”收为“页面职责句子”

选择：

- 我的页顶部副标题改为“你的资料、资源和消息都在这里”，优先说明这个页面集中管理什么。
- 资料页副标题继续保留“房源信息稍重、普通资料更轻”的产品口径，但文案改成更软、更日常的表达。

原因：

- 当前四个 Tab 都在收心智，顶部一句话应该帮助用户理解页面用途，而不是只重复品牌名或产品概念。
- 资料页本来信息就多，副标题再写得太硬，会把首屏挤成说明书。

### 决策：资料页顶部 banner 按全场景口径写，不默认站在房源视角

选择：

- 资料页顶部文案默认采用中性表达，适配资料 / 房源 / 团购 / 商机等场景切换。
- 与场景强相关的重点说明下沉到具体卡片、筛选区或列表内容中，不占据全局 banner。
- 资料页主筛选选中态继续统一到蓝色，不再引入黑色主按钮感。

原因：

- 场景切换后如果顶部 banner 仍写房源，会让整页心智错位。
- 资料页已经有多类筛选和标签，颜色越多越显散；蓝白作为主基调更稳。

### 决策：我的页资源库次级入口不展示“预留”，统一用更像产品文案的开放口径

选择：

- `行业通讯录` 和 `行业资源` 这类尚未上线的资源入口，对用户统一展示为 `近期开放`。
- `行业通讯录` 语义偏找人、找渠道、找合作；`行业资源` 语义偏找资料、找机会、找可复用信息。

原因：

- `预留` 更像研发占位词，不像用户界面的正式文案。
- 两个入口都挂在资源库下时，必须先把职责方向拉开，避免用户觉得只是重复命名。

### 决策：专题暂不放在资料页主流程里，合集保留为对外分享主路径

选择：

- 资料页“更多工具”不再展示 `专题管理`，主筛选也不再展示专题筛选。
- 资料编辑页暂时移除专题输入与编辑操作，只保留标签整理。
- `合集` 继续承担对外发送、对比整理、客户查看的主路径；`专题` 如后续保留，只作为更后台的内部整理能力再考虑回归。

原因：

- 用户当前更关心发客户和客户回流，`专题` 在这个阶段会和 `合集` 形成概念竞争。
- 编辑页里标签、场景、客户动作已经不少，再保留专题会让资料主链路变重。

## 2026-06-27

### 决策：前四个 Tab 先统一视觉语言，房源页与非房源页保持不同信息密度

选择：

- 首页、资料、合集、雷达先统一到同一套轻玻璃感、冷色高光和紧凑卡片语言。
- 房源资料页保留价格、地铁、电梯、户型、面积、状态等高价值标签，不为了“更酷”牺牲判断效率。
- 非房源资料、合集和雷达页允许压缩说明文案，用更轻的标题区、摘要卡和 AI 建议卡承接。
- 我的页本轮只确定视觉骨架，不提前深做内部功能布局。
- PDF/方案书能力本轮只预留文案和入口心智，不进入主开发链路。

原因：

- 当前最重要的是先把转发链路和雷达体验做得更顺眼、更像成熟产品，再尽快真机落地。
- 房源场景和普通资料场景的判断成本不同，不能用一套极致压缩方案覆盖全部。
- 我的页内容后续还会单独讨论，先定风格能避免现在过早做死信息架构。

### 决策：支付和分销先不抢跑，月费策略先作为草案沉淀

选择：

- 当前不立即开发正式支付系统和分销系统。
- 先跑通四工作台、群资源库、公开页传播、生成同款和客户雷达回访。
- 免费版早期可给较宽额度，例如 50 个资料资源、10 个合集/公开页、每月 3 个群资源、最近 7 天基础雷达。
- 专业版可先以 9.9/19.9 元/月内测价验证，后续正式价可考虑 19.9/29.9 元/月。
- 99 元/月不作为早期主推，而作为后续 `成交雷达 Pro / 经营增长版`，必须用高意向识别、用户画像、客户轨迹、沉默复活、资料优化和跟进话术支撑。
- `去水印` 暂不作为核心收费点，改用 `品牌展示增强 / 专属展示页 / 弱化平台标识` 表达。
- 分销系统等真实付费和自然推荐成立后再规划。

原因：

- 当前最重要的是验证“用资源找人，用样板打动人，用雷达留住人”的飞轮，而不是先把收费墙搭重。
- 过早收费可能卡住冷启动，过早分销可能吸引刷返佣用户，干扰真实产品价值验证。
- 月费适合本产品，但用户应先感受到持续经营价值，再升级付费。

### 决策：群资源库第一版采用搜索优先和积分交换，不做树形黄页

选择：

- 在“我的”或资源相关入口中新增轻量 `群资源库`，作为四工作台的渠道补给站。
- 第一版搜索优先，不做树形分类目录；首页用搜索框、热词、最近可查看和发布入口承接。
- 群资源用积分交换：新用户送 100 分，查看群二维码扣 30 分，发布群加 20 分，成功进群确认继续加分。
- 查看次数只作为热度，不作为信用；成功进群确认才作为有效信号。
- 二维码 5 天内自然过期不扣分；超过 5 天且多人反馈失效才扣轻罚。
- 群类型和用途采用“系统预设 + 用户自定义标签”模式，不把分类做死；金融、爱好者、细分行业等长尾场景允许用户自行添加。
- 上传群二维码流程遵循“能系统识别就系统识别，能点选就点选，尽量少手填”的原则；系统负责识别二维码可读性、疑似微信二维码和重复，城市/类型/用途/人数/活跃度/有效期由用户点选。
- 每个群必须设置二维码有效期，默认 5 天，支持 1/3/5/7 天点选。
- 群资源库首页可展示真实统计，例如 `今日新增 X 个群 · Y 个确认可进`，但不能伪造数字。
- 虚假群下架时必须追回该群已获得的发布奖励和确认奖励，再按严重程度额外扣罚。
- 举报不立即奖励，只有经多人确认或平台确认有效后，才给少量积分奖励。
- 群资源规则通知以站内通知为底座，订阅消息只做重要结果提醒，微信客服只做咨询和申诉解释。
- 第一版不做充值、人工撮合、群资源交易、公开二维码墙、企业通讯录爬虫。

原因：

- 前期基础数据少，树形目录会显得空、重，并暴露哪些城市或行业资源不足。
- 搜索能让用户直接表达需求，空结果还能沉淀“想找什么群”的需求池。
- 积分机制能降低白嫖和垃圾发布，同时避免重人工运营。
- 群资源库的价值是给房源、团购、服务、资料四个工作台带来渠道，不应抢首页成交机会心智。

### 决策：产品主表达升级为资料驱动的成交辅助系统

选择：

- 产品仍保留“资料整理助手”的长期基座，但当前第五期主表达从“整理资料”升级为“私域资料成交助手”。
- 首页和反馈页优先展示“今日成交机会、客户雷达、跟进建议、资料优化建议”，而不是只展示资料数量和访问统计。
- 本期不做外部推送，先做小程序内提醒、高亮和可复制跟进话术。
- 本期不用大模型，先用规则引擎判断高/中/低意向，后续再预留 AI 话术增强。

原因：

- 用户愿意付费的不是单纯资料归档，而是“知道客户看没看、有没有兴趣、该不该跟进、怎么开口”。
- 小程序内提醒最快可验收，也避开订阅消息授权和企业微信主动回消息的不确定性。
- 规则引擎能先跑通稳定闭环，避免把成交辅助能力绑定在模型成本和模型失败兜底上。

### 决策：公开页负责成交展示，后台页负责成交判断

选择：

- 客户公开页只展示公开资料和转化按钮，只上报行为，不展示系统判断。
- 发布者后台才展示客户雷达、意向判断、跟进建议、客户列表和私密字段。
- 后端私有接口必须校验 `requesterUserId == ownerUserId`；不能靠前端入口隐藏保护权限。
- `privateData`、`analyticsData`、`opportunityAlerts`、`radarProfiles` 只允许 owner 私有接口返回。

原因：

- 客户行为可以被记录，但客户不能看到系统对自己的判断，否则会破坏信任。
- 同一个小程序服务用户和用户的客户，必须用接口权限和页面模式隔离。
- 后续加入课程、服务、商品等场景时，仍可复用同一身份隔离原则。

## 2026-06-26

### 决策：房源助手作为首页增强入口，不重排原首页

选择：

- 房源版首页保留原有结构：banner、今日概览、常用入口、最近成果、反馈。
- 不再把首页改成新的大“接盘助手”页面，避免压掉用户已确认的工作台结构。
- 在原 banner 中增加轻量“房源助手已准备好”入口，在常用入口中把第一项改为“添加房源助手”。
- 常用入口标题保持中性，使用“常用入口”，不写“租房中介常用入口”。
- 底部五个 tab 保留：`首页 / 资料 / 合集 / 反馈 / 我的`。

原因：

- 当前首页结构已经被用户真机看过，直接大改会丢掉今日概览和客户反馈闭环。
- 房源助手是主路径增强，不是替换所有工作台信息。
- “反馈”是成交闭环的一部分，不能从底部导航中删除。

### 决策：企业微信完成后必须有反馈，第一版先发文本

选择：

- 企业微信客服收到房源并处理完成后，后端生成结构化通知，记录结果路径、动作和发送状态。
- 真实 `sync_msg` 导入完成后尝试用微信客服接口给用户发送文本反馈。
- 文本反馈包含完成标题、隐私保存说明和小程序结果路径。
- 发送失败只记录 `sendStatus=failed/sendError`，不影响资料生成。
- 第一版不强做企业微信小程序卡片消息，后续在真实文本反馈稳定后再升级。

原因：

- 中介发给助手后需要确定感，否则会怀疑是否处理成功。
- 文本反馈最稳，能先验证 48 小时客服会话窗口、token、open_kfid 和外部联系人链路。
- 发送动作不能阻塞核心生成链路，否则企业微信临时失败会影响入库。

## 2026-06-25

### 决策：首批推广聚焦房源中介，前台采用“房源版”尖刀策略

选择：

- 第一批目标客户优先选择房源中介、二房东和对盘群里的房源流通参与者。
- 对外推广阶段不平均展示日常资料、团购/商品、服务四个工作台，而是默认进入房源工作台，包装为“资料整理助手 · 房源版”。
- 其他三个工作台保留为长期架构和后续扩展能力，不删除、不回退；只是中介冷启动版本里隐藏主动切换入口或下沉到“更多场景”。
- 中介版首页核心动作收口为：发房源给助手、生成房源卡、建房源合集、看客户反馈、生成同款。

原因：

- 房源中介高频发资料、离佣金近、对客户反馈和带看跟进敏感，且天然存在对盘群和同行传播网络。
- 首批冷启动需要打穿一个尖场景，不能让中介一进来就看到日常、团购、服务等无关入口而分散理解。
- 保留稳定基座和多工作台架构，后续可把房源打法复制到团购、服务和日常资料场景。

### 决策：房源合集是首批核心展示页，主推“清单对比”和“精选橱窗”

选择：

- 第一批推广不只推单套房源卡，重点推“房源合集”作为中介的移动房源橱窗。
- 首批主推两个合集模板：
  - 清单对比：适合对盘群和同行快速扫房源，重点展示租金、户型、区域、可看状态。
  - 精选橱窗：适合客户和朋友圈，强调大图、主推房源和视觉吸引力。
- 合集页客户侧展示发布者头像/昵称、合集标题、套数、更新时间、可约看数量、联系电话/微信复制和房源列表。
- 合集编辑侧必须支持快速移除、隐藏、排序和设为主推；“从合集移除”只删除合集引用，不删除资料库房源。
- 合集页和单房源页都保留轻量转化入口，例如“我是中介，也想生成这种合集 / 生成同款房源卡”。

原因：

- 中介更常见的真实动作是给客户或同行发一组房源，而不是只发单套。
- 合集比单卡更像个人房源货架，更适合作为对盘群种草和同行裂变入口。
- 清单对比和精选橱窗分别覆盖同行效率和客户视觉，是第一批最容易理解和验证的模板。

### 决策：生成同款只复制公开房源内容，私密上游联系人不继承

选择：

- A 中介发布房源卡或房源合集后，B 中介点击“生成同款”或转发给企业微信助手时，只复制公开房源内容、图片和展示结构。
- B 生成的对外联系方式自动替换为 B 自己的电话/微信。
- B 的上游联系人默认可记录为 A 中介，因为 B 的房源来源是 A。
- B 可以自行编辑自己的上游联系人，但默认不能看到或继承 A 私密保存的真实房东、二房东或渠道联系方式。
- A 私密记录的上游联系人只有 A 自己可见；除非 A 后续主动开启明确的合作共享开关，否则不对复制者开放。
- 公开客户页不展示“隐藏了房东联系方式”等提示；“上游联系人已私密保存”只应出现在发布者管理态或生成同款说明中。

原因：

- 上游联系人是中介的私有资产，若被同行复制走，A 不会愿意用系统发布房源。
- B 需要的是“把房源变成自己的客户页”，而不是绕过 A 获取 A 的上游资源。
- 默认把 A 作为 B 的上游联系人，符合真实对盘关系，也能承接后续合作、分佣和带看沟通。

### 决策：媒体资产优先去重，房源卡和合集只保存引用

选择：

- 图片和视频作为独立媒体资产处理，房源卡、合集和用户资料只保存引用关系。
- 上传或转存媒体时先计算原始文件 `sha256`，hash 一样即认为是同一个原始媒体，不重复存储。
- 图片统一压缩并转为 WebP 作为长期展示文件；视频统一转为 H.264/AAC MP4，并生成 WebP 封面图。
- 同时保存 `originalSha256` 和 `storageSha256`：前者用于原始文件完全去重，后者用于校验压缩/转码后的存储文件。
- 删除房源卡或从合集移除房源时只删除引用，不直接删除媒体本体；无引用媒体后续由后台清理。
- 第一版先做 sha256 完全去重；相似图片、截图、微信压缩后二次识别后续再考虑 perceptual hash。

原因：

- 同一套房源标题、描述、租金和联系方式可能不同，强行合并房源容易误伤；但相同图片/视频去重收益高且风险低。
- 中介复制同行房源时，最大成本是图片和视频重复存储；媒体资产去重能同时降低服务器成本和用户重新传图成本。
- “同行转来的房源，不用重新传图，一键生成你的版本”也是房源版的关键营销卖点。

### 决策：房源合集默认一列展示，双列作为可选紧凑模式

选择：

- 所有房源合集模板都支持“一列 / 双列”排列选择。
- 默认一列，保证标题、图片、标签、价格和联系按钮在手机上不被挤压。
- 双列只作为用户主动选择的快速浏览模式，不作为默认。
- 小程序按钮和标签的基础居中规则统一放到 `miniprogram/app.wxss`，页面只补局部尺寸。

原因：

- 用户真机截图显示双列和原生按钮默认样式容易造成按钮变形、内容被遮挡。
- 中介发给客户或同行时，稳定可读比首屏堆更多卡片更重要。
- 全局按钮基线能减少不同页面重复写样式带来的反复偏移。

### 决策：微信助手入口优先打开企业微信客服，未配置时复制兜底

选择：

- 生成同款页的主按钮语义改为“打开微信助手”。
- 后端复用现有归纳整理企业微信客服配置，通过 `WECOM_CORP_ID + WECOM_OPEN_KFID` 生成小程序打开客服需要的 `corpId/extInfoUrl`。
- 小程序优先请求 `/api/wecom/customer-service-config` 并调用 `wx.openCustomerServiceChat`。
- 后端未部署、参数缺失或调用失败时，继续复制整理指令，让用户手动粘贴给助手。

原因：

- 微信小程序不能凭一个微信号直接自动添加客服，必须走官方企业微信客服能力。
- 当前项目已有归纳整理用企业微信客服，不应再要求前端手工维护另一套客服配置。
- 当前阶段先保留可用的复制兜底，避免后端未部署或微信客服调用失败时主链路中断。

### 决策：日常资料台不默认 SCRM 化，资料库必须包含普通 note-only 资料

选择：

- 日常资料台定位为资料管理底座，核心是保存笔记、图片、链接、整理资料和生成资料包。

原因：

- 普通用户新增笔记后首先期待能在资料库看到，不应因为它没有旧 Card backing 而丢在列表外。

- 普通资料加入资料包时，资料包编辑页默认按普通资料包处理，不套用房源推荐包文案或租金校验。

- 当前工作台为房源、团购或服务时，资料库默认只展示对应业务资料。
- 反馈页不再提供四个工作台的横向切换；工作台切换仍放在首页模式选择里。
- 反馈页统计和列表按当前工作台过滤，日常资料台使用中性“分享反馈”语义，业务工作台内部再展示客户、买家、咨询等业务词。

原因：

- 资料整理助手的普通用户不一定是中介、团长或服务顾问，日常模式直接看到房源/服务会让产品定位显得错位。

## 2026-06-23

### 决策：房源卡保留用户发布标题，系统只整理标题下方信息

选择：

- 房源资料库卡片和房源微信转发标题优先使用用户原始标题，不清洗标题里的表情符号、符号和中介发布风格。
- 系统负责整理标题下方的结构化信息，例如租金/价格、户型、区域、导入来源、访客、客户动态、预约、留资、咨询和待跟进。
- 房源卡主操作只保留一个：有客户动态时优先“看客户”，没有客户动态时优先“分享”。
- 编辑、加入合集、复制文案和删除收进“更多”，不再常驻挤占房源标题和客户信号。
- 房源详情页前台不用 `轻 SCRM`，改成“客户功能”和“客户反馈”；标签与专题在房源场景弱化为“资料归类”。

原因：

- 中介房源标题经常带表情符号和个人风格，这是行业发布习惯，不应被系统误判为冗余。

- 房源详情页是编辑和发布工作台，不应该把后台能力名、低频标签维护和全部操作都放到首屏。

### 决策：房源卡分享常驻，合集按当前工作台归属

选择：

- 房源资料库卡片中，`分享` 是常驻动作；有客户动态时额外显示 `看客户`，不能用 `看客户` 替代 `分享`。
- 租金和户型是房源客户决策优先级最高的两个字段，必须在房源卡、客户页和微信转发卡片中前置。
- 微信转发标题不把租金/户型融进标题本体：第一行保留用户原始标题，第二行展示 `租金 · 户型`；页面内主标题同样继续保留用户原始标题。
- 房源资料库卡片也按同一层级展示：标题第一行，`租金 / 户型` 第二行，不再做成容易被误读的普通胶囊标签。
- 微信转发封面图采用房源专属 canvas 动态生成，封面图内固定展示标题、租金、户型和房源图；标题换行仍保留，但不能只依赖微信标题渲染。
- 对旧导入卡，资料库前端允许从标题、摘要和详情文本兜底识别租金/户型；识别不到时显示待补，不让房源卡静默缺少关键字段。
- 分享图的营销露出当前只做轻品牌署名，例如 `由资料整理助手生成`；四个资料工作台完成后，再统一讨论品牌区、转化话术和是否引导创建同款资料卡。
- 客户页预览从站内进入时应能返回上一页；如果从微信分享单独打开导致没有上一页，页面需要提供回首页兜底。
- 合集页遵循当前 `workspaceMode`：房源工作台默认展示房源合集，团购工作台默认展示团购合集，服务工作台默认展示案例合集，日常资料台默认展示普通资料包。
- 自动生成合集 / 一句话生成合集是核心增强能力，但必须等到能真实筛选资料并生成展示页时再做，不做空壳入口。

原因：

- 中介日常工作里，看到客户动态后仍然可能继续转发同一套房源，分享不能被隐藏。
- 租金和户型比来源、标签、客户动态更接近客户第一判断点，应在标题后立即出现。
- 工作台已经拆成日常、房源、团购、服务，如果合集页仍默认展示四类合集，会削弱工作台模式的清晰边界。
- 微信分享打开的小程序页面通常没有原来的首页/资料库页面栈，不能只依赖左上角返回。
- 现阶段房源分享的第一目标仍是帮中介把房源发出去并获得客户动作，营销露出不能喧宾夺主。

### 决策：合集新建流程采用模板先行

选择：

- 合集生成流程固定为：`先选模板 -> 新建合集 -> 选择生成方式 -> 选择和确认房源 -> 预览 -> 发布`。
- 模板不是后置美化步骤，而是第一步认知入口，用来帮助用户理解“合集是给客户看的页面”。
- 第一版生成方式只真实支持 `从当前筛选生成` 和 `手动选择`。
- 房源合集的增强方向优先是强字段筛选，例如租金、户型、地铁距离、电梯/楼梯、区域和可看状态；AI 自然语言只是后续入口，不是第一版主角。
- `按条件筛选`、`按近期反馈推荐` 暂时只作为下一版能力提示，不能做假入口或伪智能生成。
- 资料选择区默认分批展示，每次 10 条，避免房源多时用户为了保存/预览长距离下滑。
- 合集模板参考图放服务器 WebP，不放小程序主包；小程序配置中只保存 HTTPS 远程地址，便于缓存和后续替换。
- 发布前必须保留用户确认环节，不能让系统自动筛选后直接发布。

原因：

- “合集”对普通用户偏抽象，先问生成方式会让用户不知道自己在做什么。
- 先看到精选橱窗、对比清单、朋友圈长页、品牌名片等模板和对应参考图，用户更容易判断自己想发给客户的最终效果。
- 房源场景涉及真实客户和真实房源，系统推荐可以提高效率，但最终展示给客户前必须由用户确认。

### 决策：客户看板首屏按处理优先级组织，而不是按分类并列

选择：

- 房源客户看板首屏主任务是回答“今天先联系谁”，不是把待跟进、新访客、咨询预约和房源效果平铺成同等重要的数据块。
- 首屏采用“优先联系队列”：预约看房、留电话/微信、明确咨询、站内留言排最前；多次看同一套、看多套、从推荐包点进单房源的新访客作为高意向补充。
- `客户动态` 保留在同一页面，但定位为观察和复盘区，用来解释优先联系原因、查看新访客、预约咨询、房源效果和推荐包带来的行为。
- `客户动态` 不是第二个待联系列表；是否联系、何时联系、用什么方式联系，由用户自己判断。
- 原 `最近访客 / 房源效果 / 推荐包效果` 继续作为下钻和分析入口，不抢首屏处理优先级。

原因：

- 用户真机反馈核心数据已经能对应，但页面信息有点多，`待跟进 / 新访客 / 咨询预约` 容易产生重复感。
- 中介打开客户看板时最需要先处理明确举手的客户，再观察还没有留资但有兴趣的人。
- 如果所有分类都用同等权重展示，用户会被迫自己判断排序，客户看板就从“处理工具”退回成“数据面板”。

### 决策落实：房源客户看板一期只做前端路由和信息架构收口

选择：

- 本期前端先复用现有客户看板和展示页数据，不新增后端模型、不新建复杂 CRM。
- 房源首页四指标点击后只做清晰分流：房源筛选、房源效果、最近访客、待跟进。
- 客户看板继续使用现有经营数据接口，但房源模式默认 Tab 改为 `followup`，展示页数据改名前台表达为“推荐包效果”。
- 资料 Tab 作为小程序 tabBar 页面，首页进入房源筛选时用本地一次性入口筛选承接，不依赖 `switchTab` URL query。

原因：

- 当前已有工作台、客户动作、展示页和资料库基础能力，先把“看得懂、点得通、知道谁该跟进”闭环，比新增后台聚合更稳。
- 微信小程序 tabBar 页面参数传递受限，用一次性本地入口筛选能避免改动路由结构，也不影响用户后续清除筛选。
- 保留展示页底层能力可以兼容原有资料包 / 合集链路，同时房源前台用“推荐包”降低理解成本。

### 决策：房源客户看板优先处理客户，展示页作为推荐包效果

选择：

- 房源首页四个指标固定朝“看得懂、点得通、能处理”收口，推荐为“房源 / 打开 / 访客 / 待跟进”。
- 第四项不再叫“客户”，改为“待跟进”，避免用户分不清是客户总数、访客数还是待联系数。
- 四个指标都必须可点击：房源进入房源资料筛选，打开进入房源效果，访客进入最近访客，待跟进入客户看板默认页。
- 客户看板默认展示“待跟进”，并以“最近访客 / 房源效果 / 推荐包效果”作为后续 Tab。
- 展示页在房源场景里解释为“多套房源推荐包”，负责展示多个房源一起发给客户后的打开、访客、房源点击和咨询，不作为客户看板默认首屏。
- 前台不使用 SCRM 作为主要命名，用“客户看板 / 待跟进 / 客户动态 / 推荐包效果”表达。

原因：

- 房产中介进入首页最关心的不是 BI，而是今天谁看了房源、谁留下联系方式、谁要跟进。
- 如果客户看板默认进入展示页效果，用户会觉得是在看后台数据，而不是处理客户。
- 展示页原本的产品价值是“多套房源一起发给客户”，应继续保留，但要放在推荐包效果里承接，而不是和单房源客户跟进混在一起。

### 决策：客户痕迹必须在首页和资料卡第一时间曝光

选择：

- 客户打开单条新资料页时，必须写入资料浏览事件，不再只统计旧 Card 分享页。
- 首页统计固定分成“资料量 / 打开 / 访客 / 客户动态”四层，客户动态包含留资、预约、接龙/下单、咨询等需要处理的动作。
- 首页“最近反馈”升级为“客户动态”，优先显示有浏览或客户动作的资料，让发布者第一眼知道哪条资料有客户。
- 资料库卡片必须直接显示“打开 / 访客 / 客户动态”，有待跟进或新客户动作时用红点和高亮标签提示。
- 详情页和 SCRM 页负责看具体人、电话、微信、预约和跟进记录；首页/卡片负责快速提醒“来了客户”。

原因：

- 资料整理助手的经营价值不只是保存资料，而是把客户打开、咨询、留资、预约等痕迹及时反馈给发布者。
- 如果浏览/访客/SCRM 只能进详情页才看到，用户会误以为没有效果，也不容易形成“发出去 -> 有反馈 -> 跟进”的习惯。
- 新资料客户页 `note-preview` 和旧 Card 统计口径必须打通，否则企业微信导入的新资料会出现“怎么点都是 0”。

### 决策：工作台总看板必须带 requester 校验

选择：

- `GET /api/dashboard/business` 不再只依赖 `ownerUserId`。
- 接口新增 `requesterUserId`，并要求 `requesterUserId == ownerUserId` 才返回工作台总览、客户看板、访客画像、客户动作等后台统计。
- 非 owner 请求返回 `403`，匿名或缺少请求者身份返回 `401`。
- 小程序 owner 自查时默认同时传 `ownerUserId` 和 `requesterUserId`。
- 展示页公开访问仍走公开接口；后台 analytics、单条资料互动和工作台总览必须保持 owner 权限边界。

原因：

- 工作台迁移后，客户看板从“我的”移到“工作台”，不能把前端入口隐藏当成隐私边界。
- 工作台总览包含客户动作、联系方式、访客画像和后台统计，属于 owner 私有经营数据。
- P0-27 要求明确证明 owner、非 owner、匿名访客三类身份不会越权看到 owner 数据。

### 决策：业务识别提示只切工作台偏好，不改资料归属

选择：

- 房源识别后建议切换 `workspaceMode=property`。
- 商品 / 团购识别后建议切换 `workspaceMode=groupbuy`。
- 服务方案 / 电子名片识别后建议切换 `workspaceMode=service`。
- 提示必须提供“继续当前工作台”和“切换到对应工作台”两个选择。
- 点击切换只保存 `workspaceMode`，不修改资料 owner、不删除资料、不强制改变身份。

原因：

- `workspaceMode` 是常用工作台偏好，不是不可逆行业身份。
- 业务识别的目的是给用户更合适的首页和工作台入口，不应改变资料安全边界。
- P0-23 要求用户可以继续当前工作台，不能被强迫切换。

### 决策：首页与 Tabbar 工作台模式一期只验导航和信息架构

选择：

- 一期目标固定为重构 `首页 / 资料 / 合集 / 工作台 / 我的` 的信息架构。
- `workspaceMode` 只影响首页、快捷入口、工作台内容、资料默认筛选、合集推荐和空态文案。
- 一期实现中 `workspaceMode` 先存小程序本地，不新增后端用户偏好字段。
- `pages/visits` 复用为“工作台 / 反馈中心”，`pages/showcases` 复用为“合集 / 资料包”，底层数据逻辑尽量不改。
- 切换工作台模式不删除资料、不改变资料归属，也不代表不可逆行业身份。
- 客户看板从“我的”迁出，归位到工作台里的反馈中心。
- 合集页一期只验轻版入口和空态，不把完整专题合集中心作为通过条件。

原因：

- 本阶段要解决“用户一进来知道这是我的工作台”，不是继续堆新行业功能。
- 如果把完整合集中心、完整 CRM、支付、库存、会员权益一起塞进一期，会让导航重构失焦。
- 普通用户不应该默认看到客户、线索、接龙、看房、SCRM 等业务入口。

### 决策：标签与专题建议必须按资料类型隔离

选择：

- 房产相关默认标签、专题和示例只允许在 `property_listing` 场景出现。
- 非房源资料详情页需要过滤旧默认房产上下文，例如“房产 / 房源 / 租房 / 万家丽 / 公寓”等。
- 用户手动添加的标签保留，以 `userTags` 作为是否人为添加的判断依据。
- 资料库列表和资料详情页使用同一套上下文过滤规则，避免一个页面干净、另一个页面仍显示旧默认值。

原因：

- 电子名片、服务方案、普通笔记如果显示“万家丽租房”这类房产专题，会让用户误以为资料类型或模板串场。
- 标签和专题属于资料管理入口，默认值必须服务当前资料类型，不能复用上一阶段房源演示数据。
- 用户自己的标签可能正好包含房产词，不能粗暴删除，只清理系统默认污染。

### 决策：运营策划沉淀为项目专属 Skill

选择：

- 新增 `skills/operation-planning/SKILL.md` 作为 teamBuy / 资料整理助手专属运营策划 Skill。
- 以后讨论运营方向、推广、增长、获客、转化、留存、私域、商业化、上线计划或运营复盘时，先使用该 Skill。
- 运营建议必须基于仓库长期记忆和当前真实产品阶段，不把聊天上下文或演示数据当作事实。
- 运营核心飞轮固定为“资料入库 -> 结构化成资料卡 -> 生成销售页/展示页 -> 发给客户/群 -> 客户动作回流 -> 跟进处理 -> 复用再发”。
- 运营输出默认包含目标人群、阶段判断、可执行动作、话术、验证指标和风险，而不是泛泛的品牌建议。

原因：

- 项目已经从早期团购工具扩展为资料整理、电子名片、服务方案、展示页、客户动作和经营看板的组合产品。
- 如果运营讨论不先校准当前功能边界，容易承诺未真机验收或当前明确不做的能力。
- 将运营策划做成 Skill，可以让后续新会话稳定继承产品定位、用户场景、增长飞轮和红线。

## 2026-06-22

### 决策：服务方案按参考图整块重做，不在旧页面上继续补丁式迭代

选择：

- `service-offer-studio` 直接按“选模板 -> 填资料 -> 确认详情页效果 -> 保存分享”重做完整工作台。
- 模板选择页不再只是线框卡片列表，而是左侧模板清单 + 当前模板完整首屏预览。
- 确认页主预览改成“客户详情页视角”，不再只看一张分享卡。
- `note-preview` 中 `service_offer` 详情页同步改成模板化销售页结构，并补底部 4 个主动作：电话、微信、预约、留资。
- `email / message` 等次级动作下沉到联系区，不和主成交动作抢层级。

原因：

- 用户这轮给出的参考图已经不是“局部样式建议”，而是完整链路标准。
- 旧实现停在半成品状态：能切模板、能填表，但模板感、详情感和工作台感都不够。
- 如果继续在旧结构上叠补丁，页面会越来越像功能拼贴，而不是独立服务方案工作台。

### 决策：服务方案走独立销售页工作台

选择：

- `service_offer` 不再只通过通用模板选择页创建，而是新增独立 `pages/service-offer-studio`。
- 服务方案工作台采用“选风格 -> 填方案 -> 确认效果 -> 保存分享”的路径。
- 4 个首批模板固定为咨询预约、服务报价、案例背书、活动招募。
- 同一份服务内容可以自由切换模板；切换模板只更新 `displayTemplate` 等风格元信息，不覆盖已填写字段。
- 已有服务方案从笔记编辑页进入“设置方案样式”，不在笔记编辑页塞大块模板预览。

原因：

- 服务方案的核心不是记一条资料，而是快速生成一张能发给客户的非标服务销售页。
- 电子名片已经验证“独立工作台 + 模板切换 + 客户页预览”的体验更符合用户预期。
- 服务方案和商品展示都可能有价格，但服务方案不应进入 SKU、接龙、订单和支付路径。
- 将模板体验前置后，用户路径从“填资料”变成“挑一个好看的销售页，改几句话，直接发”。

### 决策：电子名片微信转发封面使用独立生成器

选择：

- 电子名片的微信聊天卡片封面不复用普通资料分享图，也不直接依赖客户页截图。
- 新增 `miniprogram/utils/business-card-share.js`，统一生成横版名片封面。
- 电子名片从客户预览页、编辑页和资料库列表转发时，都优先使用该生成器产出的 `imageUrl`。
- 封面内容固定围绕首屏成交信息：圆形头像、姓名、身份、公司/门店、服务范围、电话/微信和“打开名片”行动提示。
- 普通笔记、房源、商品、服务方案暂不使用该生成器，避免业务表达混淆。

原因：

- 微信聊天里的小程序卡片不是客户页 WXML，也不会自动截图；不独立生成封面就会退回普通小程序卡片或二维码卡片。
- 电子名片的核心价值是“第一眼像一张漂亮名片”，微信收到的卡片必须和模板预览、编辑页首屏、客户页首屏保持同一套视觉语言。
- 将封面生成独立出来后，后续增加 4 套名片风格时只扩展生成器，不需要每个页面重复画图逻辑。

### 决策：电子名片详情页不复用通用客户预览页

选择：

- `business_card` 在客户详情页走独立名片页结构，不再和 `service_offer` 共用通用销售页首屏和动作网格。
- 电子名片详情页固定突出“人”：圆形头像、姓名、身份、公司/门店、服务范围、电话/微信。
- 名片详情页首屏下直接放四个圆形转化动作：电话咨询、微信咨询、留下电话/微信、预约沟通。
- 后续内容区按名片逻辑组织为服务介绍、服务范围、联系与二维码。
- `service_offer` 继续使用服务销售页结构，突出服务价值、报价、流程和案例。

原因：

- 电子名片本质是“人和联系方式”的信任入口，不是普通资料详情页，也不是服务方案页。
- 用户收到或打开电子名片时，第一眼需要像一张完整名片，而不是看见资料预览、蓝色动作卡或普通客户页模块。
- 将名片详情页独立后，模板预览、微信分享封面和点进去的详情页才能保持一致。

### 决策：电子名片头像和二维码作为图片字段，不作为 URL 明细字段

选择：

- 电子名片编辑页不再把头像和二维码作为普通 URL 输入字段暴露给用户。
- 头像和二维码在编辑页直接显示图片预览；用户通过素材区上传图片后，明确点击“设头像 / 设二维码”。
- 二维码字段兼容常见命名，但推荐最终统一写入 `structuredData.qrCodeUrl`。
- 公司网址作为选填文本字段保留，详情页点击复制，不默认用小程序打开网页。
- 4 款电子名片模板必须在卡片封面和详情页上都有可感知差异，而不是只改模板名称。

原因：

- 用户上传头像和二维码时关心的是图片是否展示，不关心图片 URL。
- 二维码如果只作为普通图片素材保存，系统无法稳定判断哪张是二维码；提供“设二维码”能减少误判。
- 小程序打开外部网页受 web-view 域名限制，第一版复制网址更稳。
- 电子名片模板的价值是快速形成不同销售场景的信任表达，不能退化成同一页换标题。

### 决策：电子名片内容和风格分离

选择：

- 电子名片的姓名、身份、公司、电话、微信、邮箱、网址、头像、二维码是内容层。
- 4 款电子名片模板是风格层，可以在编辑页随时切换。
- 切换风格只更新展示模板元信息，不覆盖用户已填写内容。
- 电子名片详情页动作区按已填写联系方式动态生成，不硬塞预约沟通。
- 电子名片第一版的联系方式动作是电话、微信、邮箱、留资；预约沟通保留给服务方案。

原因：

- 用户真实使用路径是“先填好一张名片，再挑哪个风格更好看”，而不是每换一款模板就重新填写。
- 电子名片是个人联系入口，电话、微信、邮箱比预约更自然。
- 动作区按字段动态生成，可以避免用户没填邮箱时出现空按钮，也避免 4 个按钮硬挤。

### 决策：电子名片和服务方案先做模板库，不做自由装修器

选择：

- 电子名片和服务方案的创建入口改为先选模板，再生成可编辑资料卡。
- 模板配置集中在 `miniprogram/utils/sales-page-templates.js`，每个模板包含场景、名称、默认字段、模块顺序和缩略预览所需信息。
- 第一批固定 8 个模板：4 个电子名片、4 个服务方案。
- 模板按销售场景组织，不只按颜色或视觉皮肤组织。
- 客户页读取模板元信息渲染销售页结构，电子名片突出“人”，服务方案突出“服务价值”。
- 第一版不做拖拽装修器、不做复杂页面搭建器，继续复用原有编辑页和客户动作。
- 电子名片的模板预览、资料库名片卡、编辑页首屏和客户页首屏必须使用同一套“圆形头像 + 姓名 + 身份 + 公司/门店 + 服务范围 + 电话/微信”的视觉母版。
- 模板选择页先展示样板人物和样板联系方式；用户创建后，编辑页和客户页自动替换成用户自己的头像、姓名和联系方式。
- 微信聊天里的小程序分享卡片不是客户页 WXML，必须单独生成电子名片分享封面图；客户页分享时优先使用该封面图作为 `imageUrl`。

原因：

- 用户真正要的是“挑一个好看的销售页，改几句话，直接发”，而不是从空表单开始填写。
- 现有后端接口、客户动作、留资、预约和待联系链路已经够用，模板化主要解决前端表达和默认内容质量。
- 自由装修器短期复杂度高，容易把重点从成交表达转移到排版操作；先用场景模板能更快形成可用体验。
- 电子名片的首屏就是客户第一眼看到的销售卡片，模板预览、编辑体验和客户打开体验必须一致，否则用户会觉得模板没有真正生效。
- 微信只允许分享卡片控制标题、路径和封面图，不能直接复用客户页布局；不单独生成封面图就会退化成普通小程序卡片。

### 决策：电子名片和服务方案卡复用资料库与 SCRM 基座

选择：

- 新增 `business_card` 和 `service_offer` 两类 `UserNote.visibilityConfig.cardType`。
- 电子名片第一版面向个人顾问，从个人资料带入昵称、头像和电话；不做门店团队或企业品牌主页。
- 服务方案第一版面向非标准销售 / 服务销售，承接咨询、留资、预约沟通和站内留言。
- 两类资料默认复用 `CustomerAction -> LeadReminder`，进入现有经营看板、客户库和待联系，不另起一套 SCRM。
- 服务方案不使用商品 SKU、下单、接龙、支付、库存、核销和正式订单能力。
- 新类型先通过明确入口创建，不加入自动识别规则。

原因：

- 资料库和经营闭环基座已经具备客户动作、线索、消息和看板能力，重复建设会增加维护成本。
- 电子名片和服务方案的差异主要在前端展示和字段结构，客户跟进链路可以复用。
- 明确入口创建能避免普通笔记被误识别为服务销售，保持普通笔记低阻力。

### 决策：P1 收口优先打通现有页面上下文，不新增大工作台

选择：

- P1 阶段不再优先新建大型“资料迁移工作台”或新经营模块。
- 优先把现有资料库、展示页效果、客户库、待联系和订单页之间的跳转上下文接顺。
- 从效果页、客户库等页面跳转时，应携带来源、状态、搜索关键词等筛选条件，让用户落到“同一组人 / 同一条资料 / 同一来源”的处理视图。
- 展示页编辑保存时用分类默认值兜底标题、简介、分享标题和联系文案，减少半成品发布。

原因：

- 当前大闭环已经基本成立，用户主要需要少迷路、少重复筛选、少手填。
- 继续新增大页面会增加维护和理解成本，短期价值不如把现有路径磨顺。
- 小程序真机体验里，跨页面丢失上下文比少一个新模块更影响使用效率。

### 决策：普通笔记默认保持笔记器，不进入运营工作台

选择：

- `text_note` 且没有房源/商品候选、不是图片 OCR、不是小程序原房源的普通笔记，详情页默认只显示轻量笔记编辑。
- 普通笔记不因为 `draft/待整理` 状态在资料库里显示成“待整理”，而显示为“普通笔记”。
- 标签、专题、功能组、候选转换等运营能力默认收起，用户点击“扩展为可运营资料”后才展开。
- 房源、商品、图片资料、小程序卡片和有候选类型的文本仍按原业务工作台或确认卡片处理。

原因：

- 普通笔记的核心是快速记录，不应该让用户一进入详情就面对房源/商品式复杂工作台。
- “待整理”状态对业务资料有意义，但对已经保存好的普通笔记会造成误解。
- 运营能力是资料助手的差异化能力，但应该由用户主动展开，不能打断普通记录。

### 决策：空头像不再强行写入，统一由前端兜底

### 决策：OCR 第一版作为图片输入适配器，不直接生成业务结果

选择：

- OCR 采用两段式：`POST /api/ocr/images` 先保存图片资料，用户在资料编辑页主动点“识别图片文字”后再调用 `POST /api/ocr/notes/{note_id}/recognize`。
- 识别成功后才进入 `ContentObject.sourceType=image_ocr -> content-to-note -> UserNote`，并在原资料上更新为房源/团购/文本等 typed card。
- 兼容保留旧 `POST /api/ocr/image-to-note`，但小程序默认不再上传即识别。
- OCR 结果保存到 `visibilityConfig.structuredData.ocr`，资料来源标记为 `sourceType=ocr`，标签包含 `图片识别`，状态区分 `pending/done/empty/not_configured`。
- OCR 引擎做成可替换 provider：`auto / paddle / tesseract / mock`。
- 当前生产优先启用 PaddleOCR，依赖固定为 `paddlepaddle==3.3.1`、`paddleocr==2.10.0`，并通过 `OCR_PROVIDER=paddle` 启用。
- Docker 内使用 headless OpenCV，避免服务端为了 OCR 引入完整桌面图形库。
- OCR 未配置或识别为空时，仍保存图片资料，允许用户手动补正文和字段。

原因：

- OCR 是资料输入能力，不应绕开已有 typed card、识别解释和中置信人工确认机制。
- 用户需求可能只是“保存这张图片”，不一定立刻需要文字；默认自动 OCR 会增加等待、成本和误识别风险。
- PaddleOCR 依赖较重，必须固定版本和容器运行库；后续升级要重新做生产镜像验证。
- 后续如接腾讯云 OCR，也只替换 provider，不改变小程序和 `content-to-note` 主链路。

### 决策：中置信类型确认由后端统一执行

选择：

- `typeSuggestions` 只负责提示候选类型和解释信号，不直接代表资料已经进入对应业务模板。
- 用户点击确认房源 / 商品 / 普通笔记时，统一调用后端 `POST /api/notes/{note_id}/confirm-type`。
- 后端负责重建 `cardType/cardState/structuredData/conversionConfig`，并清空 `typeSuggestions`。
- 前端不得在页面里自行拼完整类型转换结构作为主链路；只能展示候选和调用确认接口。
- 确认类型时必须保留 `structuredData.miniapp`、原始正文和图片，避免小程序卡片转房源后丢失原小程序入口。
- 识别结果必须保存 `recognitionExplanation`，包含候选类型、分数、命中字段、可读信号和人工确认记录。

原因：

- 类型转换会影响客户页动作、轻 SCRM、商品接龙和原小程序跳转入口，不能由多个前端页面各自拼配置。
- 可解释数据能让测试和用户理解系统为什么给出“可能是房源 / 商品”的建议。
- 人工确认是中置信资料进入业务工作台的正式边界，应该有持久化记录。

- 企业微信 `msgtype=weapp` 进入统一 `ContentObject -> content-to-note -> UserNote` 链路。
- 小程序卡片保存为 `sourceType=miniapp`、`systemCategory=小程序`，结构化保留 `appid`、`username`、`pagePath`、`houseCode`、`cityId`、`source` 等字段。
- 页面正文只展示短信息：小程序标题、来源、appid、房源编码；完整 pagepath 只保存在结构化字段，不直接展示。
- 贝壳小程序卡片如果只有标题/来源/pagepath，只给“可能是房源信息”的中置信提示，不自动生成完整房源工作台。
- `miniapp_card` 不从正文提取手机号，避免 pagepath 或 share_time 的长数字被误判为电话。
- 当用户确认或系统转换为房源字段卡时，必须保留 `structuredData.miniapp`；我们的房源块显示“查看贝壳原房源”，客户点击跳转贝壳小程序原页面。
- 贝壳原页面承载详细价格/图片/户型，我们的小程序承载轻 SCRM、留资、预约、微信咨询、客户跟进等能力。
- 可以根据 `cityId + houseCode` 生成贝壳网页候选 URL 并存入 `sourceUrl` / `structuredData.miniapp.webUrl`，但只作为备用链接，不承诺可爬取详情。

原因：

- 企业微信转发小程序时通常只下发卡片外壳，不包含贝壳详情页里的价格、户型、图片、地址和坐标。
- 如果强行高置信生成房源卡，会让用户误以为系统已经拿到了不存在的字段。
- pagepath 很长且包含大量数字，直接展示会影响前端可读性，也会污染手机号识别。
- 跳转原小程序比爬虫更稳定、更合规，也符合用户对贝壳原房源详情的预期。
- 贝壳网页会触发验证码/风控，URL 能存储和人工打开，不等于服务器能稳定解析图片、价格和户型。

### 决策：房源地址解析要使用标题小区和最近城市记忆

选择：

- 房源识别时，标题里的小区名可以作为 `community` 信号参与高置信判断。
- 客户页/编辑页地图解析时，如果地址不含城市，优先使用最近一次房源城市记忆补全，例如 `长沙市 + 小区名/地址`。
- 最近城市只作为地图匹配辅助，不覆盖用户实际填写的地址字段。

原因：

- 房产中介常把小区名写在标题里，正文只写户型、价格、位置等字段。
- 同名小区跨城市很常见，不补城市会导致腾讯地图匹配到错误城市或返回不稳定结果。
- 记忆最近城市比强制用户每次填写完整省市更轻。

### 决策：客户页动作使用客户语言，不暴露“留资”等内部术语

选择：

- `我要留资` 改为 `留下电话/微信`。
- `私聊咨询` 改为 `微信咨询`。
- `联系咨询` 改为 `电话咨询`。
- 预约看房使用页面内表单，默认今天，也支持明天和精确到分钟的时间选择。

原因：

- “留资”是运营/CRM 术语，客户不一定理解。
- 客户只关心自己要留下什么、怎么联系、什么时候看房。
- 预约看房如果只给今天/明天/周末，不够贴近日常约看房的具体时间需求。

### 决策：工作台主动作使用“发给好友”，保存和手机号记忆走轻量本地体验

选择：

- 房源/团购资料的主动作文案从“生成推广/生成海报”收敛为“转发给好友”，并优先接入微信原生分享按钮，减少二次点击。
- 编辑页保留底部保存，同时新增小尺寸浅绿色悬浮保存，默认右侧吸附；用户拖动后按左右距离吸附到最近侧。

- 客户页预览视为真实客户可见页面，必须展示完整房源图片；微信分享卡片仍只使用封面图。
- 地图定位优先提供导航 App 入口，不支持时回退微信内置地图和复制地址。

原因：

- 用户想要的是“整理完可以直接发出去”，不是理解后台生成流程。
- 本地手机号记忆能快速减少重复输入，不需要现在引入复杂用户资料系统。
- 微信好友/朋友圈分享卡片无法承载多图，但客户页本身可以展示完整图片信息。

- 客户页正文中不再放大面积分享按钮，分享按钮固定在右侧靠下，避免和内容动作混淆。

### 决策：客户页链接是主分享路径，分享图只是辅助素材

选择：

- 房源/团购真正承接转化的是客户页链接，用于微信好友、微信群和朋友圈分享。
- “海报”不再作为主路径表达，统一弱化为“分享图”。
- 资料详情顶部主动作保留分享文案、客户页预览、转发给好友；“保存分享图”放在弱入口。
- 分享图页面提供保存到相册和复制文案，用于朋友圈图片、群图、私聊图片等辅助传播。

原因：

- 客户页链接能承接图片、视频、地图、留联系方式、预约和咨询，是完整闭环。
- 静态海报无法直接完成留资、预约和地图导航，不应和客户页链接争主路径。
- “朋友圈海报”容易让用户误解必须先生成海报才能分享到朋友圈。

### 决策：客户页地图不展示经纬度数字，默认地址通过后端解析成地图点

选择：

- 客户页只展示地图结果和“小房子”位置标记，不展示 `latitude/longitude` 数字。
- 房源有默认地址但没有经纬度时，前端先调用后端地理编码接口解析默认地址。
- 地图 Key 只配置在后端 `TENCENT_MAP_KEY`，小程序前端不保存、不提交地图服务 Key。
- 解析成功后，编辑页会把 `structuredData.mapLocation` 保存回资料卡；客户页则可直接用解析结果展示地图。
- 解析失败或未配置 Key 时，继续保留微信原生地图选点作为兜底。

原因：

- 对客户来说，经纬度是技术信息，不是业务信息，展示会增加理解负担。
- 微信小程序 `<map>` 组件必须依赖坐标，不能只用文字地址直接画出准确地图点。
- 用后端解析默认地址，可以让“默认地址”和“地图位置”尽量天然一致，同时避免把地图 Key 泄露到前端。

### 决策：房源资料页按 4 态组织，不再堆成单页长表单

选择：

原因：

- 房源资料必须先完成字段确认，再进入整理审核和生成管理。
- 分态后更容易测试每一步是否正确，也方便后续替换生成态为真正的房源推广页 / 海报 / 文案 Skill。

原因：

- 先隐藏入口、强制新链路，可以集中测试房源/团购资料卡、`conversionConfig` 和生成态。

原因：

- 房源和团购不是普通文章，它们是强结构业务信息，必须进入字段表单和场景行为。
- 如果所有资料都按普通笔记展示，用户后续编辑、搜索、生成推广内容都会变得混乱。
- 用 `UserNote` 兼容扩展可以快速验证产品形态，避免过早做大迁移。

### 决策：房源/团购转化能力用 conversionConfig 单独保存

- `structuredData` 只保存房源/商品本体字段，例如小区、价格、户型、商品名、规格、取货地点。

原因：

- “联系电话是否展示”和“是否开启轻 SCRM”是页面行为和转化能力，不是资料内容本身。
- 分离后生成态可以稳定读取配置，用户编辑字段时也不会误伤转化开关。

### 决策：资料库正式持久化以 PostgreSQL 仓储为准，JSON 仅作为开发兜底

选择：

- 资源卡片、分类标签、浏览记录、接龙名单、导入批次等正式数据继续走后端仓储接口。

- `backend/mock/runtime-state.json` 只作为本地开发兜底和 mock 演示数据，不作为正式资料库数据底座。

原因：

- 用户资料库需要跨设备、长期保存，不能依赖本地运行态 JSON。
- 当前后端已有 `PostgresRepository` 和索引结构，先收口使用方式，比重新设计存储层更稳。

### 决策：上传到后端的图片和视频必须先压缩再入库

选择：

- 手动上传和企业微信媒体转存都会先进入同一套媒体处理服务。
- 图片限制最大边长并转为 WebP 压缩版。
- 视频通过 ffmpeg 转为 H.264/AAC MP4，限制宽度和码率质量。
- v0.1 默认不保留原始大文件，资料库只保存可展示的压缩文件 URL。
- 上传接口返回 `originalSize`、`storedSize` 和 `compressed`，便于验收压缩是否生效。

原因：

- 小程序资料库会高频上传图片和视频，原文件直接入库会快速占满服务器磁盘，也会拖慢页面加载。
- 展示型资源页优先需要稳定、够清晰、加载快的文件，而不是原图/原视频归档。

原因：

- 用户希望用 Pinia 思路管理资源状态；在原生小程序里应保留这个架构意图，但不能强行引入不匹配的 Vue 生态包。
- 原始 URL 和本地缓存展示路径分离，可以避免保存资源时把手机本地路径写回后端。

选择：

- 后端拒绝同一 `userId` 对同一 `cardId` 重复创建 active 接龙。
- 发布者管理页将未跟进接龙单独高亮为“待跟进新线索”。

原因：

- 接龙本质是留资线索，不是可无限重复提交的评论。
- 重复提交会污染发布者待跟进列表，也会让客户不知道自己是否已经提交成功。

### 决策：客户视角资源页不展示统计和接龙名单

选择：

- 普通客户打开资源页时，不展示已接龙名单。
- 发布者打开资源页时，继续展示统计卡片、访问详情入口和完整接龙名单。

原因：

- 分享出去的资源页首先是客户浏览和提交接龙的正式页面，不应混入团长管理数据。
- 浏览统计、接龙名单、电话和地址属于发布者跟进线索，不属于普通查看用户的信息范围。

### 决策：资源编辑页必须支持发布后继续补素材

选择：

- 新增素材继续写入卡片结构化 `media`，再通过“保存修改”持久化。
- 首张图片可自动成为封面，其他图片/视频默认进入详情展示区。

原因：

- 资源是长期维护对象，发布后补图、补视频是高频动作。
- 如果要求用户回到创建流程，会割裂资源维护体验，也容易让用户误解为需要重新创建资源。

原因：

原因：

- 企业微信办公场景需要稳定、可解释、低误判的入口。

- 用户长期目标是“资料整理助手”的个人笔记库，而不是只生成一次性资源卡片。
- 现有小程序页面仍依赖 `Card`，直接替换会扩大风险。
- 先双写 `UserNote` 和 `Card`，可以在不打断旧链路的情况下启动 P0 第二阶段。

### 决策：小程序“我的笔记”先做基础管理，不抢占 tabBar

选择：

- “我的笔记”先作为普通页面，通过“我的”页和资源库快捷入口进入。
- 不新增 tabBar 项，不替换现有“资源库”。
- 第一版只覆盖列表、搜索、详情、编辑和删除。

原因：

- 当前 tabBar 已承载首页、资源库、添加、访问记录、我的；贸然替换会影响既有资源卡片链路。
- 笔记库刚上线，需要先验证数据和编辑闭环，再决定是否升级为一级 tab。

### 决策：会话内容存档作为独立 wecom-archive-core，不复用客服 sync_msg 配置

选择：

- 企业微信会话内容存档使用独立配置项：`WECOM_ARCHIVE_SECRET`、`WECOM_ARCHIVE_PRIVATE_KEY_PATH`、`WECOM_ARCHIVE_PUBLIC_KEY_PATH`。
- 会话内容存档的原始消息单独落到 `wecom_archive_messages`，拉取游标单独落到 `wecom_archive_cursors`。
- 当前企业微信客服 `sync_msg` 继续保留作为过渡入口；会话内容存档接入后不直接替换客服入口。
- 会话内容存档原始消息查询接口必须 admin token 保护。

原因：

- 会话内容存档属于合规归档基座，权限、Secret、RSA 密钥、SDK、游标和审计口径都不同于微信客服 `sync_msg`。
- 两条入口后续可以共用 `ContentObject -> content-to-note -> UserNote`，但不应混用入口配置和存储游标。
- 原始会话内容敏感度高，不能暴露给普通小程序用户接口。

### 决策：会话存档 P0 拆成“拉取”和“处理”两步

选择：

- `POST /api/wecom/archive/pull` 只负责调用官方 SDK 拉取、解密并保存原始归档消息。
- `POST /api/wecom/archive/process` 只负责把已解密消息转换为 `ContentObject -> content-to-note -> UserNote`。
- 归档消息上保存 `generatedNoteId`、`generatedCardId`、`processedAt`、`processError`，确保处理幂等且可排查。

原因：

- 企业微信 SDK、可信 IP、Secret、RSA 解密和内容整理是两类问题，拆开后人工验收更容易定位失败环节。
- 后续后台任务可以先定时 pull，再独立重试 process，不会因为内容整理失败阻塞归档游标推进。
- 原始合规存档必须先可靠落库，用户笔记是业务产物，二者生命周期不同。

### 决策：会话存档自动化先用轻量 worker，身份未绑定前仍进入新导入

选择：

- 后端启动轻量 `wecom-archive-worker`，生产每 60 秒执行一次 `pull -> process`。
- worker 只负责自动拉取、解密、落库和生成 `UserNote`，不负责用户身份归属判断。
- `identity-core` 未完成前，生成内容仍以 `ownerUserId=unclaimed` 进入小程序“新导入资料”，由用户认领。

原因：

- 自动拉取和身份绑定是两类问题，先让消息自动进入系统，可以减少人工操作。
- 直接把企业微信外部联系人消息归到某个小程序用户，在没有绑定关系时风险较高。
- “新导入资料”是过渡入口，上线前可弱化为异常/未归属入口。

### 决策：微信笔记优先按 note 消息天然聚合，普通多消息再按 5 秒窗口聚合

选择：

- 企业微信会话存档 `msgType=note` 视为一个天然聚合内容，解析 `info.items` 后生成一条 `UserNote`。
- 普通连续消息按同一会话、同一发送人、相邻消息不超过 5 秒聚合为一条业务笔记。
- 原始归档消息仍逐条保存；合并只发生在 `ContentObject -> UserNote` 业务产物阶段。

原因：

- 微信笔记本身已经包含文本、位置和多媒体结构，不能再拆成多条新导入。
- 用户真实发送房产资料时，经常是多图加文字，5 秒窗口能减少碎片化。
- 合规存档和业务整理生命周期不同，原始消息逐条保存更利于审计和追溯。

### 决策：会话存档图片必须服务端下载转存，不依赖小程序本地缓存

选择：

- 企业微信会话存档中的图片、视频、文件先保存 `sdkfileid`、`md5sum`、`filesize` 等媒体引用。
- 正式展示前必须由后端通过官方 SDK `GetMediaData` 下载媒体本体。
- 下载后的媒体进入后端媒体处理链路，图片转 WebP，视频后续按 H.264/AAC 处理，再保存为小程序可访问的 URL。
- `UserNote.media.url` 只保存服务端持久地址；小程序本地缓存只用于显示加速，不作为业务数据来源。

原因：

- 会话存档返回的 `sdkfileid` 不是可直接展示的图片 URL。
- 如果不转存，笔记只能知道“这里有图片”，但小程序无法预览图片本体。
- 小程序本地缓存会随设备和缓存清理变化，不能作为资料库长期存储。

### 决策：真实企业微信联调用生产可行，但后续需要拆 staging

选择：

- 当前 P0 阶段，为了验证企业微信会话内容存档、小程序合法域名和公网 HTTPS，允许在生产环境边开发边测试。
- 后续进入更稳定的 P1/P2 前，应增加独立测试环境，例如 `test.teambuy.lifelove.top`、企业微信测试应用和小程序测试 request 域名。
- 生产环境只保留已经通过本地测试和小范围验证的改动。

原因：

- 企业微信会话存档、小程序真机和体验版都依赖公网可访问域名，本地环境无法完整模拟。
- 但长期直接在生产试错风险较高，尤其是自动 worker、媒体下载、通知和身份绑定这类会影响真实数据的能力。

### 决策：处理完成后的企业微信回复不走会话存档通道

选择：

- 会话内容存档是拉取与合规归档通道，不负责给微信用户回消息。
- “已整理完成”这类通知后续应走单独通知通道：
  - 企业微信应用消息：优先通知内部成员。
  - 微信客服消息：在客服通道权限打通后通知外部联系人。
  - 小程序订阅消息：在用户绑定小程序后通知用户。
- 通知失败不能影响笔记入库，只记录失败并允许后台重试。

原因：

- 会话存档解决“拿到会话内容”，不等于有“回复用户”的能力。
- 入口、归档、业务处理、通知应保持解耦，避免一个通知通道失败拖垮导入主链路。

### 决策：identity-core 第一版采用“认领后绑定”策略

选择：

- 新增 `WecomIdentityBinding`，记录企业微信来源身份与小程序用户的绑定关系。
- 第一版绑定键为 `sourceType=wecom_external_user` + `externalUserId`。
- 用户第一次在小程序认领导入后，系统保存绑定。
- 后续同一个企业微信来源的新导入自动归属到该小程序用户，`ImportBatch` 直接标记为 `claimed`，`UserNote.ownerUserId` 指向该用户。
- 暂不引入 unionid、正式微信登录 code 换 openid、企业微信成员/客户复杂绑定流程。

原因：

- 当前 P0 最关键的是让用户感知“这是我的资料助手”，减少每条资料都手动认领。
- 正式微信登录和企业微信客户身份联动还未完全打通，直接做复杂绑定容易扩大风险。
- “认领后绑定”可以用现有真实导入链路快速闭环，并为后续正式身份体系保留迁移空间。

### 决策：文章 URL 默认轻收藏，明确整理才进入深度笔记

选择：

- 用户在企业微信或后续入口发送普通文章 URL 时，默认生成“文章收藏卡”，不是通用笔记模板。
- 轻收藏第一层只保留原始链接、标题、封面、来源、收藏时间、基础分类、基础标签和一句话摘要。
- 用户点击轻收藏卡片时，默认优先打开原文；公众号文章优先尝试小程序能力打开，普通网页按微信限制降级复制链接。
- 用户明确发送 `整理链接`、`文章总结`、`整理文章`、`做笔记` 等指令时，才走 `content-to-note` 深度整理。
- 小程序轻收藏详情页先展示文章卡片和基础字段，再提供“整理为笔记”动作，用户需要时再把收藏升级为深度笔记。
- 后续企业微信快捷菜单里的“整理链接/整理笔记”属于明确深度整理入口，不按轻收藏处理。

原因：

- 用户看到好文章时，很多时候第一需求是先收藏，过早做复杂解析会让入口变重。
- 轻收藏的核心体验应接近微信公众号文章卡片：先能识别、打开和回看原文，再决定是否深度整理。
- “轻收藏 -> 用户需要再深度整理”的路径更符合资料助手习惯，也能降低模型调用和解析失败成本。
- 企业微信快捷指令仍保持确定性，避免用户明确要整理时被误判为普通收藏。

### 决策：资料组织采用强标签、弱分类、专题聚合

选择：

- 不做强制三级分类。
- `sourceType` 对齐微信收藏基础类型：笔记、链接、图片与视频、语音、位置、聊天记录、文件、小程序。
- `systemCategory` 作为系统弱分类，只用于基础展示和筛选。
- `tags` 作为核心组织结构，用于搜索、筛选、召回和后续 AI 理解。
- `topics` 作为用户行为结构，用来承载场景集合，替代多级文件夹。
- 标签按规则标签、轻模型标签、大模型深度标签三层逐步增强。

原因：

- 用户随手收藏时不适合先思考三级目录，强制分类会提高保存成本。
- 标签更适合多维交叉筛选，也更适合后续模型理解。
- 专题比分类树更贴近真实使用场景，例如亲子露营、某小区团购、学习资料合集。

### 决策：房源/团购前台体验收敛为两层工作台

选择：

- 不再把“收藏、编辑、整理、生成”四态流程作为用户主 UI。
- 四态保留为后台数据生命周期和调试语义，前台只呈现：
  - 自动生成的房源/团购工作台。
  - 板块级编辑、隐藏、恢复和功能组配置。
- 高置信房源/团购直接展示工作台，并默认带对应功能组。
- 中置信资料保留普通卡片，只给轻提示让用户确认“房源 / 团购 / 普通笔记”。
- 低置信资料直接当普通笔记，不打扰用户。

原因：

- 用户转发资料后想看到结果，不想学习“整理流程”。
- 房源/团购真正有吸引力的是能直接拿去分享、留资、预约、接龙和跟进，不是字段整理过程本身。
- 置信度机制可以把自动化做得更稳：高置信减少操作，中置信轻确认，低置信避免误判。

### 决策：专题是轻文件夹，资料库不做传统文件夹树

选择：

- 资料库默认最新上传/导入在前。
- 每个资料卡片必须展示上传时间。
- 搜索范围包括标题、摘要、正文、字段、标签、专题、上传日期和归一化日期数字。
- 标签继续做多维搜索和筛选。
- 专题作为轻文件夹使用，一条资料可进入多个专题。
- 保留“未整理”入口承接新进资料。

原因：

- 用户早期上手不能被分拣压力拖住。
- 多级文件夹会强迫用户先决定唯一归属，但微信资料常常同时属于小区、客户、活动、来源等多个维度。
- 标签和专题组合更适合后续模糊搜索与 AI 归纳。

### 决策：字段编辑采用快捷项 + 输入框，不做强制下拉

选择：

- 房源/团购字段仍保留输入框作为主编辑方式。
- 户型、水电物业、服务费、自提/配送、库存备注等高频字段提供快捷项。
- 用户点快捷项可快速填入，仍可继续手动修改。
- 图片删除只从当前资料卡展示中移除，不删除服务端归档素材。

原因：

- 房源和团购字段高度非标，强下拉会限制真实表达。
- 纯输入又太重，尤其是户型、服务费、自提方式这类高频重复字段。
- 快捷项 + 输入框能降低操作成本，同时保留灵活性。
- 当前资料编辑不应误删原始归档素材，媒体删除先限定为资料卡展示层操作。

### 决策：海报做视觉传播，客户页做行动承接

选择：

- 海报页定位为朋友圈、社群、私聊里的视觉卡片和发群文案入口。
- 客户页定位为真正分享给微信好友 / 群的承接页，负责联系咨询、留资、预约、接龙和地图定位。
- 海报页第一版不做深色重设计，采用浅色背景和可选强调色，保证文字可读。
- 房源地图定位通过编辑页手动选点保存经纬度，客户页再调用腾讯地图打开。
- 没有经纬度时不伪造定位，只复制地址让用户自行搜索。

原因：

- 海报和客户页如果都承担完整转化，会让产品关系混乱。
- 海报更适合“看一眼有兴趣”，客户页更适合“点进去完成动作”。
- 地址文本无法稳定转换成准确经纬度，第一版让发布者选点更可靠，也避免引入地图服务密钥。

### 决策：小程序房源允许用户补素材，不强依赖第三方详情抓取

选择：

- 贝壳等第三方小程序房源，第一版优先保存原小程序 appid、path、标题、房源编码和可推导网页 URL。
- 不把第三方页面抓图、抓价格、抓完整字段作为主链路依赖。
- 资料详情必须允许用户自行上传图片和视频。
- 用户补传素材后，资料卡和客户页预览直接使用这些素材；首张图片可作为封面。

原因：

- 第三方小程序内容和网页内容常受登录、风控、反爬、跳转和动态渲染限制，不能保证稳定抓到图片、价格和详情。
- 用户真实操作里“先存住原小程序房源，再补图补字段”更可靠，也更符合资料整理助手的定位。
- 这样既保留原房源入口，又能继续使用轻 CRM、留资、预约和客户页分享能力。

### 决策：客户动作优先在资料工作台内按 noteId 查看

选择：

- `customer-action-plugin` 的动作记录统一落 `customer_actions`，但发布者日常查看入口放在对应资料详情的“轻 SCRM”板块。
- 房源资料详情提供“查看客户动作 / 查看线索”按钮，进入 note 级明细页，按当前 noteId 展示留资、预约、后续咨询动作和已投影线索。
- 全局线索列表继续保留，适合跨资料排待办；单套房源的跟进优先从房源工作台进入。
- 红点提醒绑定待跟进线索，而不是永久绑定历史动作；处理完线索后红点应消失。

原因：

- 房产中介的工作习惯是围绕某套房源查看客户反馈，不应要求用户离开房源详情去全局列表里搜索。
- noteId 是客户页动作的天然归属边界，避免不同资料、不同房源的动作混在一起。
- 红点如果只表示“曾经有动作”会变成噪音；绑定待处理状态更接近微信未读的心智。

### 决策：房源状态属于房源工作台，不属于标题重写

选择：

- 房源标题保持用户原始热点表达，不自动拆分或重写。
- 房源是否继续推广使用结构化 `propertyStatus` 表达：`active` / `rented` / `paused`。
- 已租 / 暂停推广状态会影响客户页转化动作：不再继续收电话、留资、预约、私聊等新动作。
- 我的笔记卡片和资料详情都展示状态，让发布者能快速知道当前房源是否仍在推广。

原因：

- 用户会刻意把价格、地铁口、户型、亮点写进标题，标题本身就是传播信息，不应被系统主动拆散。
- 房源生命周期需要影响客户动作入口，不能只靠标题或备注表达。
- 状态作为结构化字段，后续可继续用于筛选、批量暂停推广和房源下架提醒。

### 决策：拨号后顺手记录跟进

选择：

- 客户动作页、全局线索页、线索详情页的拨号入口保持一致。
- 拨号成功后提示是否标记已联系。
- 用户确认后更新 `lead_reminders.status=contacted`，并写入“已电话联系客户”的跟进记录。

原因：

- 房产跟进里电话是最高频动作，拨完电话后顺手记状态，比要求用户返回再点“标记已联系”更自然。
- 这能让“待跟进 N”和卡片红点更快回到干净状态。

### 决策：企业微信归档解析器采用注册式 parser

选择：

- 企业微信归档消息不继续堆在 `ContentObjectAdapter` 的大分支里。
- 按 `msgtype` 注册 parser：`text`、`note`、`weapp`、`chatrecord` 等分别处理。
- `chatrecord` 作为独立 parser 先服务商品/团购聊天记录，提取文字并过滤媒体占位。
- parser 只负责把来源消息转成 `ContentObject`；是否生成房源卡、商品卡，仍交给 `content-to-note` 的类型识别。

原因：

- 后续企业微信会继续出现更多消息形态，注册式 parser 更容易扩展。
- 商品团购场景常来自群聊天记录转发，必须先把 `chatrecord.item[]` 拆成正文，后续 SKU/接龙才有基础。
- parser hint 可以降低强依赖固定字段的风险，但不绕过统一内容生成链路。

### 决策：商品展示是基座，团购接龙只是可选模块

选择：

- 商品工作台按“商品信息 / 图片与视频 / 规格与价格 / 自提配送 / 团购接龙”分区。
- 商品信息只放标题和简介；价格统一归到规格与价格。
- 自提、配送、取货地点、联系方式、截止时间归到履约信息。
- 团购接龙只保留开关、接龙名单入口和客户提交能力，不再混进商品基础字段。
- 客户页默认先展示商品；只有开启 `enableGroupRelay` 后才出现 SKU 选择、数量和提交接龙。

原因：

- 商品展示可以独立存在，不应该因为类型名叫 `groupbuy_product` 就默认让用户理解为团购。
- SKU 和履约是电商基座能力；接龙是转化玩法。
- 这个边界后续方便扩展普通商品、团购、预订、咨询等不同转化方式。

### 决策：商品下单意向必须持久化，接龙只是名单展示方式

选择：

- 商品客户预览页默认展示 SKU 点选、数量和下单按钮，不受 `enableGroupRelay` 开关影响。
- `enableGroupRelay=false` 时，客户提交写入 `customer_actions.order-intent`。
- `enableGroupRelay=true` 时，客户提交写入 `customer_actions.relay-intent`。
- `order-intent` 和 `relay-intent` 都不投影到 `lead_reminders`，不进入房产 SCRM。
- 团长统一从商品资料详情和我的笔记卡片进入名单页；不开接龙叫“商品下单名单”，开接龙叫“商品接龙名单”。
- 客户再次进入预览页，应看到自己已经提交的 SKU 和数量状态。

原因：

- “下单”是商品基座能力，不能因为没有开启接龙就只做前端本地提示。
- 接龙是团购玩法和名单文案，不应决定商品意向是否落库。
- 统一落 `customer_actions` 可以保持 note 级归属、红点、复制汇总和团长查看入口一致。

### 决策：轻订单中心先复用 customer_actions，不引入正式订单域

选择：

- 第一版商品下单仍写 `customer_actions.order-intent / relay-intent`。
- 订单中心是读取和整理这些客户动作的轻量视图，不新增 `orders` 表。
- 订单状态只做 `submitted / contacted / completed / cancelled`。
- 地址和电话作为商品下单必填字段；微信号、收货人、备注可选。
- 轻订单不进入 `lead_reminders`，不进入房产 SCRM。

原因：

- 当前业务重点是“商品展示 + 接收意向 + 商家跟进”，不是支付结算。
- 复用 `customer_actions` 可以保持 note 归属、客户身份隔离、红点和名单能力一致。
- 后续若要支付、退款、分账、核销，应另起 `order-core`，避免把正式交易逻辑塞进客户动作。

### 决策：站内消息采用异步文本留言，不做实时 IM

选择：

- 新增 `message_threads` 和 `message_records`。
- 会话绑定 `noteId`，可选绑定 `orderActionId`。
- 第一版只做文本、未读、已读；页面进入加载，发送后刷新。
- 商品页、房源页、订单详情、资料详情和我的页都提供消息入口。

原因：

- 当前目标是让买家和商家在小程序内留下可追溯沟通记录，不要求双方实时在线。
- 异步留言比 WebSocket 实时 IM 更轻，适合第一版快速闭环。
- 绑定 note/order 后，后续可以自然扩展到商品咨询、房源咨询、订单跟进等多个场景。

### 决策：前端消息入口必须走 message-plugin

选择：

- 新场景打开站内会话统一调用 `messagePlugin.openMessageThread({ noteId, orderActionId, buyerUserId })`。
- 打开消息中心统一调用 `messagePlugin.openMessageCenter()`。
- 页面可视入口统一优先使用 `components/message-entry`。
- 业务页面不再直接手写 `api.createMessageThread` 和 `/pages/message-thread/index` 跳转。

原因：

- 站内消息是跨房源、商品、订单和后续场景的基座能力，不属于某一个场景页面。
- 统一组件能集中处理未读数、文案、样式和后续权限提示。
- 统一方法能避免后续多个页面重复出现会话创建、买家身份和订单绑定逻辑。

### 决策：企业微信纯图片导入只保存图片，OCR 必须由用户二次触发

选择：

- 企业微信客服同步和会话归档里，如果导入内容只有图片、没有用户正文和链接，并且图片已经转存成功，则生成 `image_ocr` 图片资料。
- 初始状态为 `structuredData.ocr.status=pending`，正文提示用户可以手动补充，也可以点击识别图片文字。
- OCR 识别仍走小程序编辑页的 `POST /api/ocr/notes/{note_id}/recognize`，不在导入阶段自动识别。
- 图文混合内容继续走 `content-to-note`；媒体下载失败时继续走媒体重试，不生成可识别图片资料。

原因：

- 用户真实需求分两类：有些图片只是素材，有些截图才需要文字识别。
- 导入阶段自动 OCR 会增加耗时和失败面，也会把“保存图片”和“识别文字”两个动作混在一起。
- 统一两段式后，小程序上传、企业微信客服图片、会话归档图片都能复用同一个编辑页确认入口。

### 决策：用户身份唯一锚点是小程序微信 openid

选择：

- 小程序微信 `openid` 是多途径来源进入系统后的唯一用户身份锚点。
- `userId` 只作为后端内部主键，业务归属必须能追溯到对应 `openid`。
- 企业微信 `external_userid` 不作为用户身份，只作为来源标识，系统内部映射到 `ownerOpenid/ownerUserId`。
- 第一次认领导入资料时写入内部映射；后续同一企业微信来源自动进入该 `openid` 对应用户的资料库。
- P0 不提供用户侧绑定管理、解绑或改绑功能；测试期误认领走后台数据修正。

原因：

- 企业微信身份、小程序身份、手动录入和 OCR 来源不是同一个身份体系，不能互相直接等同。
- `openid` 是当前小程序用户身份最稳定、最明确的唯一标识。
- 不做解绑/改绑 UI 可以减少 P0 复杂度和误操作风险，先保证导入归属闭环。

### 决策：展示页 V1 固定四套标准模板，编辑入口优先低操作

选择：

- 展示页构建器 V1 固定四套模板：精选橱窗、朋友圈长页、清单目录、品牌名片。
- 新建展示页默认走“模板 -> 分类 -> 默认全选该分类资料”的低操作流程，不要求用户逐条从空白页配置。
- 默认优先选择房产分类；若没有房产资料，则选择有资料的分类或全部。
- 第一、第二模板的 banner 默认取当前已选资料第一张封面图；名称、简介、分享标题、电话、微信尽量从模板、账号和资料字段自动生成。
- 展示页选资料复用 `utils/note-display.js`，不要再单独复制一套笔记类型、标签和摘要展示逻辑。

原因：

- 展示页主要给客户看，创建动作应该像“选模板并确认资料”，而不是让用户从零搭建页面。
- 固定四套模板更利于形成稳定交付标准，也便于后续验收和视觉打磨。
- 复用笔记展示逻辑可以避免“我的笔记”和“展示页选资料”对同一条资料显示出不同类型、标签或摘要。

### 决策：展示页模板文案必须跟随分类/资料类型

选择：

- 展示页保存当前选择分类到 `displayConfig.activeCategory`。
- 客户展示页模板文案优先按 `activeCategory` 判断，其次按展示资料的 `cardType` 兜底判断。
- 房产分类可以展示“房源 / 好房 / 成交案例”；商品或团购分类必须展示“好物 / 团购 / 成交订单”等商品口径；泛资料分类使用“资料”口径。
- 展示页列表必须显性展示“编辑 / 预览 / 删除”，发布态额外展示“发给客户”。

原因：

- 展示页模板是通用能力，不只服务房源；把房源文案写死会让商品/团购页显得不可信。
- 保存分类上下文比只看模板 ID 更稳定，因为同一个模板可以服务不同业务类型。
- 编辑入口不能只依赖整行点击，否则草稿和下架页会被用户误解为“只有预览”。

### 决策：经营看板作为独立 SCRM 看板收口

选择：

- 经营看板放在“访客线索/经营看板”独立入口，不再铺在“我的”页首页。
- 第一版固定四个视图：展示页效果、访客详情、笔记数据、客户资料。
- 展示给用户的是打开、访客、看资料、咨询、下单、接龙、跟进等业务语言，不展示“行为强度分层”等内部判断概念。
- 面向资料主人的经营看板不脱敏手机号和微信；手机号必须支持外呼，微信必须支持复制。
- 测试数据可以写入生产库做真机验证，但必须带可识别标记，并提供一键清理入口。

原因：

- 经营看板是辅助决策工具，重要但不应挤占“我的”页的基础导航空间。
- 用户关心的是“谁看了、看了什么、有没有咨询或下单、下一步怎么跟进”，不关心内部评分模型。
- 这是用户自己的 SCRM 系统，对自己的客户资料继续脱敏会增加操作障碍。
- 真机验证需要接近真实数据结构，单纯前端 mock 容易造成上线后视觉和数据口径不一致。

### 决策：上线闭环先用 shareId 追踪真实分享批次

选择：

- 展示页分享时生成 `shareId`，并把 `sid/from/scene/ref` 放入分享路径。
- 客户打开、点击资料、电话咨询、复制微信都携带同一个 `shareId`。
- 第一版不单独建立分享批次表，展示页事件直接保存 `shareId/shareFromUserId/scene/referrer`。
- analytics 先按 `shareId` 聚合打开、看资料、咨询，形成“分享批次”视图。

原因：

- 当前最重要的是知道“这次发给客户有没有打开、有没有看资料、有没有咨询”。
- 微信小程序分享回调不适合强依赖分享前后端建表，前端生成批次 ID 更轻。
- 先把真实行为归因跑通，后续渠道码、群来源、转化漏斗再升级为独立分享表。

### 决策：手动新建房源/商品先走“快速向导 -> UserNote -> note-edit”

选择：

- 小程序底部“添加”入口改为“添加资料”快速向导，而不是继续沿用旧资源库创建页。
- 房源、商品团购、普通笔记手动新建统一保存为 `UserNote`。
- 粘贴文案作为主路径，复用 `content-to-note` 规则提取字段；用户选择的类型视为人工确认。
- 空白创建只生成结构化草稿壳，深度字段编辑继续交给现有 `note-edit` 工作台。
- 图片资料继续复用现有 OCR 图片保存入口，不在本轮重做图片流程。
- 首版不新增房源表、商品表或单独的手动表单后端模型。

原因：

- 当前产品早期最关键是迁移和沉淀资料，手动新建应服务“快速放进笔记库”，不应把用户卡在复杂表单里。
- `UserNote.visibilityConfig.cardType/structuredData/conversionConfig` 已经能承载房源和商品草稿，新增表会放大同步和展示页适配成本。
- 统一进入 `note-edit` 能复用现有房源/商品工作台、图片、SKU、接龙和转化配置能力。
- 用户选择类型比规则识别更明确，适合首版作为“人工确认类型”。

### 决策：底部“添加”主形态改为极简随手记

选择：

- 底部中间“添加”不再默认展示房源/商品/普通笔记/图片资料选择卡。
- 页面主标题为“放进笔记库”，主体验是一块大输入框和轻工具栏。
- 普通记账、备忘、客户需求等低置信内容直接保存为普通笔记，保存后留在当前页。
- 房源/团购文案如果高置信识别，直接保存为对应业务草稿，再用方案 B 的页面内业务提示层引导用户完善详情。
- 用户取消“去完善”时，资料仍保留为房源/商品草稿，而不是降级为普通笔记。
- 空白房源、空白商品、图片资料放在更多入口里弱露出，不抢主画面。

原因：

- 用户真正需要的是“先把资料丢进系统”，不是每次先做类型选择。
- 随手记入口能覆盖普通笔记、记账、客户一句话和粘贴业务文案，心智更轻。
- 高置信自动分流比让用户先选类型更接近企业微信导入链路，也能复用已有结构化工作台。
- 业务入口弱露出可以兼顾新用户发现能力和页面极简感。
### 决策：公开展示页必须读取发布快照

选择：

- 展示页发布时生成 `publicSnapshot`，包含客户公开页所需的标题、配置、资料摘要和模板字段。
- 客户打开公开展示页时优先返回 `publicSnapshot`，不再每次实时读取笔记表并重新拼装页面。
- 已发布但没有快照的旧展示页，第一次公开访问时自动补一次快照并保存；之后同样走快照读取。
- 用户重新发布展示页时刷新快照版本；删除资料时同步从相关展示页快照中剔除该资料。

原因：

- 展示页是给客户高频打开的公开页面，不能每次访问都拉取多条资料并动态组装，否则分享扩散后会给服务器造成不必要压力。
- 发布快照能保证客户看到的是一次明确发布后的稳定版本，也符合“编辑后重新发布才更新客户页”的业务心智。
- 删除资料属于安全边界，必须主动修剪快照，避免已删除资料继续被客户看到。

### 决策：个人资料先做轻设置中心，不扩大到账户体系

选择：

- `User` 继续作为小程序用户资料的唯一承载，暂不新增 profile 表。
- 第一版设置中心只允许修改昵称、手机号和头像信息。
- 后端提供 `PATCH /api/auth/users/{user_id}/profile`，保存到 `User.nickname/avatarUrl/phone`。
- 小程序“我的”页的“编辑资料/设置中心”直接打开底部弹窗，不新增复杂页面。
- 头像为空或不可用时继续用彩色首字兜底；长期头像托管后续单独做上传能力。

原因：

- 用户当前痛点是登录后头像白块和没有地方补资料，不是完整账号管理。
- 看板、客户库、待联系、订单处理都需要稳定的昵称、电话和头像兜底，轻设置中心可以马上改善真机体验。
- 头像上传涉及媒体存储、域名白名单和跨设备访问，应该作为独立能力做，不和本次资料编辑混在一起。

### 决策：经营看板排行默认下钻到具体访客

选择：

- “资料点击排行”不只跳到资料动作页，默认点击后筛出点过这条资料的访客。
- 后端在 `visitorProfiles` 中保留 `noteIds`，前端用资料 ID 做精确筛选，标题只作为兜底。
- 经营看板动作流水跟随当前筛选，不展示和当前资料无关的动作。

原因：

- 用户看经营看板的目的不是看排行榜本身，而是知道哪条资料带来了哪些客户。
- 只展示点击次数会形成报表感，无法进入电话、微信、线索或订单处理。
- 用 `noteIds` 比按标题匹配更稳，避免两条资料同名时把访客混在一起。

### 决策：经营看板访客点击先看处理卡

选择：

- 经营看板访客列表点击后，不直接离开当前页面，而是先打开页内客户详情处理卡。
- 详情卡集中展示头像、来源、联系方式、看过资料、分享批次和可处理入口。
- 外呼、复制微信保留在详情卡里，线索/订单/资料动作作为明确的下一步按钮。

原因：

- 用户看板里的核心问题是“我应该处理谁”，直接跳走会打断对客户上下文的判断。
- 先看客户处理卡，可以把总数、来源、资料兴趣和联系方式串成一条业务线。
- 这比继续增加报表维度更接近用户实际处理动作。

### 决策：客户库也保留“先看人，再处理”的入口

选择：

- 客户库原有快操作保留，点击客户头像/姓名区域打开页内客户详情处理卡。
- 详情卡集中展示阶段、意向、联系方式、来源资料、最近查看、最近跟进、订单状态和标签。
- 下一步处理作为主按钮，辅助入口保留查看客户和来源资料。

原因：

- 客户库虽然不是报表页，但用户仍需要先确认“这个人是谁、从哪来、现在该做什么”。
- 把上下文聚合在一个轻弹层里，可以减少在客户库、线索详情、资源详情、订单详情之间反复跳转。
- 不移除原有快操作，可以兼顾熟练用户效率和新用户理解。

### 决策：待联系也统一为线索处理卡入口

选择：

- 待联系页点击线索头像/姓名区域时，先打开页内线索详情处理卡。
- 详情卡展示状态、跟进时间、联系方式、来源资料、查看次数、备注、最近跟进和归档原因。
- 原列表快操作保留，详情卡提供“查看线索 / 来源资料 / 立即处理”三个清晰动作。

原因：

- 待联系是最接近真实处理动作的页面，如果只展示一排按钮，会让用户跳过上下文直接操作。
- 和经营看板、客户库保持同一套“先看人，再处理”心智，能减少页面之间的理解成本。
- 线索处理卡可以把电话、微信、来源和跟进记录放在一起，帮助用户判断是外呼、复制微信还是继续编辑线索。

### 决策：订单/接龙列表也先看买家处理卡

选择：

- 订单/接龙列表点击订单卡后，先打开页内买家订单处理卡。
- 处理卡展示买家、状态、来源商品、规格/数量、类型、备注、地址和联系方式。
- 商家侧主动作优先外呼，其次复制微信，没有联系方式时进入订单详情。

原因：

- 用户要求最终落实到“下单的具体的人”，订单列表不能只像交易流水。
- 先看买家订单处理卡，可以把来源商品、联系方式和订单状态放在同一处，减少直接跳详情造成的上下文丢失。
- 和经营看板、客户库、待联系保持统一交互，形成“总览 -> 来源/状态 -> 具体人 -> 处理动作”的闭环。

### 决策：头像只接受稳定 HTTPS，其他情况使用文字兜底

选择：

- 小程序统一把空头像、`example.com`、`avatar-default`、本地临时路径和非 HTTPS 地址视为无效头像。
- 无效头像不渲染图片，直接显示彩色文字头像。
- 后端登录默认头像为空；用户资料更新时拒绝无效头像地址。
- 展示页、经营看板、客户库、待联系、订单、访问记录、接龙名单等“具体人”场景都要有兜底头像。

原因：

- 微信登录只能拿 openid，不天然提供头像；用示例头像或临时头像会在真机显示白块。
- 真机域名限制下，前端不能相信任何看起来像 URL 的头像都可显示。
- 用户要识别具体客户，头像区域必须稳定可见；没有真实头像时，彩色首字比白块更可靠。

### 决策：个人页只保留经营看板作为经营主入口

选择：

- “我的”页不再同时放“访客线索 / 待联系 / 客户库”等多个经营入口。
- 主入口收敛到“经营看板”，订单入口保留；客户库和待联系底层页面暂时保留给看板下钻、历史链接和后续客户档案能力。
- 不做本轮物理删除路由和接口，避免误伤已存在的经营闭环。

原因：

- 用户当前主要判断入口是经营看板，多个类似入口会造成“到底去哪处理客户”的困惑。
- 客户库仍有客户沉淀价值，但不适合继续作为个人页主入口抢占心智。
- 待联系后续如果确认完全废弃，应单独做依赖扫描后再删除，不在 UI 小优化里硬删。

### 决策：普通笔记在列表中拥有显式分类

选择：

- “我的笔记”快捷分类展示“全部 / 普通笔记 / 房源 / 商品团购”。
- 普通笔记筛选按 `text_note` 且没有房源/团购候选的笔记本地过滤。
- 待处理迁入筛选必须有明显选中态，不只改变列表条数。

原因：

- 普通笔记是用户最频繁的轻入口，不能被房源、商品和待整理状态淹没。
- 用户点“待处理”后需要一眼知道当前处于筛选状态，否则只看到条数变化会不确定。
- 本地过滤改动小，避免为小优化新增后端查询参数。

### 决策：电子名片使用独立工作台，不再依附普通笔记入口

选择：

- 资料库新增“电子名片”独立按钮，直接进入三步式工作台。
- 工作台流程固定为“选风格 -> 填资料 -> 确认效果”，确认页同时看转发卡片和客户详情页。
- 电子名片保存后仍是 `business_card` 类型的 `UserNote`，继续复用现有公开页、客户动作和轻 SCRM 基座。
- 旧添加页中的电子名片入口跳转到新工作台，避免用户进入旧模板选择页。

原因：

- 电子名片的用户心智不是“写一条笔记”，而是“挑一个能发客户的名片模板”。
- 同一份个人资料需要反复套不同风格，不能让用户每切一次模板就重新填写。
- 独立工作台可以先把首屏卡片、详情页、分享效果放在同一个确认流程里，降低“保存后才发现不好看”的返工。

### 决策：服务方案工作台按“横向看样式，纵向填内容”组织

选择：

- 顶部步骤区固定为横向三段：“选模板 / 填资料 / 确认效果”。
- 模板方案区使用横向滑动卡片，不再做竖向长列表。
- 模板切换只改变样式和默认展示图，不覆盖用户已经填写的服务内容。
- 资料库保留“快速入库”入口，同时在“电子名片”旁边新增“服务方案”独立入口。

原因：

- 服务方案工作台的核心任务是先看模板效果，再决定是否继续填写，横向结构更接近用户的选择心智。
- 手机上纵向堆叠太长时，模板参考会被表单挤出视野，用户容易失去对照。
- 服务方案和电子名片都属于“直接发客户”的产物，入口层级应该一致，不能只藏在笔记器链路里。

### 决策：服务方案步骤区复用电子名片三列样式

选择：

- “选模板 / 填资料 / 确认效果”步骤区固定为三列，不再使用横向滚动卡片。
- 模板方案区仍保留横向滑动，但必须限制在阶段卡片内部，不允许撑开整页。
- 模板选择卡只展示模板名称、标签和适合场景说明；真实图片只放在下方详情预览里展示。
- 三步页面的主要容器必须按手机宽度约束：`width: 100%`、`max-width: 100%`、`min-width: 0`，内层卡片保留 `2rpx` 安全留白。

原因：

- 用户已经确认服务方案和电子名片心智接近，步骤区应直接复用电子名片的稳定适配方式。
- 横向滚动更适合模板选择，不适合顶部流程，因为流程必须一眼看完。
- 真机截图显示横向步骤卡会带来页面宽度溢出风险，三列 rpx 布局更稳。
- 模板卡放缩略图会使首屏横向区域过高过挤，并更容易在手机端造成整体页面溢出；视觉差异由下方联动预览承担。

### 决策：服务方案分享和列表展示必须与模板保持一致

选择：

- 服务方案和电子名片一样，微信转发必须优先使用专门生成的横版封面图，不依赖默认小程序卡片。
- “我的笔记”里的服务方案不再使用普通资料的左图右文卡，而使用专属方案预览卡。
- 服务方案列表卡和转发封面优先使用用户上传封面，没有时使用当前模板默认图。
- 模板预览、我的笔记列表、客户详情页和微信转发卡片要围绕同一份 `serviceOfferPreview / serviceOfferDetail` 信息展示。

原因：

- 服务方案是直接发给客户的销售页，默认小程序卡片会削弱模板感和完整性。
- 电子名片已经验证“列表卡 + 微信转发封面 + 客户详情页”一致能明显提升可信度。
- 用户会从资料库列表直接判断方案是否可发，列表卡如果退回普通资料样式，会显得像半成品。

### 决策：首页与 Tabbar 工作台模式一期按 P0 闭环验收

选择：

- 工作台一期验收不能只看代码侧自测通过。
- 只要 P0 存在“部分覆盖”或缺少真机/权限回归证据，验收结论就不能写“通过”。
- 本次 `工作台第一期_验收报告.md` 结论定为“不通过”，不是因为主链路完全不可用，而是因为 P0-23 和 P0-27 未闭环。

原因：

- Tabbar、首次引导、模式切换、首页布局、工作台入口属于真机强相关功能，静态扫描无法替代用户侧验收。
- 权限和隐私属于 P0，不能用“本轮没改后端权限逻辑”替代真实回归证据。
- 业务识别后的工作台切换提示直接影响用户身份和资料流向，必须明确允许继续当前工作台。

### 决策：房源客户看板必须走 `mode=property` 专属口径

选择：

- 首页房源四指标、房源客户看板、房源效果、最近访客和待跟进，统一使用 `GET /api/dashboard/business?mode=property` 的后端聚合口径。
- 房源模式只统计房源资料和包含房源资料的推荐包；推荐包中如果混入服务/普通资料，非房源资料点击不得进入房源看板的资料排行、访客画像和待跟进。
- 首页 `打开` 使用房源单页打开与推荐包内房源点击/打开的综合口径；`访客` 使用去重访客；`待跟进` 使用 pending lead。
- 单条房源卡片有客户动作时，入口进入 note 级客户动作页，而不是旧卡片管理页。
- 本地后端测试统一使用 `.venv312` 的 Python 3.12 环境。

原因：

- 房源工作台的付费价值是“来客户了、谁看了、谁需要跟进”，不能停留在展示页 BI 或通用经营看板。
- 中介用户需要第一眼处理客户，不能在旧管理页和新客户动作页之间迷路。
- 如果通用看板把服务、普通资料、房源混在一起，首页数字会失真，用户会不信任系统。
- Python 版本不稳定会反复拖慢验收，固定本地 3.12 环境能降低后续开发成本。

### 决策：房源首页必须同时支持今日和累计

选择：

- 房源首页概览默认展示“今日”，并提供“累计”切换。
- 今日口径只统计当天事件：今日新增房源、今日打开、今日访客、今日新增待跟进。
- 累计口径统计历史总量和当前未处理：当前房源总数、历史打开、历史访客、当前待跟进。
- 点击今日访客/今日待跟进时，客户看板必须按 `range=today` 过滤访客和动作列表。
- 单条房源直接打开也要进入访客画像，不能只统计推荐包访客。

原因：

- “今日概览”显示累计数据会误导用户，尤其是客户痕迹这种付费核心能力。
- 中介每天最关心的是“今天谁来了、看了哪套、我怎么联系”，不是先看历史报表。
- 累计数据仍有价值，但应该作为切换后的效果沉淀，而不是默认冒充今日。
- 2026-06-23 决定：房源客户看板后端同时保留 showcaseBreakdown（推荐包拆解）和 propertyBreakdown（单房源拆解），前端可逐步切到更明确的 propertyBreakdown，旧字段保持兼容。

### 决策：合集列表采用手机缓存 + 后台同步

选择：

- 合集首页不应每次进入都阻塞式拉数据库。
- 小程序端按 `userId + workspaceMode` 缓存合集列表 5 分钟。
- 有缓存时先展示缓存数据；缓存过期时后台同步并刷新页面。
- 删除合集、强制刷新等会重新拉取并覆盖缓存。

原因：

- 合集列表是高频入口，用户多次切换 Tab 时不应反复看到“加载中”。
- 合集数据变化频率低于客户动态，短时间缓存不会明显影响业务判断。
- 先显示旧数据再同步最新数据，可以同时降低服务器压力和等待感。

### 决策：资料库红点只表达待处理，不表达历史动态

选择：

- 房源卡红点只由未读或待跟进产生。
- 已处理后的历史客户动态仍保留在卡片和客户动作页中，但不再点亮红点。
- “客户动态 1 / 看客户”用于复盘，“红点”用于提醒当前需要处理。

原因：

- 用户处理客户状态后红点仍常驻，会误导用户以为还有未处理事项。
- 历史行为轨迹有解释推荐、复盘和筛选价值，但不能和待办提醒混成同一种视觉信号。

### 决策：资料库工具区只放资料相关动作

选择：

- 资料库“更多工具”保留待认领、管理标签、我的笔记。
- 电子名片、服务方案从资料库工具区移除，后续放到对应工作台或统一新增入口中。

原因：

- 房源资料库用户当前意图是整理、筛选、编辑、分享房源资料。
- 电子名片和服务方案属于服务/销售页产物，混入资料库会增加理解成本。

### 决策：标签入口按“筛选和生成合集”解释，不按后台管理解释

选择：

- 资料库入口命名为“标签设置”，弱化“管理后台”感。
- 标签页必须明确告诉用户：标签用于快速筛选、系统自动归类、生成合集。
- 房源场景示例优先使用地铁口、电梯房、价格段等强筛选属性。

原因：

- 用户不会为了“管理标签”本身打开页面，只有知道它能更快找房源、组合集，才会愿意使用。
- 合集后续会依赖价格、户型、地铁、电梯等标签和字段，标签心智需要提前铺好。

### 决策：客户功能设置默认紧凑展示

选择：

- 房源/服务资料详情页的客户功能设置展开后采用两列卡片式开关。
- 默认仍折叠，只展示已开启功能摘要；需要调整时再展开。

原因：

- 客户功能属于低频设置，不应占用房源详情页过多纵向空间。
- 两列布局能保留说明文字，同时减少页面长度，避免用户在核心房源信息和客户反馈之间滚动过久。

### 决策：房源库筛选按强属性前置

选择：

- 房源模式资料库新增专门筛选面板。
- 筛选维度一期包括价格区间、户型、地铁/近地铁、电梯/楼梯、房源状态。
- 价格同时支持常用区间快捷按钮和最低价/最高价两个输入框。

原因：

- 中介找房源时最常用的是强属性筛选，不应完全依赖搜索标题或标签。
- 这些筛选条件也会成为后续一键生成房源合集的基础。

### 决策：房源详情页优先看客户反馈，再看编辑设置

选择：

- 房源详情页顶部保留转发房源、客户页预览、复制文案等发客户动作。
- 顶部动作后优先展示“客户反馈”，让用户先知道这套房是否有人看、预约、留资、待跟进。
- 房源字段作为核心资料展示/编辑区。
- 客户功能设置属于低频配置，继续折叠并紧凑展示。

原因：

- 房源工作台不是纯编辑器，用户打开详情时经常是为了“发客户”和“处理客户”。
- 把低频配置放在高频客户反馈前面，会让页面显得像后台表单。

### 决策：房源筛选入口不依赖分类区

选择：

- 资料库只要有房源资料，就前置显示“房源筛选”面板。
- 默认不强制切到房源列表；只有用户设置价格、户型、地铁、电梯、状态等条件后，才按房源条件筛选。
- 合集“按条件筛选”使用同一类强属性条件，并自动加入符合条件的房源。

原因：

- 用户如果找不到“分类筛选”，房源筛选能力就等于不可见。
- 条件筛选是生成房源合集的核心入口，不能只做成资料库里的隐藏能力。

### 决策：房源工作台小闭环先做轻量联动

选择：

- 房源卡状态先用待处理、已跟进、有浏览、待分享四类表达。
- 客户反馈页先用快捷按钮处理线索状态，不新增复杂 CRM 流程。
- 资料库筛选条件可以直接带入合集编辑页，合集按条件自动选房源，再允许用户手动删减。
- 合集效果页先用现有事件做客户看房轨迹，不新增后端聚合表。
- 房源详情页先用“发客户 / 编辑资料”二段切换降低长页面压力。

原因：

- 当前阶段重点是让房源工作台形成顺手闭环，不是扩展完整 CRM。
- 这些能力都能复用已有数据和接口，风险小、验收快。
- 用户需要的是“我筛了房 -> 生成合集 -> 发出去 -> 看客户轨迹 -> 标记跟进”的连续体验。

### 决策：标签设置是“常用标签库”，不是自动给所有房源打标签

选择：

- 标签设置页创建的是全局常用标签。
- 单套房源需要在房源详情页“编辑资料 -> 资料归类”里选择常用标签后才应用到该房源。
- 资料库房源卡和标签筛选同时读取 `userTags/tags`，让单房源标签能体现出来。

原因：

- 全局标签直接自动加到所有房源会污染筛选结果。
- 用户建标签的目的，是后续给具体房源快速选择，而不是只维护后台字典。

### 决策：房源系统标签由字段自动生成

选择：

- 系统标签不让用户逐个点选。
- 保存房源时根据结构化字段自动生成系统标签。
- 系统标签进入 `systemTags`，同时合并进 `tags` 用于筛选和合集生成。
- 用户主动选择的标签仍保留在 `userTags`。

原因：

- 租金区间、户型、地铁、电梯、状态是后续选房和合集生成的基础索引，不能依赖用户手动维护。
- 用户标签应表达个人判断；系统标签应表达客观字段。

### 决策：房源工作台先做发客户前检查，不做重 CRM

选择：

- 房源详情“发客户”页签展示客户视角预览和发布前检查。
- 合集编辑页发布前展示检查项，发布时遇到缺项弹窗确认，但不强制阻断。
- 筛选维度继续围绕强属性：价格、户型、地铁、电梯/楼梯、面积、押付、入住、状态。
- 房源卡状态只提示下一步动作，不扩展复杂跟进阶段。

原因：

- 当前阶段核心是降低发错房源、漏填关键信息的风险。
- 中介用户需要快速发房，不应因为轻微缺项被系统强制卡住。
- 发布前检查可复用到后续团购、名片、服务方案工作台。

### 决策：团购/商品详情页采用“发群 / 编辑商品”双视角

选择：

- 单商品详情页默认先展示“发群”视角。
- “发群”视角放客户预览、发群前检查、接龙/买家反馈。
- “编辑商品”视角放商品字段、图片视频、SKU、取货方式、下单开关和资料归类。
- 发群前检查只提醒风险，不做强阻断。

原因：

- 团购/商品工作台的高频动作是发到群里、看接龙、处理买家，不是反复改后台字段。
- 如果详情页只是普通商品编辑器，会失去“团购/接龙工作台”的差异化。
- 房源工作台的“发客户 / 编辑资料”经验可迁移到团购场景，但文案和检查项必须围绕价格、规格、取货、接龙和库存。

### 决策：商品合集以发群前检查为主，不做普通商品橱窗

选择：

- 团购/商品工作台里的“商品合集”直接进入商品合集编辑页。
- 商品合集页面根据分类切换成商品语境，使用“发群、商品、取货、价格、截止时间”等文案。
- 第一版商品条件筛选只做价格区间、取货方式、截止时间。
- 商品合集发布前检查覆盖已选商品、封面、联系入口、价格完整度、取货信息。
- 发布仍只负责生成可分享客户页；真正发群通过发布后的转发按钮完成。

原因：

- 团购场景的核心不是维护商品橱窗，而是快速组织一波可发群的商品。
- 商品合集最容易出错的是价格、取货方式和截止时间，不是复杂后台配置。
- 不应把“发布”伪装成自动转发，避免用户误解小程序行为。

### 决策：团购/商品订单名单归属以 noteId 为准

选择：

- 商品接龙/下单名单的后端过滤参数使用 `noteId`。
- 订单页来源分组内部 key 优先使用 `noteId`，展示名仍使用商品标题。
- 同名商品不能只靠标题分组或过滤。

原因：

- 团购场景中同类商品或同名商品非常常见，只按标题过滤会串单。
- `noteId` 是当前商品资料的稳定标识，能和客户动作、消息线程、商品详情页保持一致。
- 标题只适合展示，不适合作为业务归属键。

### 决策：商品资料复用只复制内容，不复制运营数据

选择：

- 商品资料支持“复用成新商品”。
- 复用只复制商品字段、图片、SKU、取货和下单配置。
- 客户动作、订单/接龙、访客统计、消息线程不复制。
- 新商品进入编辑状态，标题增加“副本”。

原因：

- 团购场景经常复用同类商品文案和规格，但每一波团的接龙和买家名单必须独立。
- 如果复用时带上旧订单或统计，会直接污染新团。
- 复制后进入编辑状态，能提醒团长检查价格、取货和截止时间。

### 决策：商品筛选优先用字段和系统标签

选择：

- 商品保存时自动生成系统标签：自提、配送、快递、今日截止、本周截止、有 SKU、已售罄、待补价格、待补取货。
- 资料库商品筛选同时读取字段和系统标签，老数据未重新保存时也尽量能筛出待补项。
- 商品合集条件筛选只继承价格、取货方式、截止时间三类高频条件。

原因：

- 团长不会稳定手动维护商品标签，筛选基础必须来自商品字段。
- 商品筛选的第一目标是快速组一波可发群商品，不是做完整电商搜索。
- 老数据可能没有系统标签，因此筛选不能完全依赖标签。

### 决策：工作台模式必须影响资料范围

选择：

- 用户处于房源工作台时，资料库和工作台聚合默认只看房源资料。
- 用户处于团购/商品工作台时，资料库、工作台聚合和团购看板默认只看团购/商品资料。
- 首页统计卡点进资料库和底部 Tab 直接进资料库，都使用同一套模式隔离规则。
- 允许在资料库内清除筛选临时看全部，但切换工作台/重新进入时仍以当前工作台模式为默认。

原因：

- “工作台”是独立业务场景，不只是视觉皮肤；数据范围不隔离会让团购用户看到房源，破坏场景心智。
- 团购/商品工作台的访客、接龙、商品数等指标只有在商品范围内才有业务价值。
- 房源和商品可以共用资料底座，但默认入口必须按当前工作台收窄。

### 决策：团购卡片列表优先保证可操作空间

选择：

- 团购商品资料卡片的动作区采用两列布局。
- 有接龙/客户动态时，“处理接龙”作为主操作独占一行，“分享/更多”在下一行。
- 编辑展示页的已选商品操作按钮放在商品正文下方，不长期占用正文右侧宽度。

原因：

- 团购场景的主操作文案和状态标签更长，继续照搬房源三按钮横排会在真机上溢出。
- 商品卡片最重要的是标题、价格/规格、取货/接龙状态和可点击操作，不能让操作按钮挤掉内容识别。
- 小程序真机字号和系统状态栏会放大布局问题，按钮必须以稳定网格和 flex 居中为基线。

### 决策：卡片列表封面从来源资料兜底

选择：

- `/api/cards` 返回列表时，优先使用 card 自身 `coverUrl`。
- 如果 card 没有封面，则使用来源 note 的 `coverUrl` 或第一张图片。

原因：

- 企业微信导入、资料编辑、展示页转发和资料列表可能读取不同层级的数据。
- 用户感知上“这条团购商品已经设置封面”，资料列表就应该显示同一张图。
- 封面兜底放在后端列表接口里，前端页面可以保持简单一致。

### 决策：服务工作台 P0 必须以客户页预览和服务数据隔离为边界

选择：

- 服务工作台的 P0 范围固定为电子名片、服务方案、客户页预览、微信分享、留言/预约回流和咨询看板。
- 首页、资料库、客户看板和后端聚合在 `mode=service` 时默认只看 `business_card` 和 `service_offer`。
- 电子名片/服务方案未保存或有未保存改动时，不开放编辑页右上角分享菜单。
- 编辑工作台确认页的主动作是“保存并预览”，先进入客户页看真实效果，再从客户页或已保存状态分享。
- 发前检查只做 P0 风险提示，不阻断头像、封面等可选项；姓名/身份、联系方式、服务名称、服务内容等核心字段仍由表单校验保障。

原因：

- 服务工作台的核心价值是“发给客户前看起来可信，并且客户动作能回到咨询看板”，不是普通资料卡编辑。
- 如果服务看板混入房源、团购或普通资料，咨询、预约和访客指标会失真。
- 小程序编辑页分享无法异步先保存；隐藏未保存分享菜单比允许用户误发编辑器页更稳。
- 客户页才是最终转发给客户的真实页面，保存后直接预览能降低发错内容、漏联系方式和模板不一致的风险。

### 决策：服务资料编辑和复用必须回到专属工作台

选择：

- 电子名片资料点击编辑进入 `business-card-studio`。
- 服务方案资料点击编辑进入 `service-offer-studio`。
- 服务资料复用只复制内容、模板、图片和联系方式，不复制访客、留言、预约、线索和统计。
- 服务资料加入合集默认进入案例合集编辑，不再走普通资料包心智。

原因：

- 电子名片和服务方案已经不是普通笔记表单，回到通用编辑页会丢失“选模板、看客户页、发前检查”的完整体验。
- 服务销售页经常复用模板和文案，但每次发出的客户反馈必须独立，否则咨询看板会被旧数据污染。
- 服务工作台的合集心智是“案例合集 / 服务资料包”，不是日常资料包。

### 决策：电子名片/服务方案资料库必须兼容 note-only 资料

选择：

- 电子名片和服务方案可以继续以 `user_notes` 为主数据模型保存。
- `/api/cards` 在 owner 场景下补充合成 `business_card/service_offer` 的 note-only 列表项，供资料库、工作台统计和旧卡片列表复用。
- 合成项必须携带 `sourceNoteId`，编辑进入专属工作台，查看进入客户预览页。
- 合成项删除时删除来源 note，不调用旧版 card 删除接口。

原因：

- 服务工作台已经走“名片/方案 -> 客户页 -> 留言/预约”的新资料链路，如果强行再创建旧 card，会让两套数据更难一致。
- 资料库仍承担统一入口角色，不能因为底层模型升级让用户保存后看不到资料。
- 用 `sourceNoteId` 明确区分来源，能保持旧资料卡兼容，同时避免客户统计和复用数据被错误合并。

### 决策：服务方案模板预览和确认效果共用真实表单内容

选择：

- 模板卡可以保留模板风格和示例图，但客户页小预览、确认效果和最终分享页必须优先使用同一份表单内容。
- 当用户未手动改写字段时，切换模板会应用当前模板 `defaults`；用户已改写的字段不被模板覆盖。
- 服务内容、统计项等容易被用户对比的区域，不再一边读 `template.preview`，一边读表单默认值。

原因：

- 用户判断模板是否可用时，看的是“我发出去会是什么样”，不是模板库示例。
- 未编辑内容时展示模板和最终效果不一致，会让用户以为保存或渲染出错。
- 服务方案是成熟销售页场景，模板应提供可直接发出的默认内容，同时允许用户继续精修。

### 决策：电子名片/服务方案优先采用确认页点选编辑

选择：

- 电子名片和服务方案先采用“半所见即所得”：保留原有表单，但确认效果页允许点击模块直接修改。
- 点选编辑只更新当前表单和预览，不立即写库；用户仍通过“保存并预览”持久化和进入客户页。
- 可编辑范围优先覆盖客户最会感知的内容：标题、卖点、人群、服务内容、流程/报价/案例、介绍、服务范围和联系方式。

原因：

- 服务销售页的用户目标不是填写字段，而是把最终发给客户的页面改顺眼、改可信。
- 直接在效果页修改能减少“模板看起来一套，最终出来另一套”的心理落差。
- 保留最终保存动作，可以避免每次点选编辑都频繁写库，也继续保证未保存时不开放分享的安全边界。

### 决策：服务工作台 P1 继续围绕客户页真实效果收口

选择：

- 点选编辑要覆盖文字、联系方式、头像/封面/案例图和按钮文案。
- 切换模板时，用户已经改过内容则必须给“保留我的内容 / 套用模板文案”的选择。
- 客户页表单先沿用现有 `lead-contact` 和 `appointment` 动作，只优化服务语境文案，不新增后端动作类型。

原因：

- 服务工作台的关键体验是“最终发给客户的页面可信且好改”，不应把用户拉回复杂表单。
- 模板切换既是换视觉，也可能换文案；不提示会让用户误以为系统覆盖或没有覆盖。
- 当前客户看板已经基于 lead/appointment 回流，P1 阶段优先稳定，不拆新的咨询表单数据结构。

### 决策：团购/商品工作台首页第四项使用订单，不使用访客

选择：

- 团购/商品工作台首页四格固定为“商品 / 待处理 / 今日接龙 / 订单”。
- “访客”保留在商品效果、客户看板等效果分析场景，不作为首页待处理核心指标。
- 普通商品下单显示“处理订单”，接龙商品显示“处理接龙”，避免所有商品都被接龙心智覆盖。

原因：

- 团购/商品场景的核心闭环是商品发布、下单/接龙、名单处理和交付，访客只是辅助效果指标。
- 普通商品不一定走接龙，首页直接给订单入口更符合经营动作。
- 访客放在首页容易让用户误以为需要处理访客，弱化真正待处理的订单名单。

### 决策：只保留“专题”和“合集”两个用户概念

选择：

- 内部整理和检索统一叫“专题”，不再前台混用“专辑、文件夹、资料包”等词。
- 外部可分享集合统一叫“合集”。
- 日常资料台叫“日常合集”，房源场景叫“房源合集”，商品场景叫“商品合集”，服务场景叫“案例合集”。
- 从专题可以一键生成对应场景的合集，但前台必须提示用户：专题用于内部整理和检索，合集用于分享。

原因：

- 用户需要在资料库里找回某个主题下的资料，不能只在详情页看到专题归属。
- 专题是内部归档和检索心智；合集是可发给客户或外部对象的展示心智，两者混在一起会让创建、分享和搜索路径都变重。
- 当前资料库已经按工作台隔离，专题筛选也必须跟随隔离范围，避免日常用户看到房源、团购、服务的突兀分类。
- 只保留两个概念能降低学习成本：用户只需理解“自己整理用专题，发出去用合集”。

### 决策：普通资料能力入口先插件化占位，不默认开启运营配置

选择：

- 普通笔记“添加能力”先展示插件面板，能力包括留言、咨询、接龙等后续可插拔能力。
- P1 阶段插件只做心智和入口，不默认启用、不写客户动作配置、不把普通笔记变成业务工作台。
- 用户需要继续整理时，提供“先补摘要、标签和专题”的轻量入口。

原因：

- 普通资料的核心是整理、检索、生成日常合集和查看分享反馈。
- 留言、咨询、接龙是有价值的扩展能力，但应作为后续插件逐个接入，避免普通笔记被 SCRM 化。
- 插件面板能让用户知道后续可扩展，同时保持当前 P0/P1 主链路清爽。

### 决策：生成同款克隆只复制公开内容，不复制 A 的私有上游包

选择：

- 生成同款后端接口统一使用 `POST /api/notes/property-same/clone`。
- 单套房源生成 B 名下新房源卡；房源合集生成 B 名下新合集，并把合集内公开房源逐条复制为 B 名下新房源卡。
- B 的电话/微信替换进新房源卡和新合集公开联系配置。
- 上游联系人只写入 B 的私有 `visibilityConfig.privateData.upstreamContact`，默认取 A 的公开联系方式或公开身份，B 可后续编辑。
- 不继承 A 的 `privateData`，也不复制 A 私密保存的真实房东、二房东或渠道联系方式。

原因：

- 中介需要的是“我可以立刻拿来发客户/同行”的正式资产，不是只能二次整理的草稿。
- A 的私域上游关系是产品信任边界，不能因为 B 生成同款而泄露。
- 生成合集时复制条目为 B 的新房源卡，能保证后续编辑、删除、统计和分享都归属 B，不污染 A 的数据。

### 决策：媒体去重以资产表为底座，先做新进入媒体的完全 hash 去重

选择：

- 新增 `media_assets` 保存媒体类型、原始 hash、处理后 hash、URL、大小和状态。
- 新增 `media_asset_refs` 保存资产被哪位用户、哪个对象、什么用途引用。
- 图片仍先转 WebP，视频仍先转 MP4；保存前后分别计算 hash。
- 命中原始 hash 或处理后 hash 时复用已有 URL，只新增引用，不再重复上传/落文件。
- 历史媒体不在本轮自动回填 hash，后续需要单独离线任务处理。

原因：

- 房源场景中图片/视频是存储大头，同图多标题、多合集、多中介转发时必须先共享媒体资产。
- 完全 hash 去重实现清晰、风险小，能先解决“重复保存同一张图/同一段视频”的基础浪费。
- 历史媒体缺少原始文件 hash，直接在线回填容易影响生产稳定性，适合单独做可暂停的后台任务。

### 决策：房东长文本先拆成多套房源，公开卖点和私密上游分层保存

选择：

- 一条房东/二房东原文里识别到多套房源时，不直接保存成一条大笔记，而是先生成多个候选房源。
- 中介可勾选候选并批量生成正式房源卡。
- `禁宠` 按公开标签处理，可展示给客户，帮助客户提前判断是否合适。
- 上游电话、微信、中介费、密码锁、红包、朋友圈有照片视频和带看协作限制默认写入私密区，不进客户公开结构。
- 无图房源仍可生成房源卡，后续由中介补图。

原因：

- 对盘群真实消息经常把多套房源和协作说明混在一起，若只存一条资料，中介后续找房、发客户和做合集都会很难用。
- `禁宠` 是租客筛选信息，公开展示能减少无效沟通。
- 上游电话、佣金和密码锁是中介协作资产，泄露到客户页会损害信任，也可能造成飞单风险。

### 决策：访客身份分层不丢数据，但默认不污染客户线索

选择：

- 访客/客户动作增加身份分层：`客户`、`疑似中介`、`疑似上游`。
- 生成同款、同行传播等动作默认标记为 `疑似中介`。
- 疑似中介进入反馈和访客看板，但不投射为待联系客户，不进入优先联系队列。
- 反馈页默认展示客户线索，并提供 `客户 / 同行 / 上游 / 全部` 分组筛选。
- 该能力按“访客身份分层”插件思路设计，后续团购、服务、名片场景也可复用。

原因：

- 中介不是坏数据，而是增长和传播数据；直接排除会丢失裂变线索。
- 同行/房东如果混入客户线索，会让发布者误以为都是租客，破坏待跟进效率。
- 身份分层能同时服务成交和增长：客户用于跟进，同行用于传播，上游用于供应关系。

### 决策：首页房源助手只保留企业微信成员好友入口

原因：

- 用户自然会把企业微信成员好友置顶，然后持续转发群里的房源信息；微信客服入口不符合这个行为。
- 首页同时出现“添加企业微信”和“打开微信客服”会制造认知混乱，也会导致按钮/插件布局反复变形。
- 自动回小程序卡片的官方通道尚未确认，不能继续把它写成主体验承诺。

### 决策：不采纳 WorkBuddy 的 `/externalcontact/message/send` 作为房源助手正式发送通道

选择：

- WorkBuddy 提供的“企业微信单聊回复”代码不并入当前后端。
- 不把 `/cgi-bin/externalcontact/message/send` 作为已确认的企业微信成员好友实时回复接口。
- 企业微信成员好友仍作为房源助手主入口和会话存档来源；结果反馈先依赖小程序内承接、待认领/自动归属、通知落库，发送卡片通道继续专项验证。
- 微信客服能力保留为已打通的技术能力，但不作为“中介长期置顶发房源”的主推广入口。

原因：

- WorkBuddy 代码存在运行级错误，实际调用发送会因 `cgi-bin` 拼接写法崩溃。
- 该方案核心接口未在当前官方文档核对中得到确认，不能作为 P0 主链路基础。
- 用户已明确第一版核心体验是把房源发给企业微信成员好友，而不是让中介寻找微信客服会话入口。

### 决策：首页房源助手主入口使用企业微信「联系我」，微信客服只做兜底

选择：

- 首页“添加房源助手”主入口走企业微信「联系我」小程序插件。
- 「联系我」配置 ID 使用企业微信后台生成的 `3bf7435f594f0d6ca83a9a185ea201e5`。
- `wx.openCustomerServiceChat` 不再作为房源助手主入口，因为它打开的是微信客服会话。
- 后续如果仍保留微信客服，只用于客服咨询兜底，不承载“置顶后持续发房源”的核心路径。

原因：

- 房源中介需要把助手置顶，持续把群里房源转发给企业微信成员；微信客服会话不符合这个使用习惯。
- 企业微信成员外部联系人会话更接近“房源助手/高士腾”长期入口，有利于形成用户习惯和会话存档链路。
- 使用官方插件比复制微信号或二维码更顺，也能直接从小程序按钮进入添加企业微信流程。

### 决策：external_userid 与 openid 的首版绑定采用“认领导入即绑定”

选择：

- 企业微信/会话存档收到房源助手消息后，先生成一条可认领导入。
- 用户用小程序登录后，在“新导入资料”页点击“认领并绑定”。
- 后端把该导入批次的 `externalUserId` 写入 `wecom_identity_bindings`，同时保存 `ownerUserId` 和 `ownerOpenid`。
- 之后同一个 `external_userid` 发来的新消息，自动归属到该 openid 对应用户，不再进入待认领。

原因：

- `external_userid` 是企业微信侧身份，小程序用户身份锚点是 `openid`，两者天然不自动相等。
- 首次认领能让用户明确确认“这条企微消息是我发的”，比后台猜测更安全。
- 保存 `ownerOpenid` 可以避免后端内部 `userId` 迁移或重建后绑定失效。

### 决策：房源助手主体验改为“企业微信回小程序链接，点击即绑定”

选择：

- 企业微信收到并整理完房源后，后端为导入批次生成签名 token。
- 企业微信发回小程序 pagepath：`pages/import-claim/index?token=...`。
- 用户点击小程序链接后，如果未登录先登录；登录回来自动认领、绑定并进入编辑结果。
- “新导入资料/待认领”保留为兜底入口，不作为第一推荐路径。

原因：

- 中介的自然动作是“发给助手 -> 等助手回结果 -> 点结果”，不应该再让用户主动去找待认领。
- 点击链接时小程序能拿到当前微信 `openid`，刚好可以把企业微信 `external_userid` 安全绑定到小程序用户。
- token 带签名和过期时间，比直接暴露 importId 更安全；已认领后禁止其他账号抢绑。

### 决策：整理完成通知先落库，发送通道不能默认使用微信客服 kf/send_msg

选择：

- 会话存档 archive 处理成功后，必须创建 `ImportNotification`，保存结果 `pagePath`、动作按钮和发送状态。
- 结果入口统一使用签名 claim token：`pages/import-claim/index?token=...`。
- 企业微信发送失败时只更新通知发送状态和错误，不影响资料生成、导入批次和小程序内认领。
- `kf/send_msg` 只视为微信客服链路能力，不再默认当作企业微信成员外部联系人私聊发送接口。

原因：

- 生产验证中，10:19 的微信笔记已被会话存档生成资料，但因为没有通知记录，用户无感知。
- 给该外部联系人使用 `kf/send_msg` 补发时返回 `48002 api forbidden`，说明当前接口不能覆盖企业微信成员好友会话。
- 先落库能保证系统不再无声失败；发送通道后续可以替换为客户联系、欢迎语、群发任务、小程序消息中心等更合适路径。

原因：

- 雷达视觉、人物标签、标题层级是首页最强心智资产，纯 DOM 版本容易受小程序字体和布局压缩影响，质感不稳定。
- 当前推广仍以房源为默认尖刀场景，静态房源 banner 能先满足主路径。
- 若后续多场景首屏都要动态高质感，需要补商品、服务商机、资料包三张 banner，或投入更多时间重做高保真 DOM。

### 决策：前台统一叫“场景”，不再强化“工作台”

选择：

- 面向用户的切换入口统一叫“使用场景 / 常用场景”。
- 房源、团购/商品、服务商机、日常资料在前台显示为“房源场景、团购/商品场景、服务/商机场景、日常资料场景”。
- “工作台”保留为代码内部概念或开发讨论概念，不作为用户主要文案。

原因：

- 用户当前真正选择的是资料用途和销售场景，不是在理解一个复杂后台系统。
- “工作台”容易让用户疑惑是不是指雷达页，也会让产品显得偏工具化。
- “场景”更适合“资料发出去，机会看得见”的总心智。

### 决策：资料和合集主按钮统一叫“发客户”

选择：

- 资料页和合集页的主分享动作统一叫“发客户”。
- “分享”只作为底层能力，不作为销售助理主按钮文案。
- 资料和合集都显示发出后的浅色状态追踪条。

原因：

- 不是所有资料都需要先做合集，单条资料也必须能直接发客户。
- “分享”太像普通系统操作，“发客户”更贴近销售动作。
- “发客户”能承接后续雷达反馈，让用户理解这是可追踪页面，不是普通转发。

### 决策：资料、合集、雷达三页形成销售助理闭环

选择：

- 资料：管理单条资料，直接发客户。
- 合集：把多条资料打包发客户。
- 雷达：看客户反馈和跟进建议。
- 资料和合集显示创建时间，雷达显示客户行为和跟进判断。
- 客户细节集中在雷达，资料/合集只显示轻量反馈和状态入口。

原因：

- 三个底部页面需要清晰分工，避免都变成资料列表。
- 用户每天真正关心的是“发出去后有没有人看、谁该跟、下一步怎么做”。
- 状态追踪能让资料和合集从静态内容变成活的销售线索。

### 决策：P1 酷功能先用规则版收口，不等待大模型

选择：

- 发前体检、画像标签、下一句话建议、生成对比合集建议、资料/合集状态筛选先用前端规则实现。
- 雷达里的“生成对比合集建议”先跳转合集创建页，并带 `method=radar_compare` 和来源 `noteId`。
- 雷达“打开来源”和资料优化建议优先打开来源资料。
- 这批 P1 不新增后端表，不声称已经完成真实发送状态流转。

原因：

- 用户需要先看到销售助理的产品味道，而不是继续停留在资料工具。
- 规则版足以覆盖价格、位置、联系方式、案例、保障、沉默复活、反复查看等高频判断。
- 真正的 P0 闭环仍是后续“发客户 -> shareId -> 发送记录 -> 客户打开 -> 状态流转”，不能混淆。

### 决策：P0 发客户真实链路复用 ViewEvent，不新增独立发送表

选择：

- 单条资料“发客户”使用 `ViewEvent` 记录 `eventType=share`。
- `ViewEvent.viewType` 增加 `share`，并增加 `shareId/shareFromUserId/scene/referrer`。
- share 事件不计入 PV/UV，只用于“已发出”和归因。
- 客户打开资料时继续记录正常 view，并带上 `shareId`。
- owner 自己打开资料或合集不计入客户 PV/UV。

原因：

- 当前 P0 目标是打通真实闭环，不先引入新的发送记录表。
- `view_events` 已经是资料级浏览统计来源，补 share 字段能最快形成“发出 -> 打开 -> 雷达”的归因链路。
- 独立 `share_records` 表适合作为后续增强，用于记录发送对象、渠道、备注和发送状态。

### 决策：裂变文案客户友好，生成同款放在页面内承接

选择：

- 资料和合集分享标题使用“xxx｜点开查看完整资料”。
- 资料/合集列表卡片下方显示“发给客户后可看反馈；对方也能生成同款，帮你带来更多传播。”
- 公开页继续保留“生成同款”入口，承接同行、上游、潜在新用户。
- 不在客户收到的分享标题里直接写“被追踪”“客户雷达”“高意向”等后台判断词。

原因：

- 裂变很重要，但客户体验也要舒服。
- 客户收到的是一份资料，不应该第一眼感到自己被系统判断。
- “生成同款”适合在客户/同行看完内容后出现，转化更自然。

### 决策：小程序主包图片优先使用 WebP

选择：

- 首页 banner、登录图、工作台场景图等大图优先使用 WebP。
- tabbar 图标继续保留 PNG，避免微信 tabbar 兼容风险。
- 大图替换为 WebP 后，必须同步删除旧 PNG/JPG 原图，不能只新增 WebP。

原因：

- 小程序主包 2MB 限制很容易被 UI 大图撑爆。
- WebP 对当前首页雷达 banner 和场景图压缩收益明显。
- 旧图不删除仍会被计入包体，引用切换本身不能降包。

### 决策：前四个 tab 用轻规则强化销售助理闭环

选择：

- 首页负责机会总控和跳转。
- 资料页负责单条资料阶段：待补强、可发送、已发出、已打开、建议跟进。
- 合集页负责销售用途：推荐包、对比包、方案包、商品包、资料包。
- 雷达待跟进页负责客户“下一步动作”：发对比合集、轻触达、发案例保障、继续观察等。
- 雷达资料优化页负责资料“优化动作”：补价格、补联系方式、强化案例、生成对比合集建议。
- 这些增强先用前端规则，不新增后端表。

原因：

- 当前阶段更需要让用户感到“下一步很清楚”，不是继续增加入口。
- 轻规则足够支撑演示和真机体验，后续可再把规则沉到后端。
- 四个 tab 分工清楚，能避免资料、合集、雷达互相重复。

### 决策：工具页不保留无效顶部 banner

选择：

- 合集页不保留没有实际决策价值的大 banner。
- 顶部只保留轻量操作栏：当前场景、合集类型、新建按钮。
- 资料卡缩略图不能过度压缩，必须保持内容识别价值。

原因：

- 合集页是工作页，不是营销落地页；无效 banner 会占首屏，降低列表效率。
- 用户进入合集页的主要任务是新建、查看、管理和发客户。
- 资料缩略图是识别资料的重要锚点，过小会降低扫描效率。

### 决策：合集页可以保留任务型 Hero，但必须服务“打包发客户”

选择：

- 合集页顶部采用参考图比例的任务型 Hero：左侧说明“把多条资料打包发客户”，右侧用“合”视觉块建立页面心智。
- Hero 下方只保留场景标签和新建合集主按钮，不再塞方向卡、统计卡或长说明。
- 合集列表继续以创建时间、状态、用途和发客户操作为核心，不把客户画像和下一步动作放进合集页。

原因：

- 之前被否定的是无效 banner，不是所有顶部视觉都不能用。
- 合集页需要让用户一眼知道“这里是把资料打包发出去”，否则会和资料页混淆。
- 页面顶部可以有品牌感，但必须紧贴任务，不能挤压列表效率。

### 决策：资料页和合集页统一卡片语言，但不强行同尺寸

选择：

- 资料页和合集页都使用白底、细边框、`8rpx` 圆角、轻阴影和胶囊状态。
- 资料页普通卡片外露操作只保留“发客户 / 编辑 / 更多”，其他低频操作进入“更多”弹层。
- 资料缩略图保留更高识别权重，合集封面可以更轻；统一的是卡片体系，不是所有尺寸完全一致。

原因：

- 两个页面都属于原材料管理页，需要像同一套产品。
- 资料页需要快速识别单条内容，封面过小会降低扫描效率。
- 合集页更强调“包”和用途，封面可以更轻，不能为了统一牺牲资料识别。

### 决策：雷达页是客户动作台，资料/合集只负责带来源进入

选择：

- 客户“下一步动作”集中在雷达待跟进页，不放到资料页或合集页主卡。
- 资料页和合集页只保留轻量反馈入口，点击后带来源筛选进入雷达。
- 雷达待跟进主池过滤疑似同行和疑似上游；这些身份仍可在访客画像中观察。
- 来源筛选通过本地入口状态传递，因为 `switchTab` 不能可靠携带 query。

原因：

- 资料和合集是原材料管理页，雷达才是成交辅助页。
- 用户从某条资料或合集进入雷达时，最关心的是“这份内容带来的反馈”，需要自动聚焦。
- 同行/上游进入主跟进池会污染销售优先级。
### 决策：前四个 Tab 继续收口为“机会 -> 发客户 -> 打包 -> 跟进”

选择：

- 首页继续只负责“今天先做什么”和跳转，不再解释点击规则。
- 资料页主状态优先展示 `deliveryStatus`，让用户先看到待发送、已打开、客户重复查看、建议跟进。
- 资料页默认只前置“发客户状态”筛选；分类、专题、标签留在展开工具区。
- 合集页先展示销售用途，再展示发布状态和反馈状态。
- 雷达页保留 AI 助理感，但把每张卡收口为“一个主动作 + 更多”，避免按钮堆满。
- 颜色体系从单纯蓝白改为蓝、绿、橙、淡紫的轻状态色，只服务阶段感和判断感，不做花哨主题。

原因：

- 结构已经清楚，下一阶段更重要的是让用户一打开就知道现在该发什么、该看什么、该跟谁。
- 用户在四个 Tab 里最需要的是结果和动作，不是更多解释文案。
- 状态色和按钮节奏统一后，产品会更像一套稳定的成交助理，而不是多个功能页拼在一起。

### 决策：无图内容默认使用标题封面卡，不再只显示占位字

选择：

- 无图资料、无图合集、无图展示项默认用“标签 + 标题重点词”的轻封面卡展示。
- 标题重点词默认取标题中最有识别度的一段，最多 8 个字，拆成两行显示。
- 列表页、展示页和分享图尽量复用同一套标题封面语言。
- 房源、商品、服务、普通资料只通过标签和轻色调区分，不为每类单独发明完全不同的无图样式。

原因：

- 真实业务里很多群消息、合作信息、文章整理和转发内容本来就没有图片。
- 只显示“资料 / 房源 / 合集”这种占位字，美观度和识别度都不够，发给客户也显得粗糙。
- 标题封面卡能在不依赖图片的情况下保留信息感，也更利于微信群、小程序卡片和展示页统一体验。

### 决策：无图分享卡的“同款”入口只做一行次级提示

选择：

- 无图分享卡仍以“打开小程序查看完整资料/合集”为主按钮。
- “我也想做同款”保留，但只做一行更小的次级文案，不进入主按钮层级。
- 资料卡和合集卡都遵守这条规则，避免不同页面各写一套。

原因：

- 用户收到卡片时，第一目标是打开内容，不是先理解推广机制。
- 同款入口需要存在，方便裂变，但它不应该盖过内容本身。

- 雷达页在视觉升级时必须显式保留“同行过滤”这一业务信息，不允许只留在数字逻辑里、界面上却看不见。
- 前四个 Tab 这一轮先视为“风格收口完成”，后续优先切去做“我的”页内部内容和其他业务开发。

  - 资源库入口
  - 当前使用场景

- 场景切换只允许保留一个入口，不再在顶部身份卡重复出现。
- 消息入口只保留一个，放在“我的内容”里，不再在设置中心重复放“消息中心”。
- 设置与帮助暂时只保留 `个人资料 / 帮助与反馈 / 退出登录`，不再提前暴露会员、积分明细、测试入口等未成熟内容。

## 2026-06-28 五个 Tab 首屏心智与名片入口决策

- 五个 Tab 首屏必须各自回答一个问题：
  - 首页回答：今天先做什么。
  - 资料回答：哪些资料适合发客户。
  - 合集回答：把多条资料打包成一页。
  - 雷达回答：谁值得跟进。
  - 我的回答：资料、资源、消息和个人资料入口。
- 名片属于资料库，但在我的页和首页服务场景显性露出：
  - 名片不作为合集页的创建入口长期存在；合集只负责把名片、方案、案例等多条内容打成一页。
  - 电子名片作为一种资料卡保存在资料库里，可通过 `我的名片` 单独筛选。
  - 服务场景下，我的页身份卡下方显示 `我的名片` 入口；首页服务场景次动作也指向 `我的名片`。
  - 名片为空时，在资料页名片筛选空态里引导“做我的名片”。
- 原因：
  - 冷启动阶段用户第一次打开，最重要的是知道下一步点哪里，而不是看到完整功能说明。
  - 普通用户不会频繁创建很多名片，名片更像个人资产，不应该埋在合集页里。
  - 资料库负责存放可发客户的单资料，名片放在这里逻辑更顺。

  - 不做自动拉群或抓取微信群成员。
  - 不公开未查看二维码。
  - 不伪造平台统计。
- 后端正式 V1 再补持久化、二维码识别、重复校验、积分明细、反馈举报、退分扣分和审核下架。

## 2026-06-28 部署前文字减负决策

- 部署前前端不展示开发态措辞和未实现按钮：`后端 / 部署 / API Key / 本地测试 / 后续` 这类表达只允许出现在内部文档和代码变量里，不应出现在用户界面。

## 2026-06-28 生产部署方式决策

- 本次生产后端部署采用“备份 + 定向同步 + 重建镜像 + 保留回滚镜像”的稳妥方式。
- 不在服务器执行 `git pull`，因为本地工作区改动和未跟踪文件较多，直接拉 Git 难以保证线上版本等于本轮已验证范围。
- 同步时明确排除生产 `.env`、`secrets/`、媒体目录、Docker volume 和运行态数据。
- 构建前给旧镜像打回滚标签；验证完成前不做 Docker 大清理。
- 后续稳定版本应整理 GitHub release/tag，再逐步切换到标准 Git 部署流程。

原因：

- 当前阶段企业微信、会话存档、积分和资料数据都已接近真实生产，密钥和运行态数据不能被本地文件覆盖。
- 保留旧镜像可在新版本启动失败时快速回滚。
- GitHub 归档是后续必须补的安全网，但不能在当前混杂工作区里仓促完成。

## 2026-06-28 PC 运营后台 V1 边界决策

- PC 运营后台第一版先做“真实已落库数据”的运营台，不做“看起来全面但数据不真实”的假后台。
- 日报、用户排行、内容排行、系统待处理，直接复用现有后端数据模型。
- 群二维码批量上传和反馈工单，先用独立轻量运营存储承接，不强行塞进主业务模型。
- `群资源库积分 / 企业资源搜索积分 / 帮助反馈前台记录` 当前仍以小程序本地存储为主，因此：
  - 不做全局资源积分余额修改。
  - 不做资源积分全局排行。
  - 不伪造“今日资源使用人数”和“积分消耗汇总”。
- PC 端入口采用独立页面 `GET /ops`，接口统一走管理员 Token 校验。

原因：

- 这版后台的第一价值是让负责人每天看数据、看异常、做处理，而不是把尚未后端化的资源体系硬凑成后台。
- 用独立轻量存储承接二维码批量上传和反馈工单，改动范围更小，也方便后续再合并进正式资源模型。

## 2026-06-28 群二维码批量处理执行决策

- 对于“我给你一批微信群二维码，你帮我传到服务器并整理模板”的场景，优先采用 Codex 代执行方案。
- 用户不需要自己维护图床或手工回填 URL。
- 批量导入里使用的 `二维码链接` 定义为：
  - 二维码图片上传到服务器后的公网访问地址
  - 不是扫码后微信内部识别出的内容

## 2026-06-28 资源积分前端展示收口决策

- 冷启动阶段，用户只在 `我的页 -> 资源工具` 看到资源积分总余额和积分规则。
- 群资源库、企业资源搜索等子工具页面不再重复露出 `100 积分 / 积分规则`，避免用户误以为有多个积分账户。
- 小程序本地 MVP 里，企业资源搜索扣分先复用群资源库同一个本地资源积分 key。
- 正式资源积分仍需后端化，后续要统一做余额、冻结积分、流水、处罚和跨设备一致性。

原因：

- 资源工具是“资源积分”的心智入口，子工具页只负责完成任务，不应每页重复解释规则。
- 当前若多个页面都露出 `100 积分`，用户会自然理解成三套积分，影响信任。

## 2026-06-28 天眼查企业搜索接入决策

- 当前企业资源搜索第一步使用天眼查 MCP，而不是 OpenAPI REST。
- 后端统一代理 MCP，前端不保存、不传递、不展示天眼查 key。
- 第一阶段只把企业候选搜索接真实数据；企业详情里的司法风险、股东结构、历史变更等深度维度后续再按 MCP `get_company_capabilities` 返回的真实 `tool_name` 逐步接入。

原因：

- 当前 key 能初始化天眼查 MCP 并调用 `search_companies`。
- 同一个 key 调用 REST `searchV2` 返回无权限，因此 REST 通道不是当前可用方案。
- MCP 工具要求会话初始化和 `mcp-session-id`，必须由后端代理，不能让小程序直接接。

## 2026-06-28 雷达主动作决策

- 雷达页客户卡主动作不再默认是 `复制话术`。
- 用户更需要看到客户浏览痕迹、客户动态和联系方式，因此默认动作改为 `看详情` 并进入客户看板。
- 只有明确需要生成对比、补方案等业务动作时，按钮才执行对应动作。

原因：

- 复制话术是辅助功能，不是用户判断是否跟进的核心依据。
- 在客户没有联系方式或浏览证据没展开前，复制话术会显得突兀且不可验证。

## 2026-06-28 企业资源搜索冷启动积分决策

- 企业候选搜索免费。
- 企业基本信息和深度查询冷启动阶段统一轻扣 `5 分/项`。
- 同企业同功能命中 24 小时缓存时不重复扣分。
- 正式上线后的积分消耗、冻结、返还和补偿必须后端化，不能长期依赖小程序本地存储。

原因：

- 真机测试发现 `基本信息 10 分 + 深度查询 20 分/项` 会让用户点几次就消耗完 100 积分，体感过重。
- 冷启动阶段优先让用户形成“这个工具有用、可以多查几次”的心智，再逐步设计会员和高阶查询权益。

## 2026-06-29 企业微信智能机器人权限网关决策

- 企业微信智能机器人不直接连数据库，只能调用后端机器人网关。
- 后端机器人网关必须先确认消息来源身份，再决定可访问的数据范围。
- 权限先分三层：
  - `public`：天气、帮助、产品说明等公开内容。
  - `self`：我的资料、我的合集、我的资源、我的雷达等个人内容，必须绑定企微身份和小程序用户。
  - `room`：群日报、广告识别、群需求等当前群内容，必须带 `roomId`。
- `self` 查询只通过 `externalUserId/fromUserId -> ownerUserId` 的绑定关系查数据；机器人请求不得直接传入 `ownerUserId` 作为查询依据。
- 群聊里出现个人数据问题，默认要求转私聊，不在群里返回个人资料。

原因：

- 机器人真正的风险不是能不能回答，而是多人同时提问时不能串数据。
- WorkBuddy 或后续官方机器人入口只能作为“嘴巴”，不能成为可信数据库角色；可信权限判断必须在我们自己的后端完成。

## 2026-06-29 微信小程序分享卡片底部文案边界确认

已确认：

原因：

- 用户看到的底部文案是微信客户端渲染的小程序身份信息，不是我们的分享封面内容。
- 如果把这个问题误判为前端样式问题，会反复改页面但真机聊天卡片仍不变。
- 上线前要分开验收：代码侧验收标题、路径、封面图；微信后台侧验收服务类目和发布版本状态。

## 2026-06-30 分享封面生成器与机器人运营卡片生成器分层

已确认：

- 小程序正式分享封面和企业群机器人运营卡片不能混成同一套业务模板。
- 可以复用底层绘图能力，例如图片加载、文字截断、canvas/图片生成、上传、5:4 比例。
- 上层模板必须分开：
  - 小程序分享封面：用户手动发客户，强调资料/合集/名片自身。
  - 机器人运营卡片：群日报、重点资料、合集入口、资源征集，强调群运营和转化。
- 第一版机器人运营卡片优先做：
  - 中午更新卡。
  - 重点资料卡。
  - 合集入口卡。
  - 资源征集卡可后补。

原因：

- 之前卡片样式反复返工，本质风险是试验模板影响正式分享模板。
- 分层以后可以“底层复用、模板隔离”，既减少重复开发，也避免运营实验破坏小程序正式分享体验。
