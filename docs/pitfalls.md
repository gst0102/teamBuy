# Pitfalls

## 2026-06-10：组件复用时不要依赖页面提前格式化接龙数据

问题：
- 管理页会把接龙 `createdAt` 和 `followUpStatus` 预先映射成展示字段，但资源详情页可能直接把后端 `relayEntries` 传给 `relay-list`。
- 如果组件只展示 `createdText || createdAt` 和 `followUpText || followUpStatus`，资源详情页会露出 ISO 时间和 `pending` 这类内部状态值。

规避方式：
- `relay-list` 组件内部必须对原始 `createdAt` 和 `followUpStatus` 做兜底格式化。
- 页面可以继续传增强字段，但组件不能依赖页面一定提前处理。

## 2026-06-10：素材排序后要同步更新 sortOrder

问题：
- 卡片编辑页上移/下移素材时，如果只交换数组位置但保留旧 `sortOrder`，后续 `normalizeMedia()` 会按旧 `sortOrder` 再排回原位，看起来就是上下移动无效。

规避方式：
- 交换素材数组后立即按当前数组顺序重写 `sortOrder`。
- 保存 payload 时继续按当前数组顺序生成 `sortOrder`，保证前端显示顺序和后端持久化顺序一致。

## 2026-06-10：待联系提醒状态存储要兼容旧数组

状态：历史坑点。当前已升级为后端 `lead_reminders`，后续不应新增本地 storage 线索状态。

问题：

- “加入待联系”早期本地存储是用户 ID 数组。
- 现在需要支持 `pending / contacted` 状态，如果直接改成对象但不兼容旧数组，用户已有本地提醒会在升级后丢失。

规避方式：

- 读取 `viewerReminders_{cardId}` 时先归一化。
- 旧数组统一迁移为 `{ userId: "pending" }`。
- 后续如升级后端持久化，也要保留一次本地状态迁移或兜底读取。

## 2026-06-10：本地待联系提醒不是团队协作线索

状态：历史坑点。当前待联系 / 已联系 / 备注已后端持久化，但仍不是完整团队协作 CRM。

问题：

- 高意向访客的“加入待联系”当前保存在小程序本地 storage。
- 当前状态只支持本地 `pending / contacted`，不代表团队共享的待办进度。
- 如果发布者换设备、清理缓存，或多人共同跟进，同步能力不足。

规避方式：

- 当前只把它定位为个人轻量提醒，不承诺团队共享。
- 如果后续要多人协作或长期备注，需要新增后端待办/备注模型和接口。

## 2026-06-10：登录访客列表不要把重复访问拆成多条普通访客

问题：

- 如果同一用户多次访问被拆成多条记录，管理页会显得拥挤，也无法直接识别重复访问带来的意向信号。
- 如果只去重但不记录访问次数，又会丢失高意向判断依据。

规避方式：

- 后端 stats 按登录用户聚合访客，返回 `viewCount` 和最新 `viewedAt`。
- 前端用 `viewCount >= 2` 且未接龙作为高意向提示。
- 已接龙访客单独标记，避免和“未接龙高意向”混在一起。

## 2026-06-10：待跟进和全部名单不要长期双列表展示

问题：

- 如果管理页同时展示“待跟进新线索”和“全部接龙名单”，同一条待跟进线索会重复出现。
- 发布者处理一条线索后，页面视觉上仍可能显得混乱。

规避方式：

- 使用“待跟进 / 已跟进 / 全部”三段筛选承载同一份线索数据。
- 默认展示待跟进；已处理线索通过筛选回看。
- 待跟进线索保留高亮样式，但不再单独复制一份列表。

## 2026-06-10：线索快捷动作只能出现在发布者视角

问题：

- 电话、地址属于客户留资字段，不能因为组件复用而出现在普通客户视角。
- 如果快捷动作不绑定 `isOwner`，复制电话、复制地址可能成为隐私泄漏入口。

规避方式：

- `relay-list` 只有 `isOwner=true` 时才渲染电话、地址和快捷动作。
- 非发布者接口仍保持电话、地址置空，前后端都不依赖单层保护。

## 2026-06-10：发布者跟进后，客户页不能一直停留在“已提交”

问题：

- 如果发布者已经标记已跟进，但客户打开资源页仍只看到“已提交”，客户感知不到后续处理进度。
- 这会让“标记已跟进”只成为发布者内部状态，无法形成客户侧闭环。

规避方式：

- stats 返回当前用户自己的 `currentUserRelay`，包含 `followUpStatus`。
- 客户页根据 `followUpStatus` 显示“已提交”或“已跟进”。
- 后端回归覆盖发布者标记跟进后，客户 stats 能读到 `followed`。

## 2026-06-10：接龙提交成功后必须给客户稳定反馈

问题：

- 如果提交成功后仍显示输入框和“提交接龙”按钮，客户会以为没有提交成功，容易重复点击或重复留资。
- 只靠前端禁用按钮不够，刷新页面或换入口后仍可能再次提交。

规避方式：

- stats 返回当前用户自己的接龙记录，页面加载后即可恢复“已提交”状态。
- 后端按 `cardId + userId + active` 做重复保护，重复提交返回 409。
- 发布者侧把 pending 线索单独高亮，避免新线索淹没在全部名单里。

## 2026-06-10：前端隐藏隐私字段时，后端也必须继续脱敏

问题：

- 客户视角前端不展示接龙名单，并不等于接口数据就一定安全。
- 后续如果页面或组件复用不小心把 `relayEntries` 渲染出来，可能重新暴露电话、地址或完整昵称。

规避方式：

- 后端 stats/list relays 接口继续按 requester 是否为 `card.ownerUserId` 判断权限。
- 非发布者只返回脱敏昵称，电话和地址置空。
- `relay-list` 组件也只在 `isOwner=true` 时渲染电话和地址，形成页面和组件两层防护。

## 2026-06-10：不要把团长访问详情入口暴露给普通查看用户

问题：

- 资源详情页既是客户看到的正式分享页，也是团长可能回看数据的入口。
- 如果“访问详情”在分享页对所有人可见，普通客户会看到本不属于他的管理入口，容易造成权限和隐私误解。

规避方式：

- 前端只在当前登录用户是 `card.ownerUserId` 时展示“访问详情”。
- 跳转管理页的方法里也保留发布者校验提示，避免入口状态异常时误跳转。

## 2026-06-10：发布后补素材不能回退到创建流程

问题：

- 资源发布后仍可能继续补图片、补视频。
- 如果只能回创建页上传，用户会误以为要重新建一条资源，旧资源的数据、访问和接龙上下文也会被打断。

规避方式：

- 编辑页直接提供继续上传入口。
- 新素材仍进入当前卡片 `media`，通过保存修改写回同一资源。
- 继续明确首图/封面图和详情素材的展示规则。

## 2026-06-09：WXML 属性里的实体标题会直接显示出来

问题：

- 自定义导航如果写成 `title="&#x60A6;..."`，页面上会直接看到实体字符串，而不是中文标题。

规避方式：

- 不要把导航标题依赖在 WXML 属性实体串上。
- 统一改为组件内部根据当前页面路由映射标题，或者通过页面 data 传纯文本。

## 2026-06-09：多图上传如果不明确“封面图”规则，用户会误判资源页展示结果

问题：

- 用户上传多张图片时，不知道哪一张会出现在资源页首页，也不知道其他素材会落到哪里。

规避方式：

- 首张图片默认设为封面。
- 上传列表中明确标记“封面图 / 详情图 / 详情视频 / 详情附件”。
- 提供“设为封面”操作，让结果可控。

## 2026-06-09：Pydantic `model_dump()` 后的嵌套对象不一定还是模型

问题：

- `CardUpdateRequest.model_dump()` 之后，`relayConfig` 已经是普通 `dict`。
- 如果继续对它调用 `value.model_dump()`，后端会直接抛异常，前端看到的就是 `PUT /api/cards/... 500`。

规避方式：

- 更新卡片时，对嵌套对象先判断是否有 `model_dump()`，否则按 `dict` 直接使用。
- 这类保存链路必须补回归测试，不要只靠前端手点验证。

本文件记录项目踩坑、错误原因和避免方式。新 Codex 会话开始前必须读取。

## 2026-06-08：微信笔记没有专门消息类型

问题：

企业微信客服不会直接收到一个完整的“微信笔记对象”。

原因：

用户转发微信笔记后，企业微信客服侧更可能收到多条文本、图片、链接、位置、视频等消息。

正确做法：

- 使用企业微信回调触发处理。
- 通过 `sync_msg` 拉取消息。
- 按同一 `external_userid`、同一客服会话、60 秒时间窗口聚合消息。
- 聚合后再生成卡片草稿。

## 2026-06-08：media_id 有时效，必须及时转存

问题：

企业微信图片、视频等媒体 `media_id` 有时效，过期后无法下载。

正确做法：

- 收到真实消息后尽快下载并转存到本地或对象存储。
- 下载失败要写入补偿队列。
- 卡片中保存持久化后的 URL，不直接依赖 `media_id`。

## 2026-06-08：不要把匿名用户展示为实名浏览用户

问题：

未登录用户无法稳定获取头像昵称。

风险：

错误展示身份会造成统计和隐私风险。

正确做法：

- 匿名用户只计入 PV/UV。
- 只有已登录用户进入浏览用户列表。

## 2026-06-08：一键复用不能污染原卡片数据

问题：

如果复用时直接复写原卡片，会破坏历史浏览和接龙数据。

正确做法：

- 复用必须创建新卡片 ID。
- 新旧卡片浏览统计、接龙名单独立。
- 新卡片可保留 `sourceCardId` 指向原卡片。

## 2026-06-09：企业微信真实 sync_msg 返回 48002 api forbidden

问题：

真实 `sync_msg` 手动触发时返回：

```text
errcode=48002
errmsg=api forbidden
from ip=81.70.84.35
```

当前判断：

代码已经请求到企业微信接口，更像企业微信后台权限或配置问题。

排查方向：

- `WECOM_SECRET` 是否为微信客服对应 Secret。
- 企业微信后台是否开启“微信客服 - 通过 API 管理微信客服帐号”。
- `WECOM_OPEN_KFID` 对应客服账号是否允许 API 管理。
- 企业微信可信 IP/白名单是否包含 `81.70.84.35`。
- 当前企业/应用是否具备微信客服相关 API 权限。

## 2026-06-09：当前工作区有未提交 UI/产品化改动

问题：

当前工作区存在已修改小程序文件和未跟踪 UI/产品化文档、图片、页面目录。

风险：

新会话如果直接覆盖、删除或乱提交，可能破坏阶段三已有成果。

正确做法：

- 先读取 `git status`、`git diff`、未跟踪文件列表。
- 不要批量删除。
- 先确认哪些改动保留、拆分提交或回退。

## 2026-06-09：不要把客服侧边栏发卡片混入 v0.1 主链路

问题：

企业微信客服侧边栏/H5 发小程序卡片能力有用，但官方能力边界和配置要求仍需实测。

正确做法：

- v0.1 继续以“小程序内编辑后分享卡片”为主链路。
- 客服侧边栏/H5 发卡片只作为 P2 技术预研。
- 不要为了该能力提前引入完整 PC 管理后台。

## 2026-06-09：UI 产品化文案不要承诺尚未实现的数据能力

问题：

小程序首页、访问记录和我的页容易为了产品化效果写出“今日访问”“智能整理”“邀请权益”等像真实能力的文案。

风险：

后端当前没有真实分日统计、AI 智能整理、会员权益或邀请奖励接口，文案过度会导致验收误判。

正确做法：

- 没有分日接口时使用“访问”“总访问”等聚合表述。
- “智能整理”改为“自动整理”或明确后续开放。
- 会员、邀请、标签管理只做占位提示，不伪造真实数据。

## 2026-06-09：手动添加不能替代企业微信导入主链路

问题：

企业微信认证和权限配置暂时受阻时，容易把手动添加资源当作主链路完成。

风险：

项目差异点仍是企业微信客服接收微信笔记和链接后自动归档。只做手动添加会偏离 v0.1 的核心验证目标。

正确做法：

- 手动添加只作为临时可用入口和本地验收链路。
- 企业微信客服回调 + `sync_msg` + 消息聚合 + 待认领仍是核心主链路。
- 企业微信认证问题解决后，继续优先排查 `48002 api forbidden`。

## 2026-06-10：不要在小程序内做“发给客服”入口

问题：

小程序里如果出现“发给客服”“立即发给客服”“去发给客服”入口，会让用户误以为需要先进入小程序，再把资料发给企业微信客服，然后再回到小程序编辑。

正确做法：

- 企业微信客服导入发生在小程序外部会话。
- 小程序内中间加号是“添加 / 快速入库”，用于手动录入资料。
- `pages/imports/index` 只展示外部导入后的待认领草稿，不展示 mock 导入按钮，不作为发送入口。

## 2026-06-10：不要把本机缓存路径写回资料库

问题：

为了减少服务器读取压力，小程序会把图片和视频缓存到用户手机。如果直接把资源 `url` 替换成本机路径，保存卡片时可能把 `wxfile://` 或本地缓存路径写回后端。

正确做法：

- 资源数据里的 `coverUrl` 和 `media[].url` 始终保留后端返回的正式 URL。
- 页面展示使用 `coverDisplayUrl` 和 `media[].displayUrl`。
- 保存、发布、复用时只提交正式 URL，不提交本机缓存路径。

## 2026-06-10：不要把原图原视频直接落后台

问题：

房源和团购资料常包含大量图片/视频，原文件直接保存会让服务器磁盘和带宽压力过大。

正确做法：

- 图片上传后压缩成展示用 WebP。
- 视频上传后用 ffmpeg 转成 H.264/AAC MP4。
- v0.1 默认只保留压缩后的展示文件；确实需要原文件归档时再单独设计对象存储策略。

## 2026-06-10：高意向访客跟进状态不要再写小程序本地 storage

问题：

待联系 / 已联系 / 备注如果只存在小程序本地 storage，用户换手机、清理缓存或重新安装小程序后都会丢失。

正确做法：

- 管理页高意向访客操作调用后端 `lead-reminders` API。
- 统一“待联系”列表也从后端读取，不做独立本地副本。
- 小程序本地缓存只用于图片/视频展示加速，不用于保存业务跟进状态。

## 2026-06-10：待联系列表不要只跳线索管理页

问题：

待联系线索卡片如果只提供“打开资源”并跳到管理页，用户会分不清这是客户看到的资料详情，还是发布者后台线索管理。

正确做法：

- 卡片上明确展示“来源资料”。
- “资源详情”跳 `pages/card-view/index`。
- “线索管理”跳 `pages/manager/index`。

## 2026-06-10：跟进记录不要覆盖备注

问题：

备注是线索的长期摘要，跟进记录是一次次沟通流水。如果把每次跟进直接覆盖备注，后面会丢失处理过程。

正确做法：

- `note` 继续作为线索摘要。
- `followUpLogs` 追加保存每次跟进内容。
- `nextFollowUpAt` 单独保存下次处理日期。

## 2026-06-10：待联系列表不要只按更新时间排序

问题：

如果线索只按更新时间排序，今天该跟进和已经逾期的线索会被新保存备注的普通线索挤下去，发布者容易漏处理。

正确做法：

- 待联系页优先按跟进状态排序：逾期、今日、未来、未设置、已完成。
- 再按下次跟进日期和更新时间排序。
- 当前先做前端排序；数据量变大后再补服务端分页和排序参数。

## 2026-06-10：页内提醒稳定前不要急着接微信通知

问题：

微信订阅消息需要用户授权、模板配置、发送时机和审核说明。如果待联系页内的提醒逻辑还没稳定，先接通知会增加调试面。

正确做法：

- 先在待联系页做今日、逾期、未处理的醒目提醒和快捷筛选。
- 确认跟进日期、状态筛选、已联系流转稳定后，再设计微信订阅消息。

## 2026-06-10：归档结论不要覆盖跟进记录

问题：

无效、暂不跟进、已完成是线索结论；备注和跟进记录是过程信息。如果用备注字段保存结论原因，后续复盘会分不清过程和结果。

正确做法：

- `conclusionReason` 保存归档原因。
- `closedAt` 保存归档时间。
- `followUpLogs` 继续保存沟通过程。
- 恢复待联系时清空 `conclusionReason` 和 `closedAt`，但保留历史跟进记录。

## 2026-06-10：待联系列表不要重新塞满编辑表单

问题：

待联系列表如果同时承载备注、跟进记录、下次跟进、归档原因和所有结论动作，会变成很长的表单列表，发布者很难快速扫线索。

正确做法：

- 列表页只放摘要和关键动作。
- 单条线索的完整编辑放进 `pages/lead-detail/index`。
- 后续新增字段优先加到详情页，列表页只加必要摘要。

## 2026-06-10：客户资料字段先保持发布者私有

问题：

手机号、微信号、预算、意向等级属于客户资料。如果在没有权限模型时做团队共享，容易产生隐私和误用风险。

问题：

如果客户资料库把所有线索都列出来，会和待联系页重复，用户也分不清哪些是真正沉淀过的客户资料。

正确做法：

- 客户资料库只展示至少填写了手机号、微信号、预算或意向等级的线索。

## 2026-06-10：客户资料搜索先不要做全局搜索

问题：

客户手机号和微信号属于发布者私有资料。如果搜索跨发布者或跨团队，会引入权限和隐私风险。

正确做法：

- 当前客户资料库只搜索当前发布者自己的线索。
- 前端只在已加载的私有客户资料列表里筛选。
- 后续要做后端搜索时，必须继续按 `ownerUserId` 隔离。

## 2026-06-10：客户筛选条件要可叠加

问题：

如果排序、意向等级、资料完整度和搜索各自覆盖结果，用户会觉得筛选条件“互相打架”。

正确做法：

- 客户资料库统一通过一个过滤/排序管线生成列表。
- 搜索、意向等级、有电话/有微信/有预算、排序模式需要叠加生效。

## 2026-06-10：客户摘要复制要基于当前筛选结果

问题：

如果“复制客户摘要”复制全量客户，而页面当前展示的是筛选后的客户，会让用户误以为复制错了。

正确做法：

- 摘要内容基于 `filteredCustomers`。
- 复制前如果当前筛选结果为空，需要提示暂无可复制客户。

## 2026-06-10：单个客户档案复制不要只复制联系方式

问题：

只复制电话或微信不能表达客户上下文，后续粘贴到聊天或表格里还要补备注、意向和来源资料。

正确做法：

- 单个客户档案复制应包含姓名、联系方式、预算、意向等级、来源资料、状态、备注和最近跟进。
- 批量客户摘要和单个客户档案复制保持不同用途。

## 2026-06-10：客户标签不要和资源分类标签混用

问题：

资源标签用于资料卡片分类，客户标签用于发布者私有客户经营。如果混用，客户筛选、资源筛选和后续权限边界都会变模糊。

正确做法：

- 客户标签保存在 `LeadReminder.customerTags`。
- 资源分类标签继续保存在资源卡片分类体系。
- 客户资料库的标签筛选只基于客户标签，不读取资源标签。

## 2026-06-10：客户资料库快捷动作不要扩展成完整表单

问题：

如果把备注、归档、客户资料、跟进时间线都塞回客户资料库卡片，列表页会重新变得难扫，和线索详情页拆分的目标冲突。

正确做法：

- 客户资料库只保留设为今日跟进、添加一条跟进记录、标记已联系这类轻量动作。
- 多字段编辑、归档原因、完整跟进时间线仍放在线索详情页。

## 2026-06-10：沉睡客户筛选不要包含已有结论客户

问题：

如果“14 天未跟进”把无效或已完成客户也捞出来，发布者会重复触达已经结束的客户。

正确做法：

- 沉睡客户基于最近跟进时间判断。
- 无效和已完成客户不进入沉睡筛选。
- 需要查看归档客户时，继续使用待联系/线索列表里的归档筛选。

## 2026-06-10：批量触达准备不要绕过当前筛选结果

问题：

如果“复制跟进清单”复制全量客户，而页面当前展示的是活跃/沉睡/标签筛选后的客户，会造成误触达。

正确做法：

- 跟进清单必须基于 `filteredCustomers`。
- 空筛选结果要提示暂无可复制清单。
- 未接群发接口前，只复制文本，不做自动触达。

## 2026-06-10：常用视图不要误当成客户数据持久化

问题：

常用视图只是筛选偏好。如果把它和客户资料一样对待，会让后续跨设备一致性和权限边界变复杂。

正确做法：

- 当前常用视图保存在小程序本地 storage。
- 客户资料、线索、跟进记录继续以后端为准。
- 后续如用户明确需要跨设备同步常用视图，再单独设计后端偏好接口。

## 2026-06-10：客户卡片不要继续平铺所有信息

问题：

客户资料库能力增加后，如果电话、微信、预算、来源、查看、跟进、动作全部平铺，用户很难快速扫出当前应该处理谁。

正确做法：

- 客户资料、跟进状态、来源资料、操作区分块展示。
- 高频动作保留在主操作区。
- 查看详情、资源详情等低频动作放在次级操作区。

## 2026-06-09：轻量资源标签不要扩展成 CRM 标签系统

问题：

参考图里有“标签管理”，但 v0.1 当前只需要资源库分类筛选，不需要完整客户标签、批量打标、标签规则和 CRM 跟进体系。

正确做法：

- 本阶段标签只绑定资源卡片 `categoryIds`。
- 标签管理只做新增、删除和筛选。
- 不把客户标签、会员标签、收益标签混入当前资源库标签。

## 2026-06-09：验收不要把“自动化通过”误判为“上线通过”

问题：

后端 `pytest`、小程序 JS/JSON 静态检查和 mock 链路通过，容易被误认为 MVP 已经可以上线。

风险：

真实企业微信 `sync_msg`、真实 media_id 下载、真实微信登录、电话拨号、字段复制、群分享打开、接龙提交等 P0 能力仍需要真实环境或微信开发者工具/真机确认。若提前标记通过，会掩盖上线阻断风险。

正确做法：

- 后端自动化通过只代表本地逻辑回归通过。
- 企业微信导入主链路必须以真实 `sync_msg` 成功作为 P0 通过依据。
- 小程序端 P0 交互必须有微信开发者工具或真机验收记录。
- P0 未全部覆盖时，AI 测试官结论只能是“不通过”或“需要人工确认”，不能写“通过”。

- 手动上传资源需要单独落到本地 `/media`，不要和企业微信真实 `media_id` 转存链路混在一起。

### 坑点：小程序上传返回相对 `/media/...` 地址时，前端不会自动预览

- 原因不是上传失败，而是 `image` / `video` 组件拿到的是相对地址，微信小程序不会替你补上 `apiBaseUrl`。

## 2026-06-10：企业微信不同客服回调不要共用同一个 URL

问题：
- 如果多个客服或应用共用 `/api/wecom/callback`，但后台配置的 Token、EncodingAESKey 或事件来源不同，企业微信保存配置时可能请求到同一个后端入口却按错误密钥校验，表现为“openapi回调地址请求不通过”。

正确做法：
- teamBuy 当前客服使用 `/api/wecom/kf/teamBuy/callback`。
- 后续新增客服或其他回调时继续拆分独立路径，例如 `/api/wecom/kf/{name}/callback` 或 `/api/wecom/oauth/{name}/callback`。
- 企业微信后台、后端配置检查、部署文档和测试用例必须同步同一个回调路径。
## 2026-06-10：企业微信回调 URL 验证不能返回 JSON 字符串

问题：
- 企业微信保存回调 URL 时，即使后端日志显示 `GET /callback?...` 返回 200，如果响应体不是原样纯文本 `echostr`，仍会提示 `openapi回调地址请求不通过`。
- FastAPI 路由直接 `return "xxx"` 会返回 JSON 字符串，正文可能带引号，不符合企业微信 URL 验证预期。

正确做法：
- URL 验证 GET 接口使用 `PlainTextResponse`。
- 加密验证场景下返回解密后的 `echostr` 明文；非加密测试场景下返回 query 里的 `echostr` 明文。
- 排查时同时看 HTTP 状态码、`content-type` 和响应体原文，不能只看 200。

## 2026-06-15：提交前不要把运行态、本地配置和换行符扰动混进业务修复

问题：
- `backend/mock/runtime-state.json` 会被本地手动测试大量改写，容易把 mock 运行态污染提交进去。
- `docs/png/` 是页面参考图目录，体积较大，不属于业务修复。
- `miniprogram/project.config.json` 和 `project.private.config.json` 是微信开发者工具本地配置，不应默认提交。
- 大文档如果只有换行符或行尾空白变化，会制造几千行无意义 diff，掩盖真正的代码改动。

正确做法：
- 提交前先用 `git status --short --branch`、`git diff --stat` 和 `git diff --name-only` 拆分范围。
- 只 stage 本轮业务修复相关文件；运行态、参考图、本地配置和未确认草稿保留在工作区但不提交。
- 遇到测试失败、部署失败、配置误判或提交范围风险，必须写入 `docs/dev-log.md`、`docs/decisions.md`、`docs/pitfalls.md`、`docs/handoff-latest.md` 中对应位置。

## 2026-06-15：本地后端测试不要依赖系统 Python 3.9 或不存在的 Pillow 版本

问题：
- 当前 shell 可能没有 `python` 和 `pytest` 命令，直接运行项目推荐命令会失败。
- macOS 系统 `python3` 可能是 3.9，跑后端测试会在 `dataclass(slots=True)` 处失败；项目需要 Python 3.10+。
- `Pillow==12.2.0` 当前包源不可安装，会导致新虚拟环境或镜像构建在安装依赖阶段失败。

正确做法：
- 本地验证优先使用 Codex 提供的 Python 3.12 运行时，或项目自建 Python 3.10+ 虚拟环境。
- 依赖安装失败时先确认版本是否存在，不要把安装失败误判为业务测试失败。
- 后端依赖固定为当前可安装版本 `Pillow==11.3.0`，后续升级需先确认包源可用再改。

## 2026-06-15：真实媒体下载失败时不能生成 mock 媒体 URL

问题：
- 真实 `sync_msg` 拉到图片/视频后，如果企业微信 `media_id` 下载失败，旧逻辑会先记录补偿队列再抛错，导致整批导入失败。
- 修复为继续导入后，又发现导入阶段会对缺失 URL 的 `media_id` 走 mock storage fallback，生成 `/mock-media/...`，容易让验收误以为真实媒体已转存成功。

正确做法：
- 真实链路中媒体下载失败只记录 `media_retry_jobs`，不阻断文本、链接、位置等内容生成待认领草稿。
- 真实链路调用 `import_synced_messages()` 时必须关闭媒体存储 fallback；卡片只保存真实转存成功的媒体 URL。
- mock 链路可以保留 fallback，便于本地演示，但不能把 mock 行为带到真实企业微信验收口径。

## 2026-06-15：图片压缩不要完全依赖 ffmpeg

问题：
- 在当前本地测试环境中，图片处理完全依赖 ffmpeg 时会回退原图，导致 `contentType=image/webp` 但文件名仍是 `.png`、`compressed=false`。
- 这种状态会让上传接口看起来返回了 WebP 类型，实际却没有稳定完成 WebP 转换。

正确做法：
- 图片压缩使用 Pillow 打开、缩放并保存为 WebP。
- 视频转码继续使用 ffmpeg。
- 图片压缩测试必须检查 `contentType=image/webp`、文件名 `.webp`、最大边限制和 `compressed=true`。

## 2026-06-17：插件化架构不要把文字整理拆成多个重复 Skill

问题：

- 微信笔记、聊天记录、链接文章从产品入口看不同，但核心都是“内容对象转用户笔记”。
- 如果拆成 `wechat-note-to-card`、`chat-to-summary-note`、`link-to-summary-note`，会让路由、模板、测试和后续付费权益重复维护。

## 2026-06-17：Skill 执行失败不能只靠异常返回

问题：

- 企业微信真实导入是异步或后台任务场景，用户不一定能看到当时接口异常。
- 如果 `content-to-note` 失败只抛异常，后续排查无法知道是哪批消息、哪个 Skill、什么输入导致失败。
- 后续计费和权益控制也需要稳定的 Skill 执行记录。

正确做法：

- 成功和失败都写入 `SkillRun`。
- 失败时同时写入失败导入通知。
- `inputSnapshot` 至少包含导入批次、原始消息 ID 和必要输入快照。
- 提供查询接口，不要让失败只存在日志文件或终端输出里。

## 2026-06-17：导入失败重试和媒体失败重试不要混在一起

问题：

- 内容整理失败需要重新执行 `content-to-note`。
- 媒体下载失败需要重新下载和转存 media_id。
- 如果都用一个“重试”按钮处理，容易把已经成功生成的文本草稿重复生成，或把媒体失败误判成内容整理失败。

正确做法：

- 导入失败重试入口使用 `importBatchId`，读取原始消息后重跑内容整理。
- 媒体失败重试入口继续使用 `mediaId` 或媒体失败状态，重跑下载和存储。
- 重试看板可以统一展示两类失败，但动作必须分开。

## 2026-06-17：上线 UserNote 时不要立刻移除 generatedCard

问题：

- 当前小程序待认领、编辑、发布、分享和线索功能仍依赖 `Card`。
- 如果正式 `UserNote` 上线时立刻移除 `generatedCard`，会破坏已有 P0 小程序链路。

正确做法：

问题：

- 会话内容存档是归档/拉取通道，不是客服回复通道。
- 如果把“处理完成后回复微信消息”混进会话存档逻辑，会误以为归档接口具备发送能力。

正确做法：

- 入库处理成功和通知用户分成两个独立步骤。
- 通知可选通道：
  - 企业微信应用消息，先通知内部成员。
  - 微信客服消息，等待客服通道权限打通后通知外部联系人。
  - 小程序订阅消息，等待小程序用户绑定后通知用户。
- 通知失败只记录失败和重试，不回滚已生成的 `UserNote`。

## 2026-06-18：会话存档 GetMediaData 读取二进制不能按字符串处理

问题：

- 官方 C SDK 的 `GetMediaData` 返回 `MediaData_t`，包含 `data` 指针和 `data_len`。
- 图片、视频是二进制内容，如果把 `GetData()` 结果当 `c_char_p` 或按 C 字符串读取，可能遇到 `\0` 截断，导致图片损坏。
- `outindexbuf` 也必须按 SDK 返回的长度传给下一次调用，直到 `IsMediaDataFinish()` 为真。

正确做法：

- ctypes 绑定时：
  - `GetData.restype = c_void_p`
  - `GetOutIndexBuf.restype = c_void_p`
  - 分别结合 `GetDataLen()`、`GetIndexLen()` 用 `ctypes.string_at(ptr, len)` 读取。
- 每次调用后必须 `FreeMediaData(media_data)`。
- 下载失败只记录 `media_retry_jobs`，不能让文字笔记入库失败。

## 2026-06-18：sdkfileid 不能原样拼进媒体文件名

问题：

- 企业微信会话存档的 `sdkfileid` 可能非常长。
- 历史媒体回填时，旧文件名规则把完整 `sdkfileid` 拼进本地文件名，生产报错：
  - `[Errno 36] File name too long`
- 这会导致媒体已经下载成功，但保存到 `/media` 时失败。

正确做法：

- `build_media_file_name()` 对清洗后的媒体 ID 做长度限制。
- 超过 80 字符时保留短前缀，并追加 `sha256(media_id)` 的短 hash。
- 文件名既可追溯一部分来源，又不会超过常见文件系统单文件名长度限制。

## 2026-06-18：identity-core 第一版不要假装已经完成正式微信身份体系

问题：

- 当前小程序登录仍是 mock 登录，不是正式微信 code 换 openid/unionid。
- 企业微信会话存档里的外部联系人 ID、企业微信客服的 external user ID、小程序 openid/unionid 不是天然同一个 ID。
- 如果直接把“认领后绑定”描述成完整身份体系，会误导后续上线判断。

正确做法：

- P0 第一版只承诺：
  - 用户认领导入后，保存 `externalUserId -> ownerUserId` 的绑定。
  - 后续同来源资料自动进入该用户笔记库。
- 文档和验收中必须明确：
  - 这是“认领后补绑定”，不是正式微信登录身份打通。
  - 后续仍需接正式微信登录、unionid 或企业微信客户绑定管理。

## 2026-06-18：远程 SQL 检查少写嵌套转义

问题：

- 通过 SSH 在远程 shell 里再调用 `psql -c "select to_regclass('public.table')"` 时，嵌套引号和反斜杠很容易被 shell 改坏。
- 本轮首次检查 `wecom_identity_bindings` 表时 SQL 变成了非法的 `to_regclass(\public...)`。

正确做法：

- 远程单行 SQL 尽量用简单查询，减少嵌套引号：
  - `select count(*) from information_schema.tables where table_schema='public' and table_name='wecom_identity_bindings';`
- 或者把 SQL 放进 heredoc，避免多层 shell 转义。

## 2026-06-18：不要把所有 URL 都自动深度整理

问题：

- 产品已确认普通文章 URL 默认是“轻收藏”，不是立刻抓全文、摘要、结构化成深度笔记。
- 如果路由测试或导入逻辑仍把任意 URL 当作 `content-to-note`，用户随手收藏一篇文章时会变成重处理流程。
- 但 `整理链接` 这类明确指令又必须保持深度整理，不能因为轻收藏策略误伤快捷命令。

正确做法：

- 路由顺序保持：精确指令优先，其次规则识别 URL 轻收藏，AI 兜底最后。
- 普通 URL 返回 `link_bookmark` / `link-bookmark`，输入适配器仍是 `input.link-article`。
- 明确命令 `整理链接` 等继续返回 `content_to_note` / `content-to-note`。
- 后端导入时只在无深度整理关键词的链接内容上走轻收藏；小程序再提供“整理为笔记”的升级动作。
