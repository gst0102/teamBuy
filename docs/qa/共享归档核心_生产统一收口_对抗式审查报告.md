# 共享归档核心生产统一收口：对抗式审查报告

日期：2026-08-16

## 审查对象与成功标准

审查对象是 teamBuy、PetLove 与共享企业微信会话存档核心的生产迁移：只能有一个 Finance SDK Worker 和企业级 `seq` 游标；项目只能收到自己的路由事件；项目必须先落库再 ACK；媒体必须按项目令牌隔离；核心中转原文按 24 小时清理；回滚不能造成双 Worker 并行。

## 结论

生产统一收口已完成，未发现阻断性 P0 问题。共享核心、两个项目消费者和唯一 Nginx 回调均已运行；teamBuy 历史投递已清空 pending。

- 共享核心 API、Worker、独立 PostgreSQL 均运行，核心 `/health` 返回 200。
- 核心状态为 `teamBuy`/`petlove` 两个项目、`rawRetentionHours=24`，游标停在 392。

## 发现与处置

1. 生产 teamBuy 进程未自动加载挂载文件更新，导致共享事件暂时返回 500。已显式重启 API/归档处理进程，并用运行时函数签名确认新接口已加载；重试后 81 条投递全部成功。
2. 共享核心路由原先只能表达群 ID，无法安全表达一对一消息。已增加 `includeDirectMessages`、`fromUserIds`、`toUserIds`，并为 teamBuy 配置显式一对一接收开关。
3. PetLove 当前配置群未出现在核心历史批次，因此尚未声称 PetLove 真实消息链路已人工验收。

## 剩余风险与人工验收

- 需要负责人在生产发送一条 PetLove 配置群消息，确认核心投递、PetLove 业务入库、2xx ACK、重复事件幂等和图片媒体读取。
- 需要负责人发送一条 teamBuy 一对一客户/资料消息，确认 `includeDirectMessages` 路由和 teamBuy 业务处理。
- teamBuy 当前一对一路由未限制 `toUserIds`；在新增第二个也处理私聊的项目之前，必须补充项目对应的企业微信成员 ID，禁止复制该全量私聊开关。
- 当前根分区使用率约 84%；未执行 Docker prune，后续需单独安排磁盘治理，不在本次迁移中清理运行态数据。

## 回滚边界

先停止共享核心 Worker，再将目标项目切回 `WECOM_ARCHIVE_SOURCE=direct` 并恢复原 Finance SDK 配置/游标；任何回滚都不得让共享 Worker 与项目直拉 Worker 同时运行。
