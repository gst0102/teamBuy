# 房源中介对盘群增长 MVP 开发文档

更新时间：2026-06-25

## 1. 背景

首批目标用户聚焦租房中介和二房东。用户已有多个房源对盘群，可通过真实房源卡和房源合集自然种草。

当前阶段不再平均推广四个工作台，而是对外采用“资料整理助手 · 房源版”心智：帮助租房中介把群里的房源整理成自己的房源卡和房源合集。

## 2. 产品目标

第一版只打穿一个核心闭环：

```text
对盘群看到房源合集/房源卡
  -> 点开查看清单
  -> 点击“我是中介，也想生成这种合集/房源卡”
  -> 补自己的微信号
  -> 默认把发布者作为上游联系人，可自行修改
  -> 复制给企业微信助手继续生成自己的版本
```

## 3. 用户与场景

- 主用户：租房中介。
- 主战场：同行对盘群。
- 主联系方式：微信号，手机号为次要。
- 第一版生成同款允许半自动：老用户可自动带入已有资料，新用户补微信号。

## 4. 首批模板

第一批房源合集主推两个模板：

- 清单对比：适合对盘群，突出租金、户型、商圈、可看状态。
- 精选橱窗：适合客户和朋友圈，突出大图、主推房源和专业感。

## 5. 本轮开发范围

### 5.1 房源版聚焦

- 小程序默认进入房源工作台。
- 隐藏日常资料、团购/商品、服务三个工作台的主动切换入口。
- 不删除其他三个工作台代码和配置。
- 首页文案改为租房中介对盘语境。

### 5.2 合集页中介转化入口

- 房源合集公开页增加“我是中介，也想生成这种合集”入口。
- 入口不影响普通客户查看房源。
- 点击后进入生成同款确认页。

### 5.3 房源页中介转化入口

- 单套房源客户页增加“生成同款房源卡”轻入口。
- 点击后进入生成同款确认页。

### 5.4 生成同款确认页

页面展示：

- 生成对象：房源合集或房源卡。
- 对外联系方式：当前用户微信号；没有则用户填写。
- 上游联系人：默认当前发布者，可修改。
- 隐私说明：只复制公开房源内容，不复制发布者私密联系人。
- 主动作：复制给企业微信助手。

第一版只做半自动引导，不承诺已经完成后端完整克隆。

## 6. 隐私规则

- A 中介私密保存的真实房东/二房东联系方式默认不继承给 B。
- B 生成同款时，B 的上游联系人默认是 A 中介，但 B 可自行编辑。
- 客户公开页不展示“隐藏了房东联系方式”。
- 上游联系人说明只出现在发布者管理态或生成同款确认页。

## 7. 暂不做

- 不删除其他三个工作台。
- 不做正式支付、分佣、会员权益。
- 完整后端克隆接口已完成底座版：支持公开房源卡/房源合集生成 B 名下正式房源卡/合集；前端仍需接入直接调用。
- 媒体资产 hash 去重落库已完成底座版：新进入系统的图片/视频会写入 `MediaAsset` 并复用相同 hash 资产；历史媒体仍需后续离线回填。
- 不把匿名访客包装成实名客户。

## 7.1 后续后端必须补齐

企业微信接收我们自己的小程序房源卡/房源合集时，不能退化成只识别标题。

后端需要识别小程序 `pagePath` 中的内部 `noteId/showcaseId/sourceNoteId` 等标识，并回查完整公开结构：

- 单套房源：标题、租金、户型、面积、位置、图片/视频、公开描述、发布者公开联系方式。
- 房源合集：合集标题、模板、房源条目、排序、每套房源公开字段和图片。
- 生成同款：复制公开字段和媒体引用，替换为当前导入用户的微信/电话，并把原发布者作为默认上游联系人。

边界：

- 不继承原发布者私密保存的真实房东/二房东/渠道联系方式。
- 如果转发的是贝壳等第三方小程序卡，仍只能按第三方给到的外壳信息保存为待补全草稿，不能承诺完整复刻。

## 8. 验收标准

- 首页默认显示房源工作台，不再弹出四工作台选择。
- 首页“切换工作台”入口不再主动出现。
- 资料、合集、反馈仍按房源工作台范围展示。
- 房源合集公开页能看到“我是中介，也想生成这种合集”。
- 单套房源公开页能看到“生成同款房源卡”。
- 生成同款页可填写微信号和上游联系人。
- 已填写过的微信号能本地记忆并自动带入。
- 复制给企业微信助手时，剪贴板内容包含来源、当前微信号、上游联系人和隐私边界说明。
- 小程序 JS 语法检查和 JSON 解析通过。

## 9. 2026-06-25 补充：展示排列与微信助手入口

- 所有合集模板的客户展示页支持“一列 / 双列”排列选择。
- 默认使用一列，优先保证房源图片、标题、标签和按钮不被挤压；双列作为用户主动选择的紧凑浏览模式。
- 按钮样式基线必须沉到 `miniprogram/app.wxss`，页面内只做必要的尺寸和颜色覆写。
- “打开微信助手”依赖微信官方 `wx.openCustomerServiceChat` 能力。小程序不能只凭微信号自动添加客服；默认由后端 `/api/wecom/customer-service-config` 复用现有企业微信整理助手配置，按 `WECOM_CORP_ID + WECOM_OPEN_KFID` 生成 `corpId/extInfoUrl`。
- 后端未部署、企业微信客服参数缺失或调用失败时，页面复制整理指令作为兜底，让中介可手动粘贴给助手。

## 10. 2026-06-25 补充：自有小程序卡后端识别

- 企业微信收到我们自己的房源卡或房源合集小程序卡时，后端必须从 `pagePath` 识别 `noteId/showcaseId/sourceNoteId/id`。
- 如果识别到房源卡，回查该房源的公开字段和公开媒体，写入导入草稿的 `structuredData.internalMiniapp`。
- 如果识别到房源合集，回查已发布合集的公开快照、模板、排列方式、公开条目和公开媒体，写入 `structuredData.internalMiniapp`。
- 回查公开结构时必须过滤上游联系人、房东、二房东、渠道、电话、微信、原始 rawText 等可能夹带私密关系的字段。
- 第三方贝壳等小程序仍按外壳标题和可解析网页链接生成待补全草稿，不承诺完整复刻。

## 12. 2026-06-26 补充：房东长文本批量拆房源

业务事实：

- 房东/二房东常把多套房源写在同一条群消息里，不一定每套都有图片。
- 原文里经常混有中介费、密码锁、看房电话、微信号、朋友圈照片视频、带看限制等上游信息。
- 这些上游信息对中介自己很有价值，但不能展示给客户。

处理规则：

- 长文本识别到多套房源时，先进入“房源批量识别”确认卡，中介可勾选要生成的房源。
- 每套房源生成独立 `property_listing`，标题、户型、租金、公开标签进入客户可见结构。
- `禁宠` 属于公开标签，可以展示给客户；`可办居住证/可落户/可办停车位/可开发票/燃气/卫生间带窗/干湿分离/已空/新装` 也按公开卖点处理。
- 上游电话、微信、中介费、密码锁、红包、朋友圈有照片视频、带小孩/孕妇/老人不租等写入 `visibilityConfig.privateData` 或 `privateTags`，只给发布者管理态看。
- 无图房源也允许生成卡片，后续可继续补图；不要因为没有图片而丢掉房源、价格和上游联系人。
- 如果用户不想拆房源，保留“按普通资料保存”兜底。

验收重点：

- 客户公开页不得展示上游电话、微信、中介费、密码锁、红包等私密字段。
- 中介管理态必须能看到系统识别出的私密上游备注提示。
- 一条原文里的多套房源不能只生成一条大杂烩资料。
