# 第二期工作台优化阶段性交接：房源工作台

更新时间：2026-06-24

## 1. 项目背景与目标

项目正式产品名是“资料整理助手”。

长期方向是把用户通过企业微信、微信小程序、手动录入、图片、链接等渠道沉淀下来的资料，整理成可编辑、可分享、可追踪的资料卡和展示页。当前阶段重点不只是“资料库”，而是让资料能进入不同业务场景的工作台。

房源工作台的业务目标：

- 帮中介用户把单套房源整理成可发客户的小程序页面。
- 支持客户浏览、留资、预约、咨询等反馈记录。
- 支持用户从房源库筛选房源，并生成可分享的房源合集。
- 让用户能知道“谁看了哪套房、是否需要联系、为什么要联系”。
- 让系统自动维护客观房源标签，后续筛选和生成合集不依赖用户手工打标签。

产品判断：

- 房源工作台不是单纯编辑器，而是“发房源给客户 -> 看反馈 -> 跟进 -> 再推荐”的轻工作流。
- 当前阶段不做复杂 CRM，只做足够轻的跟进闭环。
- 分享封面、营销化广告、四个工作台统一品牌露出，用户已决定等四个工作台都完成后再统一讨论。

## 1.1 团购/商品工作台首页一期

用户确认团购场景主入口采用“团购/商品工作台”：

- 不单独叫“商品工作台”，避免落入普通商品管理或电商后台竞品心智。
- 不只叫“团购工作台”，避免限制商品展示、商品合集和访客反馈。
- 商品是资料和展示载体，团购/接龙是私域团长场景的核心差异。

当前首页一期已完成：

- 顶部标题改为“团购/商品工作台”。
- 说明文案改为“整理商品，发到群里，管理接龙和买家反馈”。
- 首页四指标改为：
  - 商品
  - 待处理
  - 今日接龙
  - 访客
- 商品数和访客数按 `groupbuy_product` 商品资料过滤。
- 待处理和今日接龙使用现有卖家订单/接龙接口汇总。
- 四指标点击去向：
  - 商品：进入资料页，只看商品资料。
  - 待处理：进入接龙/买家名单的待处理筛选。
  - 今日接龙：进入接龙/买家名单的今日筛选。
  - 访客：进入团购看板访客页。
- 卖家侧订单页前台标题改为“接龙/买家名单”。

当前资料库商品卡一期已完成：

- `groupbuy_product` 商品卡从普通资料卡升级为业务卡片。
- 商品卡展示状态：
  - 待处理
  - 有接龙
  - 有下单
  - 有访客
  - 待发布
- 商品卡标题下方前置展示：
  - 价格
  - 规格
  - 提货方式
  - 截止时间
- 商品卡展示接龙/下单/待处理/访客信号。
- 有客户动态时操作区为“处理接龙 + 分享 + 更多”。
- 无客户动态时操作区为“分享 + 更多”。
- “处理接龙”进入单商品接龙/下单名单，空名单也展示该商品空态。
- 商品详情页顶部工作台名称同步为“团购/商品工作台”。

当前边界：

- 本轮只收首页入口层、轻筛选和命名，不扩库存、支付、核销、完整订单或电商后台。
- 后续再继续打磨商品详情页、客户页、接龙看板和团购合集。

## 2. 当前阶段目标

本阶段围绕房源工作台完成“从可用到更顺手”的打磨。

目标包括：

- 房源资料库卡片更清楚展示租金、户型、客户状态和下一步动作。
- 房源库支持更实用的筛选，不只靠搜索或用户标签。
- 房源详情页分层：默认先看发客户和客户反馈，低频编辑项下沉。
- 房源详情增加客户视角预览，用户发出去前能快速判断客户第一眼看到什么。
- 单套房源和合集发布前做轻提醒，减少缺封面、缺租金、缺联系方式、已租误发等问题。
- 合集新建链路按用户心智改为：先选模板 -> 新建合集 -> 生成方式 -> 选择确认房源 -> 预览发布。
- 合集支持按条件筛选自动选房源。
- 系统标签根据房源字段自动补齐，用户标签只表达个人判断。

## 3. 已完成的功能

- 房源卡保留用户原始标题，不改用户标题里的表情符号和行业写法。
- 房源卡第二行显示租金和户型，之后顺延来源、打开、访客、客户动态。
- 有客户动态时，“看客户”和“分享”按钮都保留，不再因为出现看客户而隐藏分享。
- 房源卡新增状态：

  - 已跟进
  - 有浏览
  - 待分享

用户已确认：

- 系统标签不让用户逐个点选。
- 系统标签应根据房源字段默认补齐。
- 后续按标签选房和生成合集要依赖系统标签。

当前系统标签覆盖：

- 租金区间：
  - 1300以下
  - 1300-1800
  - 1800-2500
  - 2500以上
- 户型 / 类型：
  - 公寓
  - 一房
  - 两房
  - 三房
- 位置：
  - 地铁口
  - 地铁
- 楼层：
  - 电梯房
  - 楼梯房
- 面积：
  - 小户型
  - 30-50㎡
  - 50㎡以上
- 押付：
  - 押一付一
  - 押一付三
- 入住：
  - 随时入住
  - 本周可住
- 状态：
  - 可租
  - 已租
  - 暂停推广
  - 待确认

数据关系：

- `systemTags`：系统根据字段自动生成。
- `userTags`：用户手动选择或输入的个人判断标签。
- `tags`：统一筛选字段，合并 `systemTags` 和 `userTags`。

已修正的边界：

- `1300-1800`、`1800-2500` 这类稍长价格区间不会被标签长度规则过滤。
- 租金区间只根据明确租金/价格字段生成，避免把标题编号如 `B-938` 误识别为 938 元租金。

### 3.6 标签设置使用链路

标签设置页定位为“常用标签库”，不是自动给所有房源打标签。

用户使用路径：

1. 资料库 -> 更多工具 -> 标签设置。
2. 创建常用标签。
3. 进入单套房源详情。
4. 切到“编辑资料”。
5. 在“资料归类”中选择常用标签。
6. 保存后返回资料库，该房源卡片会显示标签，并可用于标签筛选。

## 6. 已知问题和风险

### 6.1 真机视觉仍需验收

房源详情新增“客户视角预览”和“发布前检查”后，需要真机确认：

- 是否过长。
- 文案是否让用户焦虑。
- 按钮和标签是否上下左右居中。
- 小屏是否拥挤。

### 6.2 筛选面板可能变长

资料库房源筛选已增加多个维度：

- 价格
- 户型
- 地铁 / 电梯
- 面积
- 押付
- 入住
- 状态

风险：

- 面板高度增加。
- 用户可能觉得筛选项太多。

后续可考虑：

- 常用条件常驻。
- 更多条件折叠。
- 最近使用条件置顶。

### 6.3 系统标签依赖字段质量

系统标签是根据结构化字段和文本判断自动生成。

风险：

- 如果用户字段填得不规范，标签可能缺失。
- 面积、楼层、押付等字段如果只写在很随意的备注里，识别可能不完整。
- 系统标签应辅助筛选，但不要向用户承诺 100% 准确。

### 6.4 发布前检查不强阻断

用户工作流需要快速发房，所以当前发布前检查是提醒，不是强制阻断。

风险：

- 用户可能仍然确认发布缺项合集。

产品取舍：

- 先提醒，允许继续发布。
- 后续可根据用户反馈决定是否对“无房源”“无联系方式”这类强问题阻断。

### 6.5 合集模板图服务器资源

模板图建议放服务器 webp，当前小程序配置的是线上 URL。

风险：

- 如果服务器静态文件未部署或 Nginx 未正确暴露，模板图会加载失败。
- 需要真机确认图片是否能加载、是否被小程序域名规则允许。

### 6.6 微信分享卡营销化暂缓

用户想在微信转发卡里做轻广告营销小程序，但已决定暂缓到四个工作台都完成后统一设计。

风险：

- 后续不要在房源单独加一套营销露出，否则四个工作台风格可能不统一。

### 6.7 当前工作区很脏

当前仓库有大量历史改动和未跟踪文件。

风险：

- 新 Codex 不应随意 `git checkout`、`git reset` 或回滚。
- 如果需要提交，必须先和用户确认提交范围。

## 8. 下一步建议执行顺序

### 第一优先级：真机验收房源工作台

建议按真实用户流程走：

1. 进入资料库。
2. 查看房源卡第二行租金/户型是否清楚。
3. 测试房源筛选：
   - 价格
   - 户型
   - 地铁
   - 电梯/楼梯
   - 面积
   - 押付
   - 入住
   - 状态
4. 点“用当前筛选生成合集”。
5. 确认合集编辑页条件已带入，候选房源一致。
6. 打开房源详情。
7. 看“发客户”页签中的客户视角预览是否直观。
8. 看单套房源发布前检查是否提示合理。
9. 处理客户反馈，确认红点/待处理状态是否刷新。
10. 发布合集，确认发布前检查弹窗只提醒、不误阻断。

### 第二优先级：修细节问题

真机验收后优先修：

- 文案太重或太焦虑。
- 筛选面板太长。
- 标签或按钮文字不居中。
- 小屏卡片拥挤。
- 发布前检查误报。
- 系统标签缺失或误判。

### 第三优先级：不要继续扩房源大功能

房源工作台当前已经完成主要闭环。

除非验收发现阻断问题，否则建议先进入其他三个工作台：

- 团购 / 商品工作台
- 电子名片工作台
- 服务方案工作台

### 第四优先级：四个工作台完成后统一讨论

等四个工作台都稳定后，再统一做：

- 微信转发卡轻广告营销。
- 分享封面品牌露出。
- 四个工作台统一首页入口和风格。
- 更完整的数据复盘。
- 更系统的客户运营闭环。
