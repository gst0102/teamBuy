## 1. 项目背景与目标

项目正式产品名为“资料整理助手”。当前阶段聚焦“房源工作台”，第一批目标客户是租房中介、二房东、房源对盘群里的房源流通参与者。

核心业务目标：

- 让中介把微信群里的房源文字、微信笔记、图片资料转成自己的房源卡和房源合集。
- 对外展示时替换成中介自己的微信/电话，方便发客户、发同行、发群。
- 对内保留上游联系人、房东电话、微信、中介费、密码锁、红包、带看限制等私密信息。
- 让中介通过“生成同款”“精选橱窗”“清单对比/合集”快速复用同行公开房源，形成自传播。
- 通过企业微信成员好友承接房源导入，让用户可以把房源资料直接发给“房源助手”，再回到小程序查看整理结果。

长期架构仍遵循 `docs/stage2-docs/08-plugin-architecture.md`：稳定基座负责企业微信通信、会话内容存档、身份识别、会话管理、合规、支付、展示页基础能力；具体整理能力作为可插拔 Skill。

## 2. 当前阶段目标

第五期的阶段目标是把“房源工作台”从功能堆叠收口成第一批中介能理解、能上手、能愿意继续使用的主链路：

1. 首页只突出房源工作台，不再同时教育多个工作台。
2. 主入口回到“添加企业微信房源助手”，用户把群里的房源/微信笔记转发给企业微信成员。
3. 后端通过企业微信会话内容存档接收消息，解析并生成房源资料/房源合集。
4. 小程序负责展示整理结果、房源卡、合集、客户反馈和后续管理。
5. 暂时不再把“微信客服自动回小程序卡片”作为首页主链路，避免入口混乱。

最新收口方向：**企业微信成员好友 + 会话内容存档收消息是主入口；微信客服仅作为可选底层能力研究，不再放在首页引导。**

## 7. 用户已经确认过的产品/技术决策

### 7.1 产品定位

- 第一批客户聚焦租房中介。
- 第一增长场景是同行对盘群。
- 核心价值是把群里的房源快速变成自己的房源卡/合集。
- “清单对比”和“精选橱窗”是第一批主推形态。
- 微信联系比电话联系更重要，但电话仍保留。

### 7.2 工作台策略

- 其他三个工作台先隐藏，不删除代码。
- 当前只打“房源工作台”这一点。
- 首页不要变成复杂导航页，要让中介一眼知道能做什么。

### 7.3 导入入口

- 主入口使用企业微信成员好友，不再强推微信客服入口。
- 用户添加企业微信后可以置顶，方便从群里转发房源。
- 首页不再同时出现“微信客服”和“企业微信成员”两个入口，避免认知混乱。

### 7.4 数据隔离

- 上游电话、房东微信、中介费、密码锁、红包、带看协作信息只给创建者自己看。
- 客户打开公开页面时只看到中介愿意展示的信息。
- B 中介生成同款后，对外联系方式变成 B；A 的私密上游联系人不直接给 B。

### 7.5 房源解析

- 一条房东消息可能包含多套房源，要支持拆分。
- 不是每条房源都有图片，不能把无图作为失败。
- `禁宠` 是公开标签。
- 媒体资产去重和 WebP/hash 存储是长期底座方向，后续继续核对实现完整性。

### 7.6 同行/房东识别

- 疑似中介/疑似房东不要直接进入客户待跟进主池。
- 可以加标签并进入单独资源/反馈视图。
- 这类能力未来可插件化。

### 7.7 微信客服与企业微信

- 微信客服 API 技术上有收发能力，但用户入口不好找，不适合作为当前主入口。
- 企业微信成员好友更符合中介使用习惯。
- 暂时不考虑企业微信主动给用户发小程序卡片，先让小程序承接结果展示。
